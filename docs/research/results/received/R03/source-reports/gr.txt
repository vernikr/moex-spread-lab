# BCS Trade API: возможности, инфраструктура и ограничения автоматизации фьючерсных спредов MOEX

Настоящий отчёт представляет собой независимое экспертное исследование программного интерфейса BCS Trade API, предоставляемого брокером БКС для автоматизации торговых операций, трансляции рыночных данных и контроля клиентских портфелей на Московской бирже. Исследование выполнено в интересах построения среднестрочных спредовых стратегий на срочном рынке (фьючерсах MOEX) и сфокусировано на выявлении задокументированных возможностей, технических ограничений, рисков инфраструктурных сбоев и требований к проектированию клиентского адаптера.

---

## 1. Правовой статус, условия подключения и экономический контекст счёта

Программный комплекс BCS Trade API разработан брокером БКС как веб-интерфейс на базе REST и WebSocket для широкого круга клиентов. В соответствии с официальными условиями обслуживание через Trade API предоставляется физическим лицам — клиентам БКС. Доступ юридических лиц планируется к открытию в последующих релизах сервиса.

Допуск к эксплуатации API регулируется категориями риска инвестора:
* **Категория КНУР (клиент с начальным уровнем риска):** Доступ к Trade API полностью закрыт регламентом брокера.
* **Категории КСУР и КПУР (стандартный и повышенный уровень риска):** Сервис доступен в полном объёме. Наличие статуса квалифицированного инвестора или категории КПУР на основном брокерском счёте не распространяется автоматически на изолированные торговые субсчета без предварительной проверки соответствия нормативным требованиям брокера.

| Параметр доступа | Регламент BCS Trade API | Практическое значение для спредовой стратегии | Источники |
| :--- | :--- | :--- | :--- |
| **Субъект доступа** | Физические лица (клиенты БКС) | Доступен прямой запуск алгоритмов без усложненных юр. процедур | Официальная документация BCS Trade API |
| **Ограничения по риску** | Запрещено для КНУР; разрешено для КСУР / КПУР | Необходима верификация статуса КПУР на конкретном фьючерсном счёте | Регламент обслуживания БКС |
| **Тарификация сервиса** | Бесплатно (ранний доступ); отдельный тариф с мая 2026 г. | Отсутствие фиксированных расходов на этапе пилота; закладываются риски изменения тарифа | Условия сервиса BCS Trade API |
| **Сетевые протоколы** | REST (HTTPS), WebSocket (WSS) | Применимо для управления ордерами и асинхронного приема рыночных данных | Спецификация API |
| **География и сеть** | Домены `be.broker.ru` и `ws.broker.ru` | Доступ из РФ; при размещении на зарубежных VPS требуется проверка роутинга/VPN | Сетевые эндпоинты БКС |

Подключение API осуществляется клиентом самостоятельно через веб-интерфейс без участия сторонних менеджеров и без изменения глобальной конфигурации брокерских счетов:
1. Авторизация в веб-версии личного кабинета «БКС Мир инвестиций» (`lk.bcs.ru`).
2. Переход в раздел: *«Профиль» → «Счета и тарифы» → Выбор брокерского счёта → «Токены API»*.
3. Выпуск первично авторизованного Refresh-токена с назначением прав доступа.

При проведении начального тестирования спредовой стратегии выделяется виртуальный бюджет в размере $30\,000\text{ \cyrr.}$, включающий гарантийное обеспечение (ГО), ликвидность под вариационную маржу (ВМ) и резервы, размещаемый на том же счёте, где находится основной портфель свыше $40\text{ млн \cyrr.}$ в фонде денежного рынка LQDT. Принятие активов LQDT брокером в качестве неденежного обеспечения маржинальной торговли сопровождается установлением дисконта (haircut). В случае накопления отрицательной вариационной маржи по фьючерсному спреду и исчерпания выделенного лимита $30\,000\text{ \cyrr.}$ брокерский риск-менеджмент запустит принудительную ликвидацию активов (Margin Call). Изъятие паев LQDT из основного портфеля без согласования считается критическим инцидентом и учитывается в лимите экстренного финансирования.

Оценка эффективности стратегии проводится относительно базового сценария сохранения средств в LQDT с учётом одинаковых внешних денежных потоков. Допустимое накопленное отставание от LQDT за период испытаний составляет $10\,000\text{--}15\,000\text{ \cyrr.}$ Регламент реагирования включает:
* Сигнал предупреждения при просадке относительно LQDT на $5\,000\text{ \cyrr.}$;
* Обязательную коррекцию или приостановку торгов при просадке $10\,000\text{ \cyrr.}$ от максимума относительного результата или накопленном отставании $10\,000\text{ \cyrr.}$;
* Внешнюю границу аварийного останова при отставании $15\,000\text{ \cyrr.}$ с пересмотром условий через 90 календарных дней.
* Внесение экстренных средств ограничено суммой $15\,000\text{ \cyrr.}$ (максимальный суммарный баланс $45\,000\text{ \cyrr.}$) и допускается исключительно для предотвращения ликвидации или безопасного вывода позиции в ноль, но не для усреднения или новых входов.

## 2. Архитектура аутентификации, безопасность и управление сессиями

Взаимодействие с BCS Trade API основано на двухкомпонентной схеме протокола OAuth 2.0, реализуемой через сервис авторизации Keycloak. Процесс аутентификации строго разделен между ручным выпуском долгоживущего ключа и автоматической ротацией сессионных токенов.

Первичным элементом доступа является **Refresh-токен**:
* Выпускается вручную в личном кабинете БКС для конкретного брокерского счёта.
* Отображается в интерфейсе **строго один раз** и не подлежит восстановлению или повторному просмотру.
* Обладает нормативным сроком действия 90 календарных дней.
* Допускает параллельное существование нескольких активных токенов на одном счёте.

Сессионный **Access-токен** запрашивается программно путем отправки POST-запроса к сервису Keycloak с передачей действующего Refresh-токена:
* Срок жизни Access-токена составляет 24 часа.
* Передается в HTTP-заголовке `Authorization: Bearer <access_token>` при каждом REST-запросе и при инициализации WebSocket-соединений.

Права доступа инкапсулируются на уровне скоупов (Client ID) при выпуске Refresh-токена:
1. **`trade-api-read` (Только для чтения):** Разрешает получение рыночной информации, стаканов, спецификаций, портфеля и лимитов. Выставление, отмена и замена торговых заявок с этим скоупом блокируются сервером.
2. **`trade-api-write` (Для торговли и чтения данных):** Предоставляет полный доступ к выставлению, снятию и изменению ордеров на Мосбирже, а также к балансовым сервисам.

Механика отзыва токенов демонстрирует различие в обработке прав:
* При ручном удалении из веб-кабинета Refresh-токена с правами `trade-api-write` все ранее сгенерированные на его основе Access-токены **аннулируются сервером мгновенно**.
* При удалении Refresh-токена `trade-api-read` действующие Access-токены сохраняют работоспособность до завершения их 24-часового цикла.

Брокер БКС **не предоставляет публичного Sandbox (песочницы)** с виртуальным исполнением ордеров для Trade API. Любая проверка торговой логики должна производиться либо в эмулированном контуре на стороне клиента (Dry-Run), либо минимальными объёмами (1 лот) на реальном рынке.

## 3. Спецификация REST и WebSocket сервисов для фьючерсов MOEX

Архитектура BCS Trade API построена по шаблону Backend-for-Frontend (BFF), в рамках которого функциональность распределена по специализированным микросервисам. Базовые точки подключения размещены на доменных именах `be.broker.ru` (HTTPS REST) и `ws.broker.ru` (WSS WebSocket).

| Название сервиса | Базовый URL / WebSocket URL | Зона ответственности и функциональность | Покрываемые сущности фьючерсов MOEX | Источники |
| :--- | :--- | :--- | :--- | :--- |
| **Auth (Keycloak)** | `https://be.broker.ru/trade-api-keycloak/realms/tradeapi/protocol/openid-connect/token` | Сервер аутентификации и выдачи OAuth2 токенов | Access- и Refresh-токены | Спецификация OAuth2 БКС |
| **Operations BFF** | `https://be.broker.ru/trade-api-bff-operations/api/v1`<br>`wss://ws.broker.ru/trade-api-bff-operations/api/v1/orders/execution-status/ws`<br>`wss://ws.broker.ru/trade-api-bff-operations/api/v1/orders/transaction-status/ws` | Управление заявками, трансляция статусов исполнения и сделок | Создание, отмена ордеров, поток статусов и сделок | Документация Operations API |
| **Portfolio BFF** | `https://be.broker.ru/trade-api-bff-portfolio/api/v1`<br>`wss://ws.broker.ru/trade-api-bff-portfolio/api/v1/portfolio/ws` | Мониторинг состава и доходности брокерского счёта | Фьючерсные позиции, накопительная ВМ, P&L | Документация Portfolio API |
| **Limit BFF** | `https://be.broker.ru/trade-api-bff-limit/api/v1`<br>`wss://ws.broker.ru/trade-api-bff-limit/api/v1/limits/ws` | Учёт финансовых ограничений и маржинальных показателей | Заблокированное ГО, свободная маржа, денежные средства | Документация Limit API |
| **Market Data** | `https://be.broker.ru/trade-api-market-data-connector/api/v1` | Поставка биржевых котировок, L2-стаканов и свечей | Стаканы цен, обезличенные сделки, исторические свечи | Документация Market Data API |
| **Information** | `https://be.broker.ru/trade-api-information-service/api/v1` | Справочные данные по финансовым инструментам | Спецификации контрактов, размер лота, шаг цены | Документация Info Service |

Сервис `information-service` поставляет полные спецификации срочного рынка MOEX: тикер (SECID), размер лота, минимальный шаг цены, стоимость шага цены, дату экспирации и начальное гарантийное обеспечение. Сервис `market-data-connector` обеспечивает получение котировок и снимков L2-стакана. Доступ к исторической информации ограничен возможностями REST-интерфейса, в связи с чем наиболее мелким бесплатным практически оправданным таймфреймом для анализа является интервал 1–5 минут.

Контроль финансового состояния срочного счёта выполняется через раздельные эндпоинты `bff-limit` и `bff-portfolio`:
* **Заблокированное ГО:** Сумма средств, удержанная брокером под открытые позиций и активные лимитные заявки.
* **Накопленная вариационная маржа (ВМ):** Текущий промежуточный финансовый результат, начисляемый или списываемый в течение торговой сессии до клиринга.
* **Свободный остаток:** Денежные средства, доступные для обеспечения новых ног фьючерсного спреда.

## 4. Механика исполнения спредовых ордеров и алгоритмические ограничения

В BCS Trade API **отсутствуют атомарные или связные спредовые заявки (Combo/Legged Orders)**. Построение фьючерсного спреда реализуется программным клиентом путем последовательной или параллельной отправки двух независимых одиночных ордеров на разносрочные или коррелирующие контракты.

В системе поддерживаются следующие базовые биржевые типы ордеров:
* **Market Order (Рыночная заявка):** Направляется на немедленное исполнение по доступным ценам биржевого стакана.
* **Limit Order (Лимитная заявка):** Содержит цену, хуже которой исполнение недопустимо.

Поддержка сложных брокерских условных заявок (Stop-Loss, Take-Profit) на стороне сервера в документации не гарантируется, поэтому стоп-логика должна эмулироваться алгоритмом на стороне клиента с отслеживанием триггерных цен по потоку WebSocket.

Идентификация ордеров строится на триаде ключей:
1. **`client_order_id`:** Уникальный строковый идентификатор, формируемый клиентским адаптером при отправке запроса. Используется для локальной привязки транзакций.
2. **`broker_order_id`:** Внутренний номер транзакции, присвоенный шлюзом БКС.
3. **`exchange_order_id`:** Номер заявки, зарегистрированный в торговой системе Московской биржи.

Главным технологическим риском при торговле спредами является **риск частичного хеджирования (Partial Hedge Risk / "Одноголая" позиция)**. Данный риск возникает в ситуации, когда Нога 1 спреда исполняется, а Нога 2 отклоняется биржей, застревает в стакане из-за недостатка ликвидности или теряет связь по таймауту. В этом случае алгоритм из нейтрального к рынку спреда превращается в держателя незахеджированной направленной позиции. Клиентский адаптер должен содержать жесткий таймер таймаута (Slippage Timeout) и при его превышении автоматически отменять неисполненную Ногу 2 и закрывать Ногу 1 рыночным ордером (Market Cross).

При совместной работе алгоритма и трейдера (ручные операции через приложение «БКС Мир инвестиций») все события по счёту транслируются в единый WebSocket-поток `wss://ws.broker.ru/trade-api-bff-operations/api/v1/orders/execution-status/ws`. Во избежание вмешательства алгоритма в ручные ордера оператора, адаптер должен фильтровать входящие события и обрабатывать только заявки с префиксом `client_order_id`, сгенерированным самим роботом.

## 5. Модель состояний заявок и процедура разрешения неопределённости (UNKNOWN)

Для предотвращения рассинхронизации локального состояния алгоритма с сервером БКС торговый адаптер должен реализовывать детерминированный автомат состояний (Finite State Machine).

Жизненный цикл ордера и правила перехода между состояниями приведены в таблице:

| Исходное состояние | Событие (Trigger Event) | Целевое состояние | Действие клиентского адаптера |
| :--- | :--- | :--- | :--- |
| **`NONE`** | Инициация отправки `POST /orders` | **`PENDING_SUBMIT`** | Запись `client_order_id` в журнал транзакций |
| **`PENDING_SUBMIT`** | Успешный ответ HTTP 200 OK | **`ACTIVE`** | Ожидание событий исполнения через WebSocket |
| **`PENDING_SUBMIT`** | Таймаут сети / Ошибка HTTP 5xx | **`UNKNOWN`** | Переход в режим заморозки, запуск процедуры сверки |
| **`PENDING_SUBMIT`** | Ошибка HTTP 4xx / Отказ риска | **`REJECTED`** | Сброс заявки, отмена парной ноги спреда |
| **`ACTIVE`** | Событие WS: Частичное исполнение | **`PARTIALLY_FILLED`** | Перерасчет требуемого объема для Ноги 2 |
| **`ACTIVE` / `PARTIALLY_FILLED`** | Событие WS: Полное исполнение | **`FILLED`** | Фиксация готовности ноги, перевод спреда в активный |
| **`ACTIVE` / `PARTIALLY_FILLED`** | Событие WS: Подтверждение отмены | **`CANCELED`** | Фиксация снятия ордера |
| **`ACTIVE`** | Отправка `DELETE /orders/{id}` | **`PENDING_CANCEL`** | Ожидание подтверждения отмены от биржи |

Состояние **`UNKNOWN`** является наиболее критическим аспектом асинхронного взаимодействия. Оно возникает, когда HTTP-запрос на создание ордера отправлен, но ответ не получен из-за сетевого обрыва, сбоя сокета или задержки сервера.

Порядок разрешения состояния `UNKNOWN` включает следующие шаги:
1. **Категорический запрет повторной отправки:** Повторно выставлять заявку до выяснения статуса первой строго запрещено во избежание удвоения позиции.
2. **Опрос REST-сервиса операций:** Выполняется запрос GET на `https://be.broker.ru/trade-api-bff-operations/api/v1/orders` с фильтрацией по сохраненному `client_order_id`.
3. **Мониторинг WebSocket-транзакций:** Адаптер анализирует входящие кадры в канале `wss://ws.broker.ru/trade-api-bff-operations/api/v1/orders/transaction-status/ws` в течение заданного интервала (3–5 секунд).
4. **Принятие решения по результатам сверки:**
   * Если ордер найден со статусом `ACTIVE` или `FILLED`, локальное состояние обновляется, и алгоритм возвращается в штатный режим.
   * Если ордер отсутствует во всех источниках по истечении таймаута сверки, состояние переводится в `REJECTED`, после чего алгоритм принимает решение о повторной попытке входа.

## 6. Матрица возможностей, ограничений и сценариев отказов (Fail-Safe)

Сводный анализ функциональных характеристик BCS Trade API представлен в матрице ниже.

| Функциональный блок | Задокументированные возможности | Технические ограничения и неизвестное | Источники |
| :--- | :--- | :--- | :--- |
| **Торговые операции** | Выставление и отмена лимитных и рыночных заявок | Отсутствие атомарных спредовых пакетов; выполнение только двумя ордерами | Спецификация торговых операций |
| **Аутентификация** | Двухуровневый OAuth2 (Refresh 90 дн., Access 24 ч.) | Мгновенная аннуляция Access-токенов при удалении ключа `write` | Спецификация безопасности |
| **Потоковые данные** | WS-трансляция ордеров, сделок, портфеля и лимитов | Обязательность самостоятельной обработки разрывов сокетов и запроса Snapshot | Спецификация WebSocket сервисов |
| **Рыночные данные** | REST-выгрузка котировок, L2-стаканов и свечей | Точные задокументированные Rate Limits на число запросов стакана в секунду отсутствуют | Спецификация Market Data |
| **Тестирование** | Проверка работы на реальном счете минимальным объемом | Отсутствие официального Sandbox-контура с виртуальной биржей | Регламент проведения проверок |
| **Маржинальный учет** | Передача данных по ГО, ВМ и балансу через API | Отсутствие автоматической защиты основного портфеля (LQDT) от списания залогов | Правила маржинальной торговли |

Для обеспечения отказоустойчивости (Fail-Safe) клиентский адаптер должен иметь четкие правила обработки нештатных ситуаций:

1. **Таймаут HTTP POST запроса (Timeout after Acceptance):**
   Перевод ордера в статус `UNKNOWN`. Запрет отправки новых ордеров. Инициация сверки через REST и WebSocket.
2. **Частичное исполнение спреда (Partial Hedge):**
   Если одна нога исполнена, а вторая застряла в стакане дольше установленного лимита времени, вторая нога отменяется, а первая закрывается рыночной заявкой для возврата в нейтральное состояние.
3. **Истечение срока действия Access-токена во время торгов:**
   Адаптер должен запрашивать ротацию токена через Keycloak каждые 20–22 часа, не дожидаясь наступления 24-часового лимита.
4. **Обрыв и пропуск кадров WebSocket:**
   При восстановлении сетевого соединения адаптер выполняет полный запрос снимка состояния (Snapshot) портфеля, лимитов и активных ордеров через REST-интерфейсы.
5. **Повторная отправка дубликата ордера:**
   Генерация `client_order_id` на основе UUID v4 гарантирует уникальность запросов. Повторный вызов функции отправки с тем же идентификатором блокируется на уровне локального автомата состояний.
6. **Превышение лимита частоты запросов (HTTP 429 Too Many Requests):**
   При получении ответа 429 адаптер приостанавливает отправку сообщений и применяет алгоритм экспоненциальной задержки (Exponential Backoff с случайным джиттером).
7. **Рассинхронизация данных по ГО и ВМ:**
   При расхождении локально рассчитанной маржи с данными сервиса `bff-limit` более чем на 5%, стратегия блокирует открытие новых спредовых позиций.
8. **Параллельное вмешательство трейдера с мобильного устройства:**
   При обнаружении сторонних изменений позиций из WebSocket-потока, не содержащих идентификатора алгоритма, робот пересчитывает доступный капитал и игнорирует чужие ордера.
9. **Принудительная ликвидация позиций брокером (Margin Call):**
   Фиксация внешнего закрытия позиций, мгновенная отмена всех выставленных роботом лимитных заявок, переход в режим `HALT` и отправка уведомления оператору в Telegram.

## 7. План предварительных проверок и границы ответственности адаптера

Во избежание незапланированных финансовых потерь эксплуатация системы разделяется на этап безопасного аудита в режиме «Только чтение» и этап санкционированного допуска к реальным торгам.

### План предварительных проверок (Read-Only Inspection)
1. **Проверка аутентификации:** Выпуск токена `trade-api-read`. Получение Access-токена через Keycloak. Проверка регулярности обновления сессии.
2. **Проверка справочников:** Запрос спецификаций выбранной фьючерсной пары через `information-service` (проверка соответствия шага цены и размера лота).
3. **Проверка поставки стаканов:** Подключение к `market-data-connector`. Измерение задержек (Latency) получения L2-стаканов.
4. **Сверка балансовых показателей:** Запрос данных о денежных средствах, ВМ и заблокированном ГО через `/bff-limit` и `/bff-portfolio` с последующей сверкой с личным кабинетом БКС.
5. **Тест стабильности WSS:** Непрерывный мониторинг WebSocket-каналов на VPS в течение 24 часов с фиксацией обрывов и пинга.

Допуск к реальной торговле (с выпуском токена `trade-api-write`) оформляется отдельным решением только после успешного выполнения всех пунктов проверки в режиме чтения.

### Архитектурный контур и ресурсы адаптера
Торговый адаптер проектируется как автономный фоновый процесс. В соответствии с ограничениями инфраструктуры:
* **Занимаемая память (RAM):** Бюджет фонового процесса составляет 250–350 МБ (на VPS 1 ГБ RAM + 2 ГБ swap).
* **Нагрузка на ЦП:** Асинхронная обработка (Async I/O) без ресурсоемких математических вычислений для эффективной работы на 1 vCPU.
* **Локальное хранение:** Фиксация состояний ордеров и журнала транзакций в локальной базе данных (SQLite) в режиме WAL.
* **Изоляция секретов:** Refresh-токены передаются исключительно через переменные окружения (`ENV`) и не записываются в конфигурационные файлы или логи.

## Выводы

Программный интерфейс BCS Trade API предоставляет необходимый набор инструментов для реализации торговых операций на срочном рынке Московской биржи, включая получение котировок, контроль маржинальных показателей и управление ордерами. При этом отсутствие атомарных спредовых ордеров и тестового контура Sandbox переносит основную задачу обеспечения надежности на клиентский адаптер. 

Для соблюдения заданных рисковых лимитов торговый алгоритм должен содержать развитый автомат состояний, встроенный модуль нейтрализации частичного исполнения ног спреда и механизм изоляции капитала, предотвращающий непреднамеренное списание активов основного портфеля. Выполнение предварительных проверок в режиме «Только чтение» является обязательным условием до допуска системы к реальным торгам.
