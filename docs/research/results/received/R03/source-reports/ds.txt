**Отчёт о возможностях BCS Trade API для автоматизации торговли фьючерсными спредами MOEX**  
*Дата исследования: 21 октября 2026 г. Все публичные источники проверены на эту дату. Персональный доступ и тариф не подтверждены.*

---

## 1. Продукт и версия

**Продукт:** «БКС Торговое API» (BCS Trade API) — программный интерфейс брокера «БКС Мир инвестиций» для автоматизации торговли на Московской бирже (MOEX), включая срочный рынок (фьючерсы).

**Версия:** публичная документация не содержит явного номера версии API (например, `v1`). В структуре URL эндпоинтов присутствует сегмент `/api/v1/`, однако это не версия продукта, а версия пути. Документация обновляется; последние публичные анонсы датированы 2026 годом (например, расширение лимитов и новые методы). Для целей отчёта версия обозначена как **действующая публичная версия на октябрь 2026 г.**, без привязки к семантическому номеру.

**Важно:** BCS Trade API — это **не** MOEX ISS API и не сторонние обёртки (например, `bcs-trade-go`, `bcs-trade-php`). Все выводы ниже относятся только к официальному продукту БКС, если не указано иное.

---

## 2. Доступ клиента, связь со счётом и квалификация

### 2.1. Требования к клиенту
- Необходим **хотя бы один брокерский счёт** в «БКС Мир инвестиций».
- Подключение и выпуск токенов происходят в веб-версии личного кабинета: «Профиль» → «Счета и тарифы» → выбрать счёт → «Токены API».
- API **бесплатен** для использования (токены выпускаются без явной платы); взимание отдельной абонентской платы за API в публичных источниках не подтверждено.

### 2.2. КПУР и квалификация
Прямых требований к статусу квалифицированного инвестора (КПУР) для **доступа к API как таковому** в официальной документации не обнаружено. Однако для **торговли отдельными инструментами** (например, некоторыми заблокированными иностранными бумагами или внебиржевыми инструментами) может требоваться статус квалифицированного инвестора. Для фьючерсов MOEX ограничение по КПУР не указано, но это остаётся **неподтверждённым** для конкретного счёта пользователя; статус КПУР у брокера может влиять на доступные инструменты и уровни риска.

### 2.3. География и сетевые ограничения
Официальных заявлений о географических ограничениях именно для BCS Trade API в проверенных источниках **не найдено**. Страницы сторонних сервисов, упоминающие ограничения для резидентов РФ, относятся к другим продуктам и не могут быть перенесены на BCS Trade API. Для доступа к веб-сервисам БКС рекомендуется использовать российские сертификаты или Яндекс.Браузер — это связано с TLS-сертификатами, а не с блокировкой по географии. Вопрос о доступности API с зарубежных IP-адресов остаётся **неизвестным** и должен быть уточнён у поддержки.

### 2.4. Допустимость автоматизации
API явно предназначен для автоматической торговли: «Создавайте роботов и подключайте через API для непрерывного трейдинга без вашего непосредственного участия». Запретов на алгоритмическую торговлю в публичных условиях не обнаружено, однако **отсутствие прямого запрета не равно явному разрешению**; полноценные правила использования API (условия обслуживания) в открытом доступе не найдены. Этот пункт требует подтверждения у поддержки.

## 3. Авторизация, токены и права

### 3.1. Схема OAuth 2.0 (refresh / access)
- **Refresh-токен** выпускается вручную в личном кабинете; бывает двух типов: «для торговли и чтения данных» и «только для чтения».
- С помощью refresh-токена клиент **самостоятельно генерирует access-токен** (OAuth 2.0 refresh token flow).
- **Срок жизни access-токена — 24 часа**, после чего его нужно получить заново. Refresh-токен действует **90 суток**; его можно удалить вручную, что немедленно аннулирует все выпущенные на его основе access-токены (для торговых токенов; для read-only токенов уже выпущенный access-токен может продолжать работать до истечения 24 часов).

### 3.2. Права доступа
Токен с правами «для торговли» позволяет:
- создавать рыночные и лимитные заявки на MOEX;
- читать рыночные данные, портфель, исторические данные.
Токен «только для чтения» позволяет только читать данные и **не даёт права выставлять заявки**.

### 3.3. Хранение и отзыв
- Токен показывается один раз при выпуске; рекомендуется сохранить его в надёжном месте.
- Хранение токенов на стороне клиента (в коде, переменных окружения) не регламентировано, но стандартная практика безопасности требует **не передавать refresh-токен в открытом виде** и использовать защищённое хранилище.

### 3.4. Параллельные сессии
Официальных ограничений на количество одновременных сессий (HTTP или WebSocket) с одним токеном в проверенной документации **не обнаружено**. Это **неизвестность**, которую следует уточнить у поддержки перед архитектурным проектированием.

## 4. Лимиты запросов, подписок и пагинация

| Параметр | Значение / статус | Источник |
|---|---|---|
| Транзакций в секунду (торговые операции) | Увеличено с 5 до **10 транзакций/сек** (анонс 2026 г.) |  |
| Максимум транзакций в день | До **200 000** (анонс 2026 г.) |  |
| Лимит баров в одном запросе свечей | **1440** баров; при превышении — ошибка |  |
| Пагинация свечей | Клиентские библиотеки реализуют разбиение на части (например, по 1000 баров) |  |
| Лимиты WebSocket-подписок | Количество одновременных подписок на каналы (стакан, котировки, сделки) в публичной документации **не указано** | — (неизвестность) |
| Rate limit (HTTP 429) | При превышении лимита возвращается 429; клиент должен обрабатывать |  |

**Важно:** лимиты могут различаться в зависимости от тарифа или прав токена. Публичные анонсы отражают общие улучшения, но **персональные лимиты для конкретного счёта не подтверждены**. Лимиты WebSocket-соединений и подписок остаются **неизвестными** и требуют запроса в поддержку.

## 5. REST и потоковые возможности: охват фьючерсов MOEX

### 5.1. Справочники и спецификации
API предоставляет доступ к списку инструментов, включая фьючерсы: «Список доступных биржевых инструментов: акции, облигации, фонды, иностранная валюта, драгоценные металлы, **фьючерсы**». Детализация спецификаций фьючерсных контрактов (например, размер лота, дата экспирации) доступна через справочные эндпоинты, однако полный перечень полей в проверенных фрагментах не раскрыт. В WebSocket-потоке портфеля присутствуют поля `expireDate`, `ticker`, `instrumentType`, что позволяет идентифицировать фьючерсные позиции.

### 5.2. Рыночные данные
- **HTTP:** получение стакана (`GET /api/v1/order-book`), исторических свечей (`GET /api/v1/candles-chart`), списка сделок (`POST /api/v1/trades/search`).
- **WebSocket:** потоковые каналы для стакана (глубина до 20 уровней), котировок, последних свечей, обезличенных сделок, а также портфеля, лимитов и маржинальных показателей в реальном времени.

### 5.3. Портфель, деньги, ГО и позиции
- **WebSocket-портфель** отдаёт позиции, включая фьючерсные: поле `lockedForFutures` (занято под ГО по фьючерсам), `futureHolding` (фьючерсные позиции), `varMargin` (вариационная маржа), `cbplPlanned` (планируемая позиция после клиринга).
- **WebSocket-лимиты** содержит блоки `moneyLimits`, `futureHolding`, `futuresLimits` с полями для ГО, вариационной маржи, чистых позиций.
- **Маржинальные показатели** включают `fortsStability` (устойчивость по ФОРТС), `riskLevel`, `refillSum` (сумма для выхода из маржин-колла), `fortsForcedClosure` (уровень принудительного закрытия).

### 5.4. Заявки и исполнения
- **HTTP:** создание, изменение, отмена заявок; получение списка активных заявок и истории сделок.
- **WebSocket:** поток статусов заявок с событиями создания, частичного исполнения, полного исполнения, отмены, замены и отклонения.

## 6. Типы заявок, time-in-force и идентификаторы

### 6.1. Типы заявок
Официально документированы **рыночные** (`orderType = 1`) и **лимитные** (`orderType = 2`) заявки. Стоп-лосс и тейк-профит в публичной документации на октябрь 2026 г. **ещё не реализованы**, но анонсированы в планах на июнь 2026 г..

### 6.2. Time-in-force (срок действия)
В проверенных фрагментах официальной документации BCS Trade API **не удалось найти** явного перечисления поддерживаемых значений `timeInForce` (например, GTC, IOC, FOK). В статусах заявок поле `timeInForce` отсутствует; документированы только `orderType` и `orderStatus`. Это **существенная неизвестность**: возможно, API поддерживает только дневные заявки (по умолчанию) или скрытые значения, не описанные публично. Для стратегий, требующих GTC или IOC, этот вопрос необходимо адресовать поддержке.

### 6.3. Идентификаторы и идемпотентность
В потоке статусов присутствуют:
- `clientOrderId` — клиентский идентификатор заявки (UUID);
- `originalClientOrderId` — идентификатор изменённой заявки;
- `orderId` — биржевой/брокерский идентификатор;
- `executionId` — идентификатор сделки.

**Идемпотентность:** официальной гарантии идемпотентности при повторной отправке заявки с тем же `clientOrderId` в проверенной документации **не обнаружено**. Это означает, что при timeout клиент не может безопасно повторить запрос, полагаясь на серверную дедупликацию; необходима собственная логика сверки состояния. **Атомарной спредовой заявки** (одной транзакцией на две ноги) API не предоставляет: спреды реализуются только как две независимые заявки, что создаёт риск частичного исполнения («одна нога исполнена, другая нет»).

## 7. Sandbox / тестовый контур

**Официальной песочницы (sandbox) у BCS Trade API нет.** Сторонние интеграторы прямо указывают: «У БКС нет песочницы — поэтому торговый режим включай осознанно: каждая заявка реальная». Это означает, что **проверка торговых сценариев без реальных сделок через официальный API невозможна**. Для предварительных проверок остаются только read-only методы (токен «только для чтения») и внешние симуляторы, не гарантирующие поведение реального API.

## 8. Сценарии отказа и минимальная модель состояний

На основе документированных статусов и ограничений можно выделить следующие риски:

| Сценарий | Что известно | Что не обеспечено сервером / требуется клиенту |
|---|---|---|
| **Timeout после принятия заявки** | Статус заявки может быть неизвестен; API не гарантирует идемпотентность. | Клиент должен запросить список активных заявок или поток статусов, чтобы определить, была ли заявка принята; повторная отправка «вслепую» опасна. |
| **Частичное исполнение** | Статусы `orderStatus = 1` (частично исполнена) и `executionType = 1` документированы. | Клиент должен отслеживать `executedQuantity` и `remainedQuantity`, принимать решение о досрочном закрытии остатка или хеджировании. |
| **Истёкший access-токен** | Access-токен живёт 24 часа; при 401 клиентские библиотеки обновляют токен и повторяют запрос. | Серверная ротация не гарантируется; клиент должен реализовать автоматическое обновление по refresh-токену. |
| **Пропуск потока WebSocket** | Документация не описывает механизм replay/snapshot при разрыве. | Клиент должен после переподключения запросить актуальный снапшот (портфель, заявки) через HTTP и сверить состояние. |
| **Дубликат заявки** | Идемпотентность не документирована. | Клиент должен вести собственный журнал `clientOrderId` и не повторять отправку без сверки. |
| **Лимит запросов (429)** | Rate limit существует; при превышении возвращается 429. | Клиент должен реализовать экспоненциальную задержку и повтор с учётом лимита. |
| **Устаревшее ГО** | ГО и вариационная маржа передаются в WebSocket-потоке, но могут запаздывать. | Клиент должен запрашивать маржинальные показатели перед выставлением заявки и учитывать задержку. |
| **Ручное вмешательство** | API позволяет управлять заявками, поданными через другие интерфейсы (анонсировано). | Клиент должен периодически сверять активные заявки, чтобы не дублировать или не отменять ручные действия. |
| **Закрытие брокером (margin call)** | В маржинальных показателях есть `fortsForcedClosure`, `refillSum`. | Клиент должен отслеживать `riskLevel` и `stabilityStatusId`, чтобы заранее снижать риск; серверное принудительное закрытие не предотвращается клиентом. |

**Минимальная модель состояний заявки** (на основе документированных `orderStatus`):
`0 (Новая)` → `1 (Частично исполнена)` → `2 (Полностью исполнена)`; альтернативные ветви: `4 (Отменена)`, `5 (Заменена)`, `6 (Отменяется)`, `8 (Отклонена)`, `9 (Заменяется)`, `10 (Ожидает подтверждения)`. Клиент должен обрабатывать все переходы, включая асинхронные события `executionType`.

## 9. План будущих проверок только на чтение (без реальной торговли)

1. **Выпустить read-only refresh-токен** в личном кабинете БКС (не торговый).  
2. **Проверить авторизацию:** сгенерировать access-токен, выполнить `GET /api/v1/order-book` по фьючерсу (например, `SiZ6` или `RIM7`) и убедиться в получении стакана.  
3. **Проверить WebSocket-портфель:** подключиться к `wss://ws.broker.ru/trade-api-bff-portfolio/api/v1/portfolio/ws`, убедиться в получении позиций, включая `lockedForFutures` и `futureHolding`.  
4. **Проверить лимиты:** подключиться к `wss://ws.broker.ru/trade-api-bff-limit/api/v1/limits/ws` и зафиксировать структуру `futureHolding` / `futuresLimits`.  
5. **Проверить исторические свечи:** запросить `GET /api/v1/candles-chart` для фьючерса с ограничением 1440 баров.  
6. **Проверить статусы заявок (без создания):** подключиться к WebSocket-потоку статусов и убедиться, что он работает; реальные заявки не создавать.  
7. **Уточнить у поддержки** вопросы из раздела 10.  

**Допуск реальной торговли:** отдельное решение, **не входящее** в этот план. Требует подтверждения персональных лимитов, допустимости автоматизации для счёта, наличия/отсутствия time-in-force и идемпотентности, а также понимания правил использования API.

## 10. Вопросы поддержке API (tradeapi@bcs.ru)

1. **Time-in-force:** какие значения `timeInForce` поддерживаются для фьючерсных заявок (GTC, IOC, FOK, Day)? Если не документированы, можно ли их использовать?  
2. **Идемпотентность:** гарантирует ли сервер дедупликацию заявок при повторной отправке с тем же `clientOrderId`? Если нет, как рекомендовано обрабатывать timeout?  
3. **Параллельные сессии:** есть ли ограничение на количество одновременных WebSocket-подписок или HTTP-соединений с одним access-токеном?  
4. **Sandbox:** планируется ли официальная песочница для тестирования торговых сценариев без реальных сделок?  
5. **Персональные лимиты:** какие лимиты транзакций в секунду и в день действуют для конкретного счёта (зависят ли они от тарифа)?  
6. **Спреды:** поддерживает ли API какие-либо механизмы атомарной отправки двух заявок (спредов) или только независимые заявки?  
7. **Replay WebSocket:** предусмотрен ли механизм восстановления пропущенных сообщений после разрыва соединения, или клиент обязан запрашивать снапшот?  
8. **КПУР:** влияет ли статус КПУР на доступность фьючерсных инструментов через API?

## 12. Итоговые выводы и условия опровержения

- **BCS Trade API пригоден для автоматизации фьючерсной торговли на MOEX** в части рыночных данных, портфеля, ГО и выставления рыночных/лимитных заявок.  
- **Ключевые ограничения:** отсутствие песочницы, недокументированный time-in-force, отсутствие гарантий идемпотентности, отсутствие атомарных спредовых заявок, неизвестные лимиты WebSocket-подписок.  
- **Персональный доступ и тариф не подтверждены.** Все выводы основаны на публичной документации; реальная доступность для конкретного счёта может отличаться.  
- **Условия опровержения:** если поддержка подтвердит наличие time-in-force (GTC/IOC/FOK), идемпотентности по `clientOrderId` или появится официальная песочница, ограничения, отмеченные как «неизвестность», могут быть сняты. Если персональные лимиты окажутся ниже публичных (например, 5 транзакций/сек вместо 10), это изменит оценку пропускной способности стратегии.
