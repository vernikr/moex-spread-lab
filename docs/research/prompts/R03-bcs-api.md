## Question
What can the actual current BCS Trade API safely support for later unattended MOEX futures spread execution, and what remains uncertain? Start from BCS official documentation, terms, API changelogs and support pages; verify the product name/version rather than conflating unrelated APIs or community wrappers.

## Investigate
1. Client eligibility, account/tariff linkage, cost, qualified/KPUR consequences, permission scopes, geographic/network constraints and whether automated trading is permitted. List onboarding steps without asking for secrets or making account changes.
2. Auth/token lifetime and refresh/rotation, scopes, revocation, concurrent sessions, rate/connection/subscription limits, pagination and retention. Identify market data entitlements/delay separately from order entry. Do not assume the trading API gives free historical books.
3. Current REST/streaming capabilities and futures coverage: instruments/specifications, prices/books/trades, balances, cash/VM/margin, open positions, orders, fills, errors and order status. Record documented endpoints/event schemas only; examples redacted and read-only.
4. Order types/time-in-force, exchange/broker IDs, client IDs and idempotency semantics, partial fills, cancel/replace races, reconnect gaps, replay/snapshot mechanisms, reconciliation, ambiguous timeout handling and manual-API coexistence. Distinguish an atomic supported spread order from sending two independent orders rapidly.
5. Sandbox/paper account or lack thereof, testing without real trades, risk/kill mechanisms, fail-closed behavior, clock/calendar rules, recovery and credential isolation. Determine what is server-side vs must be implemented client-side. No automatic blind resend after an unknown order outcome.
