# Проверяемый отчёт: BCS Trade API — возможности и ограничения автоматизации фьючерсных стратегий на Московской бирже

Настоящий отчёт подготовлен в рамках предварительного исследования технической пригодности **BCS Trade API** для реализации среднесрочных спредовых стратегий на фьючерсах Московской биржи (MOEX). Отчёт носит аналитический характер и не является индивидуальной инвестиционной рекомендацией или торговым алгоритмом.

---

## 1. Официальный продукт, версия и архитектура

* **Официальный ресурс и документация:** [trade-api.bcs.ru](https://trade-api.bcs.ru), официальный портал БКС Мир Инвестиций.
* **Архитектурный паттерн:** REST API + WebSocket потоки (BFF — Backend-for-Frontend микросервисная архитектура).
* **Продуктовая база:** Цифровой шлюз брокера для программного доступа к рыночным данным, управлению портфелем и торговыми операциями.

---

## 2. Раздел 1. Доступ, статус КПУР и сетевые ограничения

* **Способ получения доступа:** Выпуск токенов осуществляется через веб-версию личного кабинета «БКС Мир Инвестиций» (*Профиль → Счета и тарифы / О счете → Токены API*).
* **Значение квалификации (КПУР):** Статус квалифицированного инвестора и категория с повышенным уровнем риска (КПУР) расширяют доступный перечень инструментов (производные финансовые инструменты с маржинальным плечом), однако на уровне REST/WebSocket протокола API авторизуется в отношении конкретного выбранного брокерского счёта. Брокерский бэк-энд проверяет лимиты ГО и маржинальные требования согласно текущему профилю риска клиента.
* **Сетевые ограничения и география:** Доступ к конечным точкам (endpoints) брокера осуществляется из интернета по протоколу HTTPS/WSS. Требуется стабильное сетевое соединение; использование зарубежных VPN-сервисов может вызывать повышенные сетевые задержки (latency) и разрывы WebSocket-соединений.

---

## 3. Раздел 2. Авторизация, сессии, лимиты и хранение данных

* **Механизм аутентификации:** Используется OAuth2 протокол через Keycloak-реализацию брокера.
* **Точки входа авторизации (Token Endpoint):** `[https://be.broker.ru/trade-api-keycloak/realms/tradeapi/protocol/openid-connect/token](https://be.broker.ru/trade-api-keycloak/realms/tradeapi/protocol/openid-connect/token)`.
* **Разделение прав (Scopes / Client ID):**
* `trade-api-read` — права только на чтение (просмотр портфеля, балансов, рыночных данных, справочников).
* `trade-api-write` — полные торговые права (создание, модификация и отмена заявок).


* **Сессии и лимиты:** Токены имеют ограниченный срок жизни, требуя регулярного обновления (ротации) по протоколу OAuth2. Параллельные сессии с одним токеном/учетной записью регламентируются брокером; превышение лимитов часто приводит к сбросу соединений (rate limiting). Исторические глубокие данные по стаканам (order book history) API, как правило, **не предоставляет бесплатно** в полном объеме — потоковые данные транслируются real-time, а ретроспективный анализ требует собственной локальной базы данных (tick-database).

---

## 4. Раздел 3. REST / WebSocket возможности и покрытие фьючерсов MOEX

Микросервисная структура API разделена на специализированные сервисы:

* **Market Data Service:** `[https://be.broker.ru/trade-api-market-data-connector/api/v1](https://be.broker.ru/trade-api-market-data-connector/api/v1)` — получение текущих котировок, стаканов и обезличенных сделок по фьючерсам MOEX.
* **Portfolio & Limits Service:** `[https://be.broker.ru/trade-api-bff-portfolio/api/v1](https://be.broker.ru/trade-api-bff-portfolio/api/v1)` и `limits` — мониторинг денежных средств, вариационной маржи (ВМ), гарантийного обеспечения (ГО) и открытых позиций.
* **Operations Service (Orders & Deals):** `[https://be.broker.ru/trade-api-bff-operations/api/v1](https://be.broker.ru/trade-api-bff-operations/api/v1)` — выставление, отмена заявок, просмотр истории сделок.
* **WebSocket Streams:** Поддерживаются потоковые каналы в реальном времени для лимитов, портфеля, статусов исполнения заявок (`execution-status/ws`) и статусов транзакций (`transaction-status/ws`).

> *Ограничение:* Информация по неторговым операциям в торговом API часто ограничена или недоступна (доступны только совершенные биржевые сделки купли-продажи).

## 5. Раздел 4. Типы заявок, идемпотентность и риски спредовой торговли

* **Типы заявок:** Поддерживаются стандартные рыночные (Market) и лимитированные (Limit) заявки. Параметры Time-in-Force (TIF) зависят от регламента MOEX (IOC, FOK, GTC и др.).
* **Идентификация:** Используются биржевые ID, брокерские внутренние ID и клиентские идентификаторы (Client Order ID) для предотвращения дублирования.
* **Спредовая торговля:**
* **Важное архитектурное ограничение:** BCS Trade API **не предоставляет атомарной спредовой заявки** (когда две ножки разных фьючерсов исполняются одновременно как единая транзакция на биржевом уровне, если это не отдельный системный календарный спред MOEX).
* Стратегия спреда должна реализовываться программно путем отправки двух независимых лимитированных/рыночных заявок. Это порождает классический риск частичного исполнения (*leg-risk*), при котором одна ножка исполнена, а вторая отклонена или зависла.



---

## 6. Раздел 5. Тестовая среда (Sandbox), риск-контроль и аварийные сценарии

* **Наличие Sandbox:** Полноценный изолированный Sandbox-счет для фьючерсов с эмуляцией стакана MOEX в документации публично не гарантирован; тестирование логики адаптера на реальном счете сопряжено с риском потери капитала (даже при минимальном объеме тестов в 30 000 ₽).
* **Риск-контроль и аварийные сценарии:**
* При возникновении сетевого таймаута (timeout) в момент отправки заявки **запрещено слепо повторять запрос** (репликация без проверки состояния порождает риск дублирования позиций). Необходимо запросить текущий статус заявки через Operations API (`/orders`).
* При разрыве WebSocket-потока клиент обязан инициировать процедуру восстановления (Replay/Snapshot sync) путем опроса REST endpoints для сверки актуального состояния портфеля и позиций.

## 7. Матрица возможностей и ограничений BCS Trade API

| Компонент / Функция | Доступность в BCS Trade API | Комментарий / Источник |
| --- | --- | --- |
| **Споты и Фьючерсы MOEX** | Доступно | Полный охват ликвидных фьючерсов через Market Data и Operations API. |
| **REST / WebSocket** | Доступно | Гибридная архитектура (REST для команд, WSS для потоков данных и статусов). |
| **Атомарные спреды** | **Недоступно** | Требуется клиентская логика двух независимых ног с риском *leg-risk*. |
| **Исторические стаканы** | Ограничено / Платное | Доступны real-time данные; глубокая история стаканов требует сторонних баз. |
| **Изолированный Sandbox** | Не гарантирован | Проверки требуют предельной осторожности на реальном счете. |

## 8. Модель состояний заявки (Order State Machine)

```
[ New / Created ] ---> ( Отправка в API ) ---> [ Pending / Submitted ]
                                                       |
         +---------------------------------------------+---------------------------------------------+
         |                                             |                                             |
         v                                             v                                             v
[ Partially Filled ]                          [ Filled (Исполнена) ]                       [ Rejected / Cancelled ]
 (требует контроля ножек)                                                                  (отказ биржи / брокера)

```

## 9. Критические сценарии отказа и вопросы в техническую поддержку БКС

### Сценарии отказа (Failure Scenarios)

1. **Timeout при отправке:** Заявка ушла, но ответ не получен. *Решение:* Запрет повторной отправки вслепую; обязательный запрос статуса по Client Order ID.
2. **Частичный хедж (Leg-risk в спреде):** Первая ножка исполнилась, вторая нет из-за скачка волатильности. *Решение:* Наличие аварийного алгоритма market-out (рыночного закрытия оставшейся ноги).
3. **Истёкший токен посреди сессии:** Ошибка 401 Unauthorized. *Решение:* Автоматический фоновый перевыпуск токена через Keycloak endpoint.

### Список вопросов для технической поддержки БКС API

1. Поддерживается ли официальный изолированный **Sandbox** (тестовый контур) для фьючерсов срочного рынка MOEX с целью отладки торговых роботов без риска реального капитала?
2. Каковы точные лимиты (rate limits) на количество запросов в секунду для REST API и максимальное число одновременно поддерживаемых WebSocket-подписок на биржевые стаканы?
3. Какова гарантия доставки и механизм восстановления пропущенных сообщений в WebSocket-каналах статусов выполнения заявок (`execution-status/ws`) при кратковременном обрыве связи?

## 10. План предварительных проверок (только на чтение)

Перед развёртыванием какой-либо автоматизации и выделением средств рекомендуется выполнить исключительно **безопасные тесты на чтение**:

1. Настроить OAuth2-авторизацию с токеном уровня `trade-api-read`.
2. Проверить стабильность REST-запросов к сервису `/information` и `/portfolio` на предмет корректного чтения балансов и текущего ГО.
3. Установить тестовое WebSocket-соединение с потоком котировок выбранной пары фьючерсов и измерить частоту разрывов/задержек в текущих сетевых условиях.
