# 1. Executive Summary, Bottom-Line Verdict & Architectural Foundation

### 1.1 The Operational Paradox and Architectural Bifurcation
The private MOEX futures-spread project operates under a fundamental operational paradox:
1. **The Mission-Critical Shared Host:** The target remote host is an entry-tier Virtual Private Server (VPS) configured with **1 vCPU, 1,024 MB physical RAM, 2,048 MB swap, and 20 GB SSD storage**, running Ubuntu 24.04 LTS x86_64. Crucially, this machine is already in production hosting an active, mission-critical **Xray / 3X-UI VPN server** (binding ports `22`, `443`, and `20724`) alongside an existing scheduled background task. Total background RAM headroom is assumed to be **250–350 MB**, but this headroom is *shared, unverified, and dynamic*.
2. **The Asymmetric Capital Risk:** The pilot allocation of **RUB 30,000** resides on the **exact same brokerage account** as a core, conservative capital holding exceeding **RUB 40,000,000 in the LQDT money-market fund**. Any catastrophic operational failure—such as an out-of-control automated trading script, unmonitored margin calls, or broker-driven forced liquidation of core collateral—presents asymmetric downside risk that dwarfs the pilot capital by three orders of magnitude.
3. **The Core Imperative:** **The trading analytics and monitoring infrastructure must NEVER compromise, degrade, throttle, or trigger Out-Of-Memory (OOM) termination of the production VPN daemon, the SSH server, or the broker account safety.** If system memory or disk resources face contention, the trading research workload must proactively self-throttle or terminate, leaving the host network services entirely undisturbed.

To resolve this paradox without requiring premature paid infrastructure or commercial software dependencies, this report establishes a strict **Architectural Bifurcation**:

### 1.2 Bottom-Line Feasibility Verdict
Based on exhaustive public-source desk research, mathematical modeling, and documentation review as of **2026-10-22**:

1. **VPS Coexistence is Technically Feasible but Strictly Conditional:**
   A continuous data collection, virtual ledger, and alert daemon **can safely run** within the 250–350 MB shared background allowance on the 1 GB VPS, **provided** it is implemented as a single-process, asynchronous daemon (Python 3.12 standard library or compiled Go/Rust) backed by an embedded SQLite database configured with strict memory-limiting pragmas. Heavy frameworks (Pandas, Polars, Docker, Docker Compose, PostgreSQL, Redis, FastAPI) are **strictly disqualified** from the VPS.
2. **Storage Retention Must Be Tiered:**
   Retaining multi-year uncompressed raw JSON snapshots on the 20 GB VPS disk is a **hard operational failure risk** (projected to consume 4.2 to 9.09 GB before indexing, WAL overhead, OS updates, and backups). The VPS must operate strictly as a rolling buffer (retaining 30 to 90 days of hot state in SQLite, $\le 1.5 	ext{ GB}$), while multi-year cold history is periodically synchronized and archived on the MacBook Pro.
3. **The MOEX ISS Legal Use Gate is Critical:**
   While MOEX provides free REST access to delayed (15-minute) market data via its Information and Statistical Server (ISS), MOEX's official terms explicitly state: *"Полученная из ИСС информация доступна только для ознакомления, не может быть использована для извлечения прибыли"* (Information obtained from ISS is available for familiarization only and cannot be used for profit extraction without a commercial contract). Free delayed access is legally sufficient for academic and non-display research, but transition to real trading requires commercial licensing or broker-provided datafeeds.
4. **Execution Latency Governs Strategy Viability:**
   With manual execution at VTB, operator response latency ranges from **3 to 90 minutes (median: ~5 to 15 minutes)**. Free MOEX ISS data carries an intrinsic **15-minute delay**. Consequently, the project cannot execute intraday high-frequency scalping; it must focus strictly on **medium-term calendar and inter-commodity spreads** with half-lives measured in days or weeks, where a 15-to-30-minute information and reaction delay represents acceptable slippage.

### 2.2 MOEX ISS Legal Terms & The Commercial Licensing Gate
A central discovery of this investigation is the legal divergence between technical accessibility and licensing authorization:
- **Technical Access:** The MOEX Information and Statistical Server (ISS) allows unauthenticated HTTP GET requests to delayed market data endpoints without requiring an API key. 15-minute delayed quotes, daily historical summaries, and contract specifications return HTTP 200 with JSON, XML, or CSV payloads.
- **Contractual Limitation:** The Russian-language Terms of Use (*Условия использования программного интерфейса ИСС*) state unambiguously:
  > *"Полученная из ИСС информация доступна только для ознакомления, не может быть использована для извлечения прибыли, публикации в средствах массовой информации, передачи третьим лицам или использования в автоматизированных торговых системах без заключения договора с ПАО Московская Биржа."*
- **Operational Impact on Project:**
  1. *Desk Research & Virtual Pilot (Stage 2–5):* Utilizing delayed ISS data to compute paper spreads, test statistical properties, and update an internal virtual ledger falls cleanly within analytical "familiarization and research" (*для ознакомления*), provided results are not redistributed publicly.
  2. *Live Capital Execution (Stage 6):* Relying directly on free ISS feeds to generate live automated trading orders at VTB or BCS breaches MOEX terms of use and exposes the operator to IP blacklisting and potential legal dispute.
  3. *Strategic Resolution:* The architecture must decouple the **Data Ingestion Seam**. For Stages 2–5, the collector consumes MOEX ISS delayed data. For Stage 6, the collector switches to the broker's authorized, authenticated client datafeed (e.g., BCS Trade API market data, which is licensed through the broker's exchange membership).

### 2.3 MOEX ISS Technical Interfaces, Query Surfaces & Practical Constraints
- **Primary Futures Endpoints:**
  - Security Specifications: `/iss/engines/futures/markets/forts/securities.json?iss.meta=off`
  - Intraday Candles: `/iss/engines/futures/markets/forts/boards/{BOARD}/securities/{SECID}/candles.json?from={DATE}&interval={INTERVAL}`
  - Daily Settlement & Historical Bars: `/iss/history/engines/futures/markets/forts/securities/{SECID}.json`
- **Pagination & Throttling Limits:**
  - MOEX ISS imposes a strict limit of **1,000 records per HTTP response** (1 000 rows per call). While default client libraries request 100 rows, queries must pass `start=0, 1000, 2000...` to paginate across broad history.
  - While MOEX does not publish an exact hard rate limit in its documentation, empirical developer usage and community libraries (`moex-iss`, `ru-moex-mcp`) confirm that sustained request rates exceeding **4 to 5 requests per second** trigger HTTP 429 ("Too Many Requests") or temporary TCP connection drops.
  - **Engineering Policy:** Ingestion jobs must implement strict client-side pacing at **1 to 2 requests per second** (average $\le 3–4	ext{ req/s}$, short bursts $\le 5–6	ext{ req/s}$), with randomized jitter (250–500 ms) and exponential backoff on HTTP 429/5xx responses.

- **BCS Trade API (Publicly Verified & Documented):**
  - Architecture: Modern REST HTTP endpoints paired with streaming WebSockets for orderbook depth and execution notifications.
  - Rate Limiting: Explicitly capped at **10 Requests Per Second (RPS)** on HTTP market data. WebSocket streaming permits up to **20 concurrent connections**, with up to **100 instruments tracked per connection**.
  - Historical Candles: Dedicated endpoint `/api/v1/candles-chart` allows querying timeframes M1, M5, M15, M30, H1, H4, D, W, MN, returning a maximum of **1,440 bars per call**.

    - *Permissions:* Tokens can be minted with granular scopes: "Только для чтения" (Read-Only) or "Для торговли и чтения" (Full Trading).
- **VTB Broker API Status (Unverified in Public Domain):**
  - Public desk research revealed **zero publicly documented, open REST/WebSocket trading APIs** for retail algorithmic clients at VTB as of October 2026.
  - VTB retail clients historically execute algorithmic trades via Windows-native QUIK terminal installations using LUA scripting or paid Trans2Quik/FIX connections.
  - **Strategic Impact:** Fully automated execution at VTB is dismissed as unviable for lightweight Linux VPS hosting. The project assumes **manual execution at VTB** during Stage 5 (driven by Telegram alert notifications) and defers programmatic execution to **Stage 6 at BCS**.

# 3. Embedded Workload Dimensioning & Mathematical Sensitivity Model

### 3.1 Universe, Ingestion, and Sampling Boundaries
The operational workload is derived strictly from the embedded planning assumptions defined in the project mandate:
- **Broad Futures Universe ($N$):** Evaluated across planning points $N \in [50, 100, 200, 300]$ active MOEX FORTS contracts across all trading sections (commodities, equity indices, single stocks, currencies, and interest rates).
- **Continuous Watchlist Pairs ($P$):** Evaluated across $P \in [5, 15, 30]$ candidate spread pairs. Each pair comprises two legs, representing $L = 2P \in [10, 30, 60]$ underlying individual contracts (before leg deduplication).
- **Trading Calendar ($D$):** Modeled at $D = 250$ to $252$ statutory trading days per calendar year.
- **Trading Session Duration ($S$):** The statutory MOEX derivatives trading window spans from **09:00 to 23:50 MSK** (14.83 trading hours), punctuated by two clearing breaks (14:00–14:05 and 18:50–19:05 MSK). For mathematical dimensioning, we model active sessions of 10 hours (baseline daytime) and 14 hours (full morning + evening session).
- **Intraday Sampling Frequencies ($q$):**
  - *Hourly Snapshots:* $q \in [10, 14]$ snapshots per trading day.
  - *15-Minute Snapshots:* $q \in [40, 56]$ snapshots per trading day (up to 96 snapshots if modeled 24/7).
- **Retention Horizons ($H$):** Retention requirements evaluated at $H \in [1, 3, 5, 10]$ years.

### 3.2 Mathematical Sizing Model: Formulation of Ingestion, Storage, and Compute

#### 1. Daily Ingestion Volume & Network Transfer
The daily network payload $V_{\text{net}}$ and HTTP request count $R_{\text{day}}$ are governed by:
$$R_{\text{day}} = \left\lceil \frac{N}{C_{\text{eod}}} \right\rceil + \sum_{k=1}^{L} \left( q \cdot \left\lceil \frac{B_{\text{bars}}}{C_{\text{candle}}} \right\rceil \right)$$
$$V_{\text{net}} = \left( N \cdot S_{\text{eod\_raw}} \right) + \left( L \cdot q \cdot S_{\text{bar\_raw}} \right)$$

Where:
- $C_{\text{eod}}, C_{\text{candle}}$: Batch pagination limits (MOEX ISS caps records at 1,000 records per request (1 000 rows per call in official docs, client libraries default to 100); client-safe chunks default to 100).
- $S_{\text{eod\_raw}}$: Raw JSON payload per contract EOD summary ($\approx 1.5\text{ KB}$ uncompressed, $0.3\text{ KB}$ gzipped).
- $S_{\text{bar\_raw}}$: Raw JSON payload per candle record ($\approx 1.2\text{ KB}$ uncompressed, $0.25\text{ KB}$ gzipped).
- $B_{\text{bars}}$: Intraday bars fetched per sampling event ($1$ bar for snapshot; multiple bars during backfill).

#### 2. Cumulative Storage Volume Modeling
Storage growth is divided into two distinct tiers:
1. **Raw Snapshot Staging Store ($V_{\text{raw}}$):** Unmodified JSON responses stored for data lineage and point-in-time auditability.
   $$V_{\text{raw}}(H) = D \cdot H \cdot V_{\text{net}}$$
2. **Normalized SQLite Relational Store ($V_{\text{sqlite}}$):** Structured B-Tree storage storing parsed OHLCV, Open Interest, Settlement, and Timestamp values.
   $$V_{\text{sqlite}}(H) = \left[ (N \cdot D \cdot H) + (L \cdot q \cdot D \cdot H) \right] \cdot \left( S_{\text{row}} + S_{\text{index}} \right) \cdot (1 + \Omega_{\text{wal}})$$

Where:
- $S_{\text{row}} \approx 80\text{ bytes}$ (integer timestamp, 8-byte float prices, 8-byte volume/OI, contract text key).
- $S_{\text{index}} \approx 30\text{ bytes}$ (B-Tree index leaf overhead for `(ticker, timestamp)` composite primary key).
- $\Omega_{\text{wal}} \approx 0.25\text{ to } 0.50$ (write-ahead log checkpoint expansion factor).

#### 3. Memory Footprint Modeling (Resident Set Size, RSS)
$$\text{RSS}_{\text{total}} = \text{RSS}_{\text{runtime}} + \text{RSS}_{\text{cache}} + \text{RSS}_{\text{parse\_buffer}} + \text{RSS}_{\text{outbox}}$$
- $\text{RSS}_{\text{runtime}}$: Python 3.12 interpreter base footprint ($\approx 28–35\text{ MB}$) vs. Go/Rust binary ($\approx 6–12\text{ MB}$).
- $\text{RSS}_{\text{cache}}$: SQLite page cache bounded by `PRAGMA cache_size = -2000` ($\approx 2.05\text{ MB}$) up to `-8000` ($\approx 8.19\text{ MB}$).
- $\text{RSS}_{\text{parse\_buffer}}$: Streaming JSON chunk buffer ($\le 5\text{ MB}$ with streaming iterators; spikes to $150–500\text{ MB}$ if Pandas is imported).
- $\text{RSS}_{\text{outbox}}$: In-memory async alert queue ($\le 2\text{ MB}$).

### 3.4 Network Ingestion, Pacing, and HTTP Transfer Dynamics
- **Request Pacing:** To stay strictly below MOEX ISS rate-limiting thresholds (where 4–5 req/s triggers HTTP 429), the ingestion engine enforces a token-bucket rate limiter:
  - Base polling cadence: **1.5 requests per second** (inter-request delay of $\approx 650\text{ ms}$).
  - Jitter: Uniform random variance of $\pm 150\text{ ms}$ to eliminate harmonic traffic spikes.
- **Execution Wall Time:**
  - *EOD Baseline (200 contracts):* $200 \times 0.65\text{ s} \approx 130\text{ seconds}$ (~2.1 minutes).
  - *Intraday Snapshot Cycle (40 legs):* $40 \times 0.65\text{ s} \approx 26\text{ seconds}$.
  - *Duty Cycle Analysis:* In a 15-minute window (900 seconds), a 26-second ingestion run consumes **$< 2.9\%$ of wall-clock time**. For the remaining 874 seconds, the process sleeps in an asynchronous event loop, consuming zero CPU cycles and maintaining a flat steady-state RAM profile.

### 3.5 CPU & Memory Footprint Modeling (Steady vs. Peak)
- **Idle / Monitoring Steady-State:**
  - Python 3.12 daemon running standard library `asyncio` + `sqlite3` + `urllib`/`urllib3`: **38–52 MB RSS**.
  - CPU load while sleeping: **$< 0.1\%$ of 1 vCPU**.
- **Ingestion / Parse Transient Burst:**
  - Incremental chunk parsing using `json.loads()` on streaming response bodies: peak RAM increases by **+15–25 MB**, reaching a transient peak of **55–75 MB RSS**.
  - Wall-clock CPU spike during JSON parsing and SQLite insertion: **8–12% CPU for 1.2 to 2.5 seconds**.
- **Disqualification of Heavy Stacks on VPS:**
  - Importing `pandas` immediately inflates process base RSS from 35 MB to **125 MB**.
  - Executing vectorized dataframe operations (`pd.read_json()`, rolling spread calculations) creates transient intermediate object allocations that spike memory by **300–600 MB**, immediately triggering Linux kernel memory cgroup limits (`MemoryHigh=200M`, `MemoryMax=250M`) and causing kernel OOM kills.

### 3.6 Bounded Ingestion Pipeline Architecture
To ensure deterministic execution and prevent runaway process memory, the ingestion pipeline implements five structural controls:
1. **Bounded Batching:** Ingestion queries are executed in strictly bounded batches of 10 to 25 instruments, writing and committing to SQLite at each batch boundary.
2. **Streaming Serialization:** HTTP responses are streamed directly into SQLite parameter bindings without constructing large in-memory dictionary lists.
3. **Cursor Watermarking:** Ingestion state is tracked via a persistent `ingestion_watermarks` table, recording `(secid, last_timestamp, last_cursor)`. If an ingestion cycle is interrupted, it resumes from the committed watermark without backfilling duplicate rows.
4. **Data Lineage Tracking:** Every stored record is tagged with an immutable `source_lineage` string (e.g., `MOEX_ISS_20261022_1905_EOD`), enabling full point-in-time auditability.
5. **Atomic Raw Archiving:** Raw JSON payloads are compressed with `gzip` or `zstd` on the fly and written to a temporary file (`.tmp`), which is atomically renamed to `.json.gz` only after filesystem synchronization (`fsync`), preventing corrupted partial files.

### 4.2 Process Execution Models: Daemon vs. Cron
Two process supervisor patterns were evaluated for VPS task scheduling:

1. **Periodic Invocation via `systemd.timer` / Cron:**
   - *Mechanics:* Spawns a new Python process every 15 minutes to pull snapshots, update the database, and exit.
   - *Defects:* Spawns interpreter startup overhead and repeated SQLite connection initialization on every invocation. Crucially, as documented in `systemd.timer(5)`, the `Persistent=true` directive immediately executes missed jobs upon system recovery. If the VPS reboots after an extended outage, `systemd` triggers an uncontrolled avalanche of backfill jobs, overwhelming the CPU and causing race conditions on database locks.
2. **Single-Process Asynchronous Supervisor Daemon (Selected Architecture):**
   - *Mechanics:* A long-running Python daemon managed by `systemd` running an internal `asyncio` event loop.
   - *Advantages:* Maintains a warm, constant memory footprint; executes polite, jittered rate limiting natively in memory; coordinates market data polling, state reconciliation, and alert dispatch within a single non-blocking thread; and completely prevents overlapping job execution.

### 4.4 SQLite Pragmas for Low-Memory VPS Deployments
To guarantee transactional durability, prevent database corruption during host kernel panics, and cap database engine memory strictly under **4 MB**, the VPS SQLite database connection must initialize with the following configuration pragmas:

```sql
-- Enforce Write-Ahead Logging for non-blocking concurrent readers
PRAGMA journal_mode = WAL;

-- NORMAL synchronization provides complete crash resilience for WAL mode 
-- while eliminating redundant fsync() calls required by FULL
PRAGMA synchronous = NORMAL;

-- Bound page cache memory to exactly 2,000 pages (~8.19 MB of RAM)
-- Baseline 2MB (PRAGMA cache_size = -2000;), or tune to PRAGMA cache_size = -8000 (8MB) if Stage-3 confirms headroom
PRAGMA cache_size = -2000;

-- Force temporary tables and indices into RAM, avoiding unnecessary SSD wear
PRAGMA temp_store = MEMORY;

-- Block writers for up to 5,000 ms on contention before returning SQLITE_BUSY
PRAGMA busy_timeout = 5000;

-- Checkpoint the WAL file back into main DB every 1,000 pages to prevent unbounded WAL growth
PRAGMA wal_autocheckpoint = 1000;

-- Standard 4KB page size matching Linux virtual memory pages
PRAGMA page_size = 4096;

-- Disable memory-mapped I/O to maintain deterministic, predictable process RSS
PRAGMA mmap_size = 0;
```

### 4.5 Schema Migration Engine & Point-in-Time Reproducibility
- **Zero-Dependency Migration Engine:** To avoid third-party migration dependencies (such as Alembic or Flyway) that consume memory, schema evolution is governed programmatically via SQLite's built-in `PRAGMA user_version`:
  ```python
  def apply_migrations(conn):
      cursor = conn.cursor()
      cursor.execute("PRAGMA user_version;")
      current_v = cursor.fetchone()[0]
      
      if current_v < 1:
          cursor.executescript(SCHEMA_V1_DDL)
          cursor.execute("PRAGMA user_version = 1;")
      if current_v < 2:
          cursor.executescript(SCHEMA_V2_DDL)
          cursor.execute("PRAGMA user_version = 2;")
      conn.commit()
  ```
- **Point-in-Time Lineage Tracking:** Every record inserted into `market_snapshots` stores:
  - `captured_at_utc`: Exact Unix epoch milliseconds of ingestion.
  - `exchange_timestamp`: Exchange-reported bar or settlement timestamp.
  - `source_lineage`: Traceable provenance string (e.g., `MOEX_ISS_20261022_EOD_V1`).
  - `payload_sha256`: Cryptographic hash of the raw upstream JSON payload.

### 4.6 Tiered Storage, Backups & Workstation Synchronization
To ensure total disaster recovery without straining the 20 GB VPS disk:
1. **The Live Hot Tier (VPS):** The SQLite database retains a rolling **30 to 90-day window** of active market data, virtual ledger transactions, and alert outbox history. Total file size is bounded under **$150	ext{ MB}$**.
2. **Online Hot Backups (Zero Locking):** Direct filesystem copying (`cp data.db backup.db`) of an active WAL database risks copying torn pages. Backups must be executed exclusively via SQLite's native atomic snapshotting:
   ```sql
   VACUUM INTO '/opt/moex-pilot/backups/snapshot_daily.db';
   ```
   Or via the SQLite Online Backup API (`sqlite3_backup_init`), which streams consistent page snapshots while writers continue uninterrupted.
3. **The Cold Tier & Synchronization (MacBook Pro):**
   - Weekly or monthly, the MacBook Pro executes a secure, encrypted `rsync` pull over SSH:
     ```bash
     rsync -avz -e "ssh -p 22 -i ~/.ssh/moex_deploy_key"        moexbot@vps.host:/opt/moex-pilot/backups/snapshot_daily.db        ~/moex-research/data/vps_snapshots/
     ```
   - On the workstation, an ETL script ingests the SQLite snapshot, normalizes the bars, converts older data into compressed Apache Parquet format (partitioned by year and asset class), and appends it to the multi-year cold archive.

### 5.3 The Human Execution Latency Gap: Alert vs. Action vs. Market Fill

- **Operational Latency Profile:**
  - Operator manual reaction latency spans **3 to 90 minutes**, with a historical median of **5 to 15 minutes**.
  - In liquid futures markets, mean-reverting spread mispricings frequently have half-lives of seconds to minutes. Chasing an expired signal after 30 minutes results in severe adverse selection and execution slippage.
- **Autonomous Ledger Defenses against Human Latency:**
  1. *Signal Validity Time-to-Live (TTL):* Every spread alert embeds a strict expiration timestamp:
     $$	ext{TTL}_{	ext{signal}} = T_{	ext{alert}} + 15	ext{ minutes}$$
  2. *Slippage Limit Tolerance:* Alerts define a maximum acceptable execution spread boundary ($	ext{Spread}_{	ext{max}}$). If the market moves beyond this limit before the operator enters orders, the manual order must be aborted.
  3. *Unfilled / Expired State Tracking:* The Virtual Ledger records signals that were dispatched but expired without user confirmation as `EXPIRED_UNFILLED`, maintaining realistic virtual performance accounting.

### 5.4 Alert Prioritization, Isolation & Outbox Architecture
To guarantee that high-priority risk warnings and system heartbeat failures are never blocked or delayed by batch data ingestion or network rate limiting, alerts are categorized into three strictly isolated tiers:

| Alert Tier | Classification & Examples | Delivery Policy & SLA | Concurrency & Throttling |
| :--- | :--- | :--- | :--- |
| **Tier 0: CRITICAL** | Drawdown limit breach (RUB 5k/10k), margin call risk, daemon crash, disk $<2	ext{ GB}$ | Immediate dispatch; bypasses batch queue; SLA $< 3	ext{ seconds}$ | Dedicated async priority queue; retries every 5s with jitter |
| **Tier 1: OPERATIONAL**| Actionable spread entry/exit signal, stale feed alert ($>25	ext{ min}$) | Dispatched sequentially; polite pacing; SLA $< 30	ext{ seconds}$ | Main outbox queue; rate-limited to 1 msg/s per chat |
| **Tier 2: TELEMETRY** | Daily EOD performance summary, LQDT matched counterfactual, hourly heartbeat | Low priority; batched and scheduled post-clearing | Suppressed automatically during network degradation |

#### The Risk Alert Isolation Rule:
The background monitoring architecture enforces a strict threading rule: **Risk monitoring and outage alerts must run on an isolated asynchronous event branch.** If a heavy network fetch to MOEX ISS encounters a 30-second socket timeout, the risk watchdog loop continues running on independent timers, ensuring margin alerts and heartbeat pings are never starved of execution time.

### 5.5 Delivery Reliability, Deduplication, Retry Backoff & State Persistence
- **Transactional Outbox Engine (SQLite):**
  Alerts are never dispatched via raw "fire-and-forget" HTTP calls inside business logic. Instead, alerts are written transactionally to an embedded SQLite `telegram_outbox` table within the same transaction that updates the virtual ledger.
- **Idempotency & Deduplication:**
  - Every alert record generates a deterministic `idempotency_key`:
    $$	ext{idempotency\_key} = 	ext{SHA256}(	ext{signal\_id} + 	ext{ticker\_pair} + 	ext{action} + 	ext{bar\_timestamp})$$
  - The outbox table enforces a `UNIQUE(idempotency_key)` constraint. If the supervisor daemon crashes and restarts, re-evaluating the current bar will attempt to insert an existing key, which is safely ignored (`INSERT OR IGNORE`), completely preventing duplicate spam notifications to the operator.
- **Retry Mechanics & Backoff:**
  - The dedicated outbox worker processes pending messages asynchronously.
  - If Telegram returns HTTP 429: Worker extracts `parameters.retry_after`, pauses the queue for `retry_after + rand(0.5, 1.5)` seconds, and reschedules delivery.
  - If Telegram returns HTTP 5xx or network timeout: Implements exponential backoff:
    $$\Delta t_{	ext{retry}} = \min(300, 2^{	ext{attempt}} 	imes 1.5) + 	ext{jitter}$$
  - Max retries: Capped at 5 attempts before marking the message as `FAILED_DEADLETTER` (dead-letter queue / deadletter handling) and escalating to the backup log.

### 5.6 Independent Outage Detection & Heartbeat Mechanism
- **The Inbound Limitation:** Telegram Bot API retains uncollected incoming updates for at most **24 hours**. Inbound long-polling (`getUpdates`) is used exclusively for operator commands (e.g., `/status`, `/ack`, `/stop`), never as a permanent audit log.
- **The Silent Failure Trap:** If the VPS suffers a total kernel crash, VPS provider network partition, or power outage, the VPS daemon cannot send an alert explaining that it is dead.
- **External Heartbeat (Dead-Man's Switch):**
  - The VPS supervisor daemon emits a periodic cryptographic HTTP GET ping every 30 minutes to an independent external monitoring service (e.g., a free Healthchecks.io endpoint or a lightweight cron job running on the user's MacBook Pro).
  - If the external monitor fails to receive a ping within **45 minutes**, the external monitor triggers an independent alert to the operator (via email or direct SMS/secondary Telegram service), exposing silent VPS failure.

### 6.4 Swap Pressure, Memory Thrashing & OOM Self-Throttling
- **The Threat of Swap Thrashing:** While the VPS has 2 GB of swap, continuous swapping on a shared cloud hypervisor degrades disk I/O, increases CPU wait (`%iowait`), and can freeze the network stack, dropping active VPN tunnels.
- **Kernel Pressure Stall Information (PSI):**
  The daemon samples `/proc/pressure/memory` every 60 seconds:
  ```
  some avg10=0.00 avg60=0.00 avg300=0.00 total=0
  full avg10=0.00 avg60=0.00 avg300=0.00 total=0
  ```
  If `some avg60` exceeds **$10.0$** (indicating processes are stalled on memory allocations $>10\%$ of the time), or if `/proc/meminfo` reports `MemAvailable < 150 MB`, the daemon initiates **Voluntary Self-Throttling**:
  1. Purges in-memory caches and invokes Python garbage collection (`gc.collect()`).
  2. Reduces watchlist polling frequency from 15 minutes to 60 minutes.
  3. If memory pressure persists for 15 minutes, exits cleanly with exit code `0`, allowing systemd to cool down without triggering an OOM panic.

### 6.5 Disk Space Exhaustion & Inode Management
- **The 2.0 GB Hard Disk Guard:**
  The daemon continuously monitors root filesystem free space (`statvfs('/')`). If available disk space drops below **$2.0\text{ GB}$**, the daemon trips an emergency circuit breaker:
  1. Halts all data ingestion and disables raw JSON caching.
  2. Triggers SQLite `PRAGMA wal_checkpoint(TRUNCATE)` to compress WAL logs.
  3. Purges uncompressed staging files older than 7 days.
  4. Dispatches a high-priority Tier-0 Telegram emergency alert to the operator.
- **System Log Capping (`journald.conf`):**
  Systemd system logs can silently consume gigabytes of storage if left unmanaged. Deployment prerequisites mandate configuring `/etc/systemd/journald.conf`:
  ```ini
  [Journal]
  SystemMaxUse=100M
  SystemKeepFree=2G
  MaxRetentionSec=1month
  ```

### 6.6 Upstream Market Data Failure & Circuit Breakers
- **Failure Profile:** MOEX ISS frequently returns HTTP 500/502/503 during exchange maintenance, HTTP 429 when polling too rapidly, or connection timeouts during network routing anomalies.
- **Circuit Breaker Pattern:**
  - Consecutive failures are tracked per endpoint.
  - Failures 1–3: Exponential backoff with jitter ($1\text{s}, 2\text{s}, 4\text{s}$).
  - Failure 5: Circuit breaker opens for **10 minutes**. Ingestion transitions to `DEGRADED`.
  - Alert Dispatch: Operator alerted only if the outage exceeds **30 continuous minutes** during statutory trading sessions.

### 6.7 System Clock Drift & Monotonic Synchronization
- **Risk:** Time-series spread calculations rely on chronological ordering of bars. Clock drift between the VPS and exchange servers invalidates tick comparisons and corrupts signal timing.
- **Mitigation:**
  - Host clock must synchronize via `systemd-timesyncd` or `chrony` against stratum-1 NTP servers.
  - The daemon compares exchange-reported HTTP header `Date` timestamps against local system time. If clock drift exceeds **$2.0\text{ seconds}$**, the daemon logs a critical warning and invalidates chronological spread evaluation until time synchronization is re-established.
  - Internal timers use `time.monotonic()`, completely shielding the scheduler from NTP step adjustments.

### 6.8 Concurrency Protection & Single-Instance Locks
To completely eliminate race conditions caused by manual command execution or rogue processes, the daemon enforces a non-blocking POSIX file advisory lock on `/var/run/moex-pilot/instance.lock` using `fcntl.flock(LOCK_EX | LOCK_NB)` upon startup. If another instance is running, the new process exits immediately with an error log.

### 6.9 Database Corruption Recovery & Replay Safety
- **Startup Integrity Audit:** Upon every startup, the daemon executes:
  ```sql
  PRAGMA quick_check;
  PRAGMA integrity_check;
  ```
  If any corruption is detected, the daemon does not attempt naive repair. It renames `data.db` to `data_corrupt_[timestamp].db`, restores the most recent verified snapshot (`snapshot_daily.db`), and queries the persistent `ingestion_watermarks` table to replay missing bars from upstream MOEX ISS.
- **Replay Safety & Execution Protection:** During database replay or backfill, **all order execution triggers and Telegram alert dispatches are strictly disabled**. Replay operations run in non-executing calculation mode, preventing duplicate alerts or phantom orders.

### 6.10 Recovery Objectives (RTO / RPO) & Account Safety Ledger
To provide formal operational boundaries, disaster recovery is dimensioned under explicit recovery targets:
- **Recovery Point Objective (RPO):**
  - *Daily EOD Baseline:* $\text{RPO} \le 24\text{ hours}$ (Recoverable at zero loss from MOEX ISS history archives).
  - *Intraday Snapshots:* $\text{RPO} \le 15\text{ minutes}$ (Bounded by the most recent sampling interval).
  - *Virtual Ledger & Outbox State:* $\text{RPO} = 0$ (Zero transactional loss; committed via synchronous WAL).
- **Recovery Time Objective (RTO):**
  - *Process Crash Restart:* $\text{RTO} \le 10\text{ seconds}$ (Automated via systemd).
  - *Database Snapshot Restore:* $\text{RTO} \le 5\text{ minutes}$ (Automated restoration from `snapshot_daily.db` followed by gap replay).
  - *Critical Outage Escalation:* $\text{RTO} \le 15\text{ minutes}$ to alert operator if recovery fails.
- **Account-Safety Information Preserved Across Failures:**
  The virtual ledger preserves four critical account-safety state variables that must never be zeroed on restart:
  1. *Cash Allocation & Gross Contributed Funding:* Tracking against the RUB 30k pilot cap and RUB 45k lifetime cap.
  2. *Excess Performance Curve & High-Water Mark:* Cumulative $X(t)$ and $X_{\text{HWM}}$ to enforce the RUB 10k action halt.
  3. *Active Spread Positions & Lot Quantities:* Ensuring theoretical exposure is never double-counted or lost.
  4. *Idempotent Alert Outbox Keys:* Preventing duplicate execution notifications after system reboot.

# 7. Capital Governance, Risk Limits & Matched LQDT Counterfactual

### 7.1 Capital Structure & Account Context: The Co-Location Dilemma
The private MOEX futures-spread project operates within an asymmetric capital structure:
- **Pilot Allocation:** **RUB 30,000**, encompassing initial margin, variation-margin liquidity reserves, and operational buffers.
- **Core Capital Holding:** In excess of **RUB 40,000,000** invested in the **LQDT money-market fund** (the primary Russian rouble cash-management ETF tracking the RUSFAR benchmark rate).
- **The Co-Location Reality:** Crucially, the RUB 30,000 pilot and the RUB >40,000,000 LQDT holding **coexist on the exact same single brokerage account at VTB**.
- **The Ring-Fencing Illusion:**
  - In the software architecture, the virtual ledger maintains an internal virtual sub-budget that tracks the RUB 30,000 independently.
  - **However, the broker recognizes only the unified legal account.** At the broker level, there is no legal ring-fencing. If a futures position suffers catastrophic adverse variation margin or a rogue limit order executes, the broker will automatically debit available rouble cash, demand immediate margin calls, and ultimately initiate **broker-enforced forced liquidation of core LQDT shares** to restore account coverage.
  - **Core Capital Imperative:** Core collateral must *never* be silently treated as pilot funds. Any broker-driven liquidation of core LQDT constitutes an immediate Category-1 operational emergency.

### 7.2 Investor Status, KPUR Recognition & Broker Collateral Rules
- **Qualified Investor & KPUR Status:** The user is a certified qualified investor (*Квалифицированный инвестор*) and reports **KPUR status** (*Клиент с повышенным уровнем риска* — Client with Increased Risk Level under Bank of Russia regulations).
- **Operational Reality & Hazards:**
  - *Unverified Recognition:* Broker-specific recognition of KPUR status at VTB and BCS, along with specific discounting rules for LQDT as margin collateral, remains **unverified** in this stage.
  - *Leverage Amplification:* While KPUR status reduces initial margin requirements and permits higher portfolio leverage, it dramatically narrows the margin-call buffer. A small adverse spread divergence can trigger forced liquidation faster than for standard-risk clients (KSOUR).
  - *Collateral Haircuts:* Under MOEX and broker risk models, ETF shares such as LQDT are subject to risk haircuts (typically 10% to 25%). If the broker discounts LQDT collateral during market volatility, account initial margin coverage can collapse independently of spread P&L.

### 7.3 Matched LQDT Counterfactual Accounting Framework
Every analytical evaluation, performance metric, and drawdown calculation must be benchmarked against a **Matched LQDT Counterfactual Portfolio** ($P_{\text{bench}}$) that mirrors the exact timing and magnitude of external cash flows:

$$X(t) = \text{PnL}_{\text{pilot}}(t) - \text{Return}_{\text{counterfactual}}(t)$$

#### Core Accounting Laws:

2. **Diverted Core Stays Invested in Counterfactual:** The RUB 30,000 diverted from core wealth to fund the pilot is assumed to have remained 100% invested in LQDT in the counterfactual benchmark.
3. **No Double-Deduction of Collateral Yield:** If broker rules permit core LQDT shares to serve as margin collateral for futures without liquidating them, the ongoing yield generated by that collateral belongs to the account and must *not* be deducted twice from the spread performance.
4. **Exclusion of Long-Term Tax Deduction (LDV):** The potential loss of the 3-year Long-Term Holding Tax Deduction (*Льгота на долгосрочное владение — ЛДВ*) resulting from unintended LQDT liquidation is excluded from the automated ledger due to unknown tax residency and account tenure, but must be factored into manual risk audits.
5. **Liquidation Proceeds Distinction:** Broker sale proceeds from core collateral do not automatically equal economic loss in spread result $X$, but represent involuntary portfolio de-risking.

### 7.5 Emergency Allocation Governance (RUB 15,000 Gross Cap)
- **Cumulative Lifetime Gross Cap:** An emergency liquidity injection is capped at a strict lifetime cumulative maximum of **RUB 15,000 GROSS**, bringing total potential cumulative gross funding to **RUB 45,000**.
- **Absolute Purpose Restriction:**
  - Emergency funding may **ONLY** be deployed to avert disorderly liquidation or cover adverse variation margin while orderly closing existing positions to **reach flat**.
  - Emergency funding is **STRICTLY PROHIBITED** from funding fresh spread exposure, increasing position size, or averaging down on an adverse divergence.
  - **Zero Emergency Allocation at Entry:** Every spread trade must satisfy all initial margin and variation margin reserves with zero emergency funding available at entry.
  - *Approval Mandate:* Every single kopeck of emergency funding requires explicit, documented human operator approval. Any broker-initiated seizure of core LQDT cash or collateral automatically counts against this RUB 15,000 allowance and is logged as a critical operational breach.

### 7.6 Human Operational Quotas & Availability
- **Operator Reaction Budget:** Manual execution assumes an operator reaction window of **3 to 90 minutes (median: ~5 to 15 minutes)**. The virtual ledger must never assume instant fills.
- **Weekly Intervention Quota:** To prevent operator cognitive fatigue, the pilot establishes a quota of **at most 2 to 4 manual spread entries per week**. Zero-trade days are fully acceptable and economically rational.

### 11.2 Minimum Security Posture: Threat Model, Secrets & Replay Safety
To maintain enterprise-grade security without commercial software overhead:

#### 1. Threat Model & Attack Vectors:
- *Vector A: VPS Compromise via Public Internet.* Mitigated by disabling SSH password authentication, enforcing ed25519 public keys, changing default SSH port if required, and running `moexbot` with strict systemd filesystem sandboxing (`ProtectSystem=strict`, `NoNewPrivileges=true`).
- *Vector B: Telegram Credential Interception.* Mitigated by storing Telegram bot tokens outside git repositories, setting file permissions to `0600`, and restricting command execution to authorized `chat_id`s.
- *Vector C: Broker Secret Leakage.* During Stages 2–5, zero broker trading credentials exist on the VPS (manual execution). In Stage 6, BCS Trade API refresh tokens are loaded via systemd encrypted credentials (`LoadCredential=`) and never written to plain log files.

#### 2. Secrets Management & Access Permissions:
- Credentials must **never** be hardcoded in Python scripts, committed to version control, or printed in application logs.
- Secrets are stored in a dedicated environment file `/opt/moex-pilot/.env` with strict permissions:
  ```bash
  sudo chown moexbot:moexbot /opt/moex-pilot/.env
  sudo chmod 600 /opt/moex-pilot/.env
  ```
- Alternatively, utilizing native systemd credential management:
  ```ini
  [Service]
  LoadCredential=telegram_token:/etc/moex-pilot/secrets/telegram.token
  LoadCredential=bcs_refresh_token:/etc/moex-pilot/secrets/bcs_refresh.token
  ```
  The daemon reads secrets dynamically from `$CREDENTIALS_DIRECTORY/telegram_token`, leaving zero traces in process memory dumps or shell environment variables.

#### 3. Replay Safety & State Restoration Governance:
When restoring a database from an offline backup or replaying historical market bars:
1. **The Replay Safety Flag:** The daemon supports an explicit `--replay-mode` CLI flag that suppresses all external side-effects:
   ```bash
   python main.py --replay-mode --from-date 2026-10-01
   ```
   In replay mode, the outbox worker and order execution seams are replaced with mock null-handlers (`NullOutboxClient`, `NullExecutionClient`), guaranteeing that zero Telegram messages or broker orders are emitted during historical state reconstruction.
2. **Idempotency Keys:** Every virtual ledger transaction and alert row enforces database-level uniqueness constraints. Re-evaluating a previously processed event results in a silent collision (`INSERT OR IGNORE`), ensuring total mathematical determinism.

### 12.3 BCS Trade API Technical Seams & Integration Points
When the project transitions to Stage 6 automated execution at BCS, the software skeleton integrates with the following documented seams:

1. **Authentication Seam (`BcsAuthEngine`):**
   - Stores the 90-day `refresh_token` in systemd encrypted credentials.
   - Executes an automated daily POST request to `https://trade-api.bcs.ru/api/v1/auth/refresh` to obtain a fresh 24-hour `access_token`.
   - Passes `Authorization: Bearer <access_token>` in all subsequent REST and WebSocket headers.
2. **Historical Bar Seam (`BcsCandleProvider`):**
   - Replaces MOEX ISS for intraday bar retrieval by calling `/api/v1/candles-chart`.
   - Respects the documented **1,440 bar pagination limit** and **10 RPS HTTP rate limit**.
3. **Execution Seam (`BcsExecutionClient`):**
   - Submits paired limit orders simultaneously across spread legs.
   - Implements automated leg-slippage protection: If Leg A executes but Leg B fails to match within **3.0 seconds**, the client immediately cancels Leg B and unwinds Leg A at market to prevent unhedged directional exposure ("legging risk").
4. **Position & Collateral Reconciliation Seam (`BcsPortfolioWatchdog`):**
   - Queries `/api/v1/client/portfolio` every 60 seconds to pull official margin utilization, cash balances, and position quantities.
   - Cross-checks official broker positions against internal virtual ledger state. If a discrepancy of $> 1\text{ lot}$ is detected, all automated order placement halts immediately.
