# Working rules
- Chat: Russian, outcome first, brief business language. Authored project files: English by default. User-requested exception: R01–R06/R12 research prompts and the user-facing sections of the research README are Russian; reports may follow their prompt language. Preserve user-supplied source documents in their original language; explicitly label redactions.
- `docs/inputs/brief.md` defines scope and stage gates. Each stage occupies at least one separate user/assistant turn and produces a committed artifact. Never combine later stages into the current one.
- Current stage: Stage 9 development. See `README.md` for status, `docs/decisions.md` for confirmed boundaries, and `docs/stages/08-planning.md` for S4 and later work.
- Workspace map and ownership (Phase 6): `packages/core` owns contracts/settings/hashing; `packages/data` owns ISS/lake/retention/benchmark; `packages/accounting` owns costs/risk/sizing/ledger/artifacts; `packages/strategies` owns isolated strategy plugins and pair/calendar datasets; `packages/proof` owns replay/search/audit; `packages/web` owns the loopback server/routes/static UI. Import dependencies flow `core -> data|accounting -> strategies -> proof -> web`; `data` and `accounting` remain siblings. Root `src/moex_spread_lab/cli.py` and `__init__.py` are public entry points; other root modules are documented backward-compatibility shims whose module docstrings name the canonical replacement.
- Default agent scope is one `packages/<name>/` subtree, including its tests/docs/fixtures/manifest. Use canonical `moex_spread_lab.<domain>` imports in all workspace package code and tests; root compatibility shims are reserved for external consumers. Cross-package contract changes start with an additive contract and conformance test, then fan out to consumers. Keep root governance files (`pyproject.toml`, `uv.lock`, workflows, `README.md`, `AGENTS.md`) minimal and coordinate cross-cutting edits.
- Adding a strategy is one new folder `packages/strategies/src/moex_spread_lab/strategies/<subpkg>/{__init__,engine,plugin}.py`; never edit `packages/strategies/pyproject.toml`, `test_architecture_dag.py` or a registry module for it (the folder is discovered, layer-classified and isolation-checked from disk), and never import a sibling strategy subfolder. Reach the strategy registry through `proof.strategy_catalog` accessors (`get_strategy_registry` / `get_proof_adapter_ids` / `get_strategy_axes`, `registry=` injection in tests) — no import-time globals, no patching module attributes.
- Package tests are collected only from `packages/{core,data,accounting,strategies,proof,web}/tests`; root `tests/` contains shared synthetic fixtures only. Run a focused suite with `uv run pytest packages/<name>/tests -q`, the dependency-light global check with `uv run python scripts/architecture_gate.py`, and the full suite with `uv run pytest -q -n auto --dist loadfile`. CI schedules dynamic xdist `loadfile` work per package; do not add a central test-duration JSON.
- **Verification cadence (plan S3, two-tier).** Within a single assistant turn, continue across internal sub-slices until the work package is complete, a genuine product/accounting/design decision is needed from the user, or the turn nears its call budget (target ~75%). Stopping after a handful of tool calls to ask for "продолжи" is a defect, not compliance. Inner-slice verification (between atomic local commits): `./scripts/verify.py --profile affected` (or `--profile quick` for very small edits). End of a coherent deliverable (before push): `./scripts/verify.py --profile full` on the exact integrated tree. A passing `affected`/`quick` result is advisory only; it is never reported as full verification. Every push goes through the full gate on the integrated tree. Browser smokes (`scripts/run_browser_smokes.py`) and C99 sanitizer runs are mandatory only when their contracts are touched, per the guardrails below.
- Code-health gate: before committing code changes, run `./scripts/check_health.sh --changed` (inner loop) or `./scripts/check_health.sh` (full gate before push); never raise ceilings in `config/code-health-baseline.json` or `.basedpyright/baseline.json`, never add `# noqa` / `# type: ignore` / broad `except Exception` without an inline justification, and always run `packages/proof/tests/test_perf_equivalence.py` (plus `scripts/run_sanitized_pytest.py` when clang/ASan is available) when touching `_fastcore.c` or its pure-Python mirrors.
- File-size budgets are tiered by archetype (TD-1, Epic #151): production `400`/`4,000` soft -> `600`/`6,000` hard; declarative registries and static catalogs `550`/`5,500` -> `800`/`8,000`; parameterized test suites `600`/`6,500` -> `900`/`9,500`; the C99 kernel `900` -> `1,350` LOC (no token budget). Tokens are estimated as `utf8_bytes * 10 // 42` (o200k_base-aligned for code). Files in the advisory band print `advisory:` lines in the `check_health` summary and never fail; only the hard ceiling fails, and it needs a genuine domain split. Never satisfy a budget by sharding a cohesive module: new `*p72*`, issue-numbered and path-encoded filenames are rejected, `<40`-LOC production modules with at most one intra-package caller warn, and package-level token growth is surfaced so a split that raises the package total is visible. Function-level cognitive complexity (`> 15`) and the acyclic import DAG stay strictly hard. The inner-loop helper `scripts/code_inspect.py check|outline` reads the same shared policy and prints the gate's `loc`/`tokens`, archetype, soft target, hard ceiling and band (`green`/`advisory`/`over-hard`); `--strict-limits` fails only over a hard ceiling or the complexity limit.
- Always set `MOEX_OFFLINE_ONLY=1` in standalone/browser harnesses so `CalendarData` never probes MOEX ISS over HTTP; never wait with `nohup <cmd> & sleep <N>` loops (use synchronous `timeout <sec> <cmd>` or native background tools); prefer structured Read/Edit/Grep tools over `Bash` `sed`/`cat <<EOF` dumps.
- Read `docs/decisions.md`, `docs/risk/pilot-policy.md` and the current stage artifact before continuing. The user clarified 10–15k means LQDT shortfall and delegated risk-default selection; numeric defaults are versioned judgment, not verified safety or authorization to fund/trade. Track unresolved groups in `docs/blockers/bNN-slug.md`; use bNN.N subitems and archive resolved groups.
- Keep durable documentation compact, agent-readable and nonduplicative. Put temporary work plans, live checklists, execution reports and dated verification evidence in the corresponding GitHub Issues/comments only; do not retain tracked Markdown/JSON copies after migration. Keep durable contracts, decisions, blockers, formal stage artifacts, reusable runbooks and research evidence in the repository. Clearly separate provided facts, dated evidence, hypotheses, proposals and approved decisions.
- Keep the repository private. Make atomic local commits for each inner slice (Conventional Commits); push once at the end of a coherent deliverable after the full gate passes on the integrated tree. Verify remote success; never claim a push that failed. Apply SemVer when software releases begin.
- Preserve the proof search and accounting contracts in `packages/proof/docs/execution-proof.md`; never infer shared capital or expanded trading authority from the offline UI.
- Workstation handoff (end of coherent deliverable only): after the full gate passes and the push to `origin/main` succeeds, fast-forward the checkout at `~/Downloads/projects/moex-spread-lab`. When bridge credentials are provided, use `moex-spread-lab remote sync` then `remote status`. Sync skips `uv sync` unless dependency inputs change or `.venv` is missing, restarts only for runtime paths, and confirms loopback health with a matching head in the same call; docs/tests/workflows/`AGENTS.md` fast-forward without restart. The launchd job is `local.moex-spread-lab.screener`. Use `remote probe` / `remote bench` for isolated diagnostics. Docs-only and test-only changes may skip workstation sync.
- Treat uploaded `AGENTS.source.md` as sanitized workstation guidance, not proof that tools or bridges exist here. Detect availability; unavailable local macOS tools are not a cloud blocker. Use available native tools when appropriate. When a workstation bridge is provided at runtime, prefer loopback HTTP APIs and CLI execution over browser automation except for UI smoke tests; never spawn orphan servers on random ports or mutate `data/analytics/research-settings.json` during benchmarks (see the workstation benchmark record [Epic #30](https://github.com/vernikr/moex-spread-lab/issues/30) and the open remaining-scope Issue [#51](https://github.com/vernikr/moex-spread-lab/issues/51)).
- GitHub connector was unsupported in this environment; direct authenticated API/git access worked. Use supported connectors where available; otherwise secure runtime credentials, never credential-bearing remote URLs.
- Broker terms, KPUR effects, collateral eligibility, margin offsets, market sessions and API/data access are unverified until evidenced by dated applicable documents. Missing safety-critical data must never become zero cost or unlimited capacity.
- All performance comparisons must address LQDT; do not assume a return guarantee, risk-free arbitrage, fixed carrying yield or that an internal allocation ring-fences the account.
- Research localization must preserve complete context, evidence requirements, dependencies and risk authority. Every prompt states search languages, maximum-breadth priority and conditional public-page retrieval priority; no claim of tested bot protection. Broader discovery does not mean harder retrieval.
- Keep benchmark-relative peaks, losses and lifetime gross top-up usage continuous across funding/reviews; no hidden resets, automatic rescue capital or unapproved access to core collateral.
- Review each turn for reusable lessons; update this file only when useful.

- For native GitHub sub-issues, ensure `.github/workflows/issue-parent-sync.yml` exists with `issues: [opened, edited]`, `permissions: issues: write`, and a job calling `vernikr/mother/.github/workflows/issue-parent-sync.yml@v1` (create the caller workflow if missing); then put `<!-- issue-parent: #N -->` on its own line in the child Issue body, or use `<!-- issue-parent: none -->` to detach (or use GraphQL `addSubIssue` directly when `gh` has `repo` scope).

## GitHub Project & Issue workflow

Full specification: [`docs/development/github-project.md`](docs/development/github-project.md). Board: [`https://github.com/orgs/vernikr/projects/2`](https://github.com/orgs/vernikr/projects/2) (`moex-spread-lab`, linked to `vernikr/moex-spread-lab`; idempotent setup/sync: `./scripts/github_project_bootstrap.sh`).

- **Source of truth:** GitHub Issues and their comments are the sole canonical home for project plans, actionable work definitions, sub-slice checklists, execution reports, dated verification/benchmark evidence, historical delivery records, checkpoints, deviations, and deferrals (open or closed). Do not retain a tracked Markdown/JSON copy of a migrated project plan or execution report. The repository owns durable engineering contracts, approved decisions (`docs/decisions.md`), cross-issue blockers (`docs/blockers/bNN-*.md`), formal stage artifacts, reusable runbooks, stable architecture references, and research evidence explicitly intended as a lasting domain record; link these durable documents to their Issues instead of duplicating live project state. Project #2 owns live operational status (`Inbox`, `Ready`, `In Progress`, `Blocked`, `Deferred`, `Done`), `Work Kind`, `Priority`, `Effort`, `Business Value` (`0–5`), and `Verification Gate`. Never create `TODO.md` or parallel master backlogs. Write all Issues and comments in English.
- **Filing Issues:** Before changing tracked files, ensure an open Issue covers the work or create one (`.github/ISSUE_TEMPLATE/{epic,work-package,bug}.yml`), add it to Project #2, apply `area:{core,data,accounting,strategies,proof,web,tooling,docs}` labels matching package ownership, and set Project fields (`Status`, `Work Kind`, `Priority`, `Effort`, `Business Value`, `Verification Gate`).
- **Hierarchy for large plans & refactors (max 2 Issue levels + body checklist):**
  1. **Level 1 — `[Epic]` Issue** (`label: epic`, `Work Kind = Epic`) for a multi-package plan or Stage-9 initiative; the Epic body/comments are the canonical plan. Link durable repository contracts/evidence as needed, but never use a tracked `docs/development/*.md` plan as a second source of truth.
  2. **Level 2 — Work Package sub-issue** (native GitHub sub-issue via `addSubIssue` or `<!-- issue-parent: #N -->`): **one coherent pushable deliverable** verified with `--profile full`. Wire ordering dependencies via native `addBlockedBy` + `blocked` label + `Status = Blocked`. Do not pre-create speculative sub-issues for gated initiatives; split oversized packages just-in-time when starting them.
  3. **Level 3 — `## Slices` task list** (`- [ ] ...`) inside the Work Package body for atomic inner commits (`--profile affected` / `quick`) executed continuously in one session.
- **Tracking intermediate progress:** Move `Status` to `In Progress` when claiming an unblocked `Ready` item; reference `#N` in commits. Do not comment per inner commit. If a Work Package spans sessions (budget limit or mid-flight blocker after a green prefix), update `## Slices` checkboxes and leave one `**Checkpoint (<sha>, YYYY-MM-DD):** Done / Remaining / Next step` comment. Put detailed parity/bench measurements in the Issue body or a clearly titled Issue comment; never create a repository evidence file for temporary execution output. Close as `completed` (`Status = Done`) only after all acceptance criteria and the Issue's `Verification Gate` pass on `origin/main`, then unblock any `blocking` dependents (`blocked` -> `Ready`).
- **Deviations, partial completion, and deferrals:**
  - *Minor implementation deviation* (invariants & goal intact): proceed autonomously, add label `plan-deviation`, post `**Deviation from plan:** <change> / **Why:** <constraint> / **Invariant check:** ...`, and update the canonical Issue body/comment. Amend only affected durable repository documentation; do not recreate a project-plan file.
  - *Scope / contract / invariant conflict* (needs owner trade-off or touches `G1`–`G12` / `run_id` / LQDT rules): stop on the conflicting part, add `blocked` + `decision`, set `Status = Blocked`, and post `**Blocked by:** owner decision` with measured options and a recommended default.
  - *Partial completion when full execution is unreasonable now*: never close as `completed` with skipped criteria and never weaken ceilings. Narrow the current Issue to the green delivered prefix (`plan-deviation`), push and close it, and split the remainder into a new sibling sub-issue under the same `[Epic]`.
  - *Deferring vs retiring*: if postponed until a trigger holds, keep the Issue open with label `deferred`, `Status = Deferred` (hidden from active `Queue`), and a `**Deferred:** <reason> / **Revisit when:** <trigger>` comment; if permanently invalidated by measurements or owner decision, post the evidence and close as `not_planned` (`Status = Done`).

## Multi-step task autonomy template (plan S3)

When starting a multi-slice work package, internalize this operating rule:

1. **Decompose before coding.** List the planned atomic sub-slices, their expected scope (which packages/files), and the verification profile each one will use. Identify any decisions that genuinely require user input (product choice, numerical default, trade-off between two valid designs) versus decisions you can make from existing code/docs.
2. **Execute sub-slices continuously.** For each sub-slice: read relevant files → make changes → run `./scripts/verify.py --profile affected` (or `--profile quick` for trivial/docs edits) → atomic local commit. Continue to the next sub-slice without asking for "продолжи". Stop only when: (a) the deliverable is complete and the full gate passes; (b) a genuine decision point is reached that existing docs do not resolve; (c) tool failures block progress; (d) you approach ~75% of the available tool-call budget.
3. **Full integrated gate before push.** After the last sub-slice commit, run `./scripts/verify.py --profile full` on the integrated tree. If it fails, fix and re-run until green. Only then push once to `origin/main` and (if required by the change) sync the workstation.
4. **Fail-to-full switch.** If the change-scope router errors out, or if non-`.py` inputs/fixtures/new files changed, run the full gate rather than relying on testmon deselection. Never report an affected/advisory run as full verification.
5. **Shadow mode for router changes.** When modifying `scripts/change_scope*.py` or the testmon integration, validate with `./scripts/shadow_runner.py --injections` and a `--commit` range replay before promoting the change. The acceptance target is zero missed failures across >=30 candidates plus all four injection categories.
6. **Turn-end report.** When stopping (whether from completion, decision needed, or budget), state: what was committed locally, what was pushed (if anything), which sub-slices remain, and the exact decision or next step needed.
