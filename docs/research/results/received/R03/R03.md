## 1. Вопрос и краткий ответ

**Вопрос:** что действующий BCS Trade API действительно позволяет для будущей автоматической торговли фьючерсными спредами MOEX.

**Ответ.** BCS Trade API («БКС Торговое API») — официальный брокерский REST + WebSocket интерфейс «БКС Мир инвестиций» для программной торговли на Московской бирже, включая срочный рынок: документированы создание/изменение/отмена одиночных заявок, чтение справочника, котировок, стакана, свечей, обезличенных сделок, портфеля, лимитов, ГО и вариационной маржи, поиск собственных заявок и сделок [S01, S02, S05–S13]. Продукт прямо позиционируется для роботов: «Создавайте роботов и подключайте через API для непрерывного трейдинга без вашего непосредственного участия» [S02]. Это **достаточное основание для будущего исследовательского подключения только на чтение** и для проектирования автоматизации на одиночных заявках.

**Подтверждения безопасной автономной торговли произвольными двухногими спредами нет.** Главные причины:

1. В схеме создания заявки один `ticker` и один `classCode`; документированной операции «все ноги либо ни одной» не найдено. Поле `spread` — «Защитный спред. Используется для условных заявок» [S09], не атомарная фьючерсная пара. Доступность биржевых календарных спредов MOEX (они существуют как отдельные инструменты) через BCS Trade API не подтверждена.
2. Асинхронный HTTP-ответ подтверждает приём запроса, не исполнение [S10]; при потере ответа исход неизвестен, повторная отправка вслепую запрещена логикой безопасности.
3. Изменение заявки описано как «отмена исходной заявки и создание новой» [S11] — это не гарантия атомарной замены без гонок.
4. Поиск собственных заявок и сделок ограничен 1000 последними записями и не ранее 26.01.2026 [S13]; это не полный архив.
5. Гарантии replay/sequence для WebSocket-потоков не найдены; после разрыва нужна HTTP-сверка [S06, S12, S15].
6. Sandbox/тестового счёта для API в исследованной документации нет; подтверждённого отсутствия тоже не доказано.
7. Персональная цена, права счёта, признание КПУР именно в БКС, допустимость LQDT в обеспечении, сетевой доступ из фактического места работы не подтверждены.
8. На общем счёте с основным портфелем свыше 40 млн ₽ в LQDT API-токен не создаёт финансовой изоляции тестовых 30 000 ₽.

**Решение для проекта (по итогам всех отчётов):** продолжать публичное исследование и подготовку read-only проверок (раздел 11); торговый режим оставить запрещённым до выполнения условий раздела 12. Это вывод о достаточности доказательств, не оценка прибыльности стратегии.

## 2. Продукт, версия, архитектура и пределы проверки

**Продукт.** «БКС Trade API / БКС Торговое API» брокера «БКС Мир инвестиций»: лендинг [S02], документация `https://trade-api.bcs.ru/` («Быстрый старт» и технический справочник), PDF «Инструкция по использованию API БКС» [S19]. Это **не** MOEX ISS, не QUIK/QPILE/Lua, не FIX/DMA/Plaza II/TWIME, не банковский eFX и не сторонняя обёртка (`bcs-trade-go`, `bcs-trade-php` и т.п. потребляют API, но не доказывают поведение сервера) [S20].

**Архитектура.** REST (HTTPS) для синхронных операций и WebSocket (WSS) для потоков; бэкенд разбит на специализированные микросервисы (BFF-паттерн), базовые домены `be.broker.ru` и `ws.broker.ru`. Документированные HTTP-адреса (сверены с публичными схемами сайта; одинаковый `/api/v1/…` не означает один базовый сервис):

| Базовый адрес | Методы/пути |
|---|---|
| `https://be.broker.ru/trade-api-information-service` | GET `/api/v1/instruments/by-type`; POST `/api/v1/instruments/by-tickers`, `/api/v1/instruments/by-isins`; GET `/api/v1/trading-schedule/daily-schedule`, `/api/v1/trading-schedule/status` |
| `https://be.broker.ru/trade-api-market-data-connector` | GET `/api/v1/candles-chart`, `/api/v1/order-book`; POST `/api/v1/quotes`, `/api/v1/last-trades` |
| `https://be.broker.ru/trade-api-bff-limit` | GET `/api/v1/limits` |
| `https://be.broker.ru/trade-api-bff-portfolio` | GET `/api/v1/portfolio` |
| `https://be.broker.ru/trade-api-bff-operations` | POST `/api/v1/orders`, `/api/v1/orders/sync`, `/api/v1/orders/cancel`, `/api/v1/orders/cancel/sync`, `/api/v1/orders/edit`, `/api/v1/orders/edit/sync`; GET `/api/v1/orders` |
| `https://be.broker.ru/trade-api-bff-order-details` | POST `/api/v1/orders/search` |

Ключевые документированные WS-адреса: состояния заявок `wss://ws.broker.ru/trade-api-bff-operations/api/v1/orders/events/ws`; маржинальные показатели `wss://ws.broker.ru/trade-api-bff-marginal-indicators/api/v1/marginal-indicators/ws`; лимиты `wss://ws.broker.ru/trade-api-bff-limit/api/v1/limits/ws`; портфель `wss://ws.broker.ru/trade-api-bff-portfolio/api/v1/portfolio/ws`; рыночные подписки — в разделах S06. POST у поисковых методов (`orders/search`, `trades/search`) является чтением: разрешение определяется назначением метода, а не HTTP-глаголом. Старые WS-пути (`/orders/transaction/ws`, `/orders/execution/ws`) из PDF **не приравнивать** к актуальному `/orders/events/ws`; маршруты PDF сверять с действующей документацией и поддержкой [S19; расхождение зафиксировано в `ex`].

**Версия.** Единой опубликованной версии релиза всего продукта с датой вступления в силу не установлено; у многих путей есть `/api/v1/`, но это версия маршрута, а не подтверждённый номер релиза. Документация помечена `current`. Зафиксирован наблюдаемый публичный срез на даты наблюдения; он не доказывает историческую доступность возможностей. В каталоге есть устаревшие методы: старый GET `/api/v1/orders/{originalClientOrderId}` помечен к удалению **31.01.2027**, действующий — GET `/api/v1/orders` с параметрами идентификатора [S17]; старые примеры без проверки не переносить. Найденный в sitemap URL `https://trade-api.bcs.ru/blog` вернул 404 — рабочего публичного changelog не обнаружено [S18].

**Даты.** Наблюдение страниц 15.10.2026 и 21.10.2026 — не свидетельство доступности ранее. У методов списка заявок и сделок указано «начиная с 26.01.2026» — это не дата запуска всего API и не срок хранения всех данных [S13]. БКС 29.01.2026 сообщал об увеличении лимита с пяти до десяти транзакций/с и появлении списков заявок/сделок [S21]; нормативные текущие величины проверять по [S04].

## 3. Доступ клиента, права, цена, квалификация, география, допустимость автоматизации

**Требование и шаги подключения (без секретов и изменений счёта).** Нужен хотя бы один брокерский счёт БКС. Порядок: веб-версия «БКС Мир инвестиций» → «Профиль» → «Счета и тарифы» / «О счёте» → нужный счёт → «Токены API» → выпустить токен режима «Для торговли и чтения данных» либо «Только для чтения» [S01]. Каждый токен привязан только к одному брокерскому счёту; число действующих токенов не ограничено; секрет показывается один раз; выпуск бесплатный [S01]. Подключение описано как самостоятельная настройка существующего счёта; автоматического изменения тарифного плана или маржинального режима документация не описывает.

**Квалификация и категории риска.** Лендинг прямо исключает клиентов с уровнем риска **КНУР**: «Сервис доступен всем клиентам, за исключением тех, чей риск соответствует уровню КНУР» [S02] — то есть как минимум КСУР/КПУР допущены, а заявленный пользователем КПУР вписывается в допустимое множество. Это **не подтверждает** персонально признание КПУР/квалификации именно в БКС (статус не переносится автоматически от другого брокера) и не доказывает права на конкретные фьючерсы. FAQ БКС: «Статус КПУР … распространяется на все его брокерские счета» после присвоения БКС; заявление клиента не заменяет проверку и не снимает требований ГО [S22]. В справочнике есть поля `isQualifiedOnly`, `availableForUnqualified`, `qualifiedTestId` — они не заменяют разрешение брокера на конкретную операцию [S05]. Отдельная страница DMA/«Торговый API» говорит «Расширенный доступ с квалификацией» — квалификация может требоваться для части инструментов/функций, но не для самого канала API [S23]. Требования КПУР именно для доступа к API как таковому в документации не найдено; для фьючерсов MOEX ограничение по КПУР не указано — для конкретного счёта это неизвестность.

**Цена и тариф.** «Токен выпускается бесплатно» [S01]; «Комиссия взимается согласно действующему тарифу»; на продуктовой странице наблюдалась сноска «С мая 2026 года будет действовать отдельный тариф для полной версии API» [S2, S19 при наблюдении 21.10.2026]; лендинг рекламирует бонус ранним пользователям: «Торгуйте через программный интерфейс с повышенными лимитами без дополнительной комиссии» [S02]. При наблюдении 15.10.2026 сноска о мае 2026 в тексте страницы не воспроизводилась (расхождение поискового индекса и наблюдаемой страницы) — **доказательством действующего тарифа это не является**. Изученный тарифный PDF БКС [S24] не дал идентифицируемой ставки «Trade API» (его раздел 17 посвящён TSLab). Фактическое введение отдельного тарифа, сумма и принадлежность счёта к ранним пользователям **не установлены**. Вывод для сметы: цена неизвестна, нулевую стоимость не закладывать; бесплатный токен ≠ бесплатная история стакана/реальное время без условий ≠ нулевые биржевые и брокерские комиссии.

**География и сеть.** Официальных заявлений о географических ограничениях, IP-allowlist или обязательных сетевых настройках именно для BCS Trade API не найдено; отсутствие упоминаний не доказывает отсутствие правил. Для веб-сервисов БКС рекомендуют российские сертификаты/Яндекс.Браузер (вопрос TLS, не гео-блокировки). Доступность торговых шлюзов из Польши, с зарубежного VPN и будущего VPS **неизвестна**; упоминания сторонних сервисов о гео-ограничениях на BCS Trade API не переносятся. Успешное чтение публичной документации не доказывает доступность боевых endpoints из фактического места работы.

**Допустимость автоматизации.** Автоматизация — заявленное назначение продукта [S02]; прямых запретов алгоритмической торговли в публичных условиях не найдено, но полноценные условия обслуживания API в открытом доступе не обнаружены: отсутствие запрета ≠ явное разрешение. FAQ возлагает ответственность за логику робота на разработчика, требует «механизмы переподключения и проверки состояния поданных поручений при восстановлении связи» и называет операции, инициированные через API, юридически действительными: «Все операции, инициированные через API, являются юридически действительными» [S02]. Это публичное описание, не проведённая юридическая экспертиза договора.

**Связь со счётом и контекст теста.** API авторизуется в отношении конкретного выбранного счёта; брокерский бэк-энд проверяет ГО и маржинальные требования по профилю риска клиента. Внутренний тестовый бюджет 30 000 ₽ (включая ГО, ликвидность под ВМ и резервы) на том же счёте, где основной портфель >40 млн ₽ в LQDT, **не обособляется средствами API**: ни поля лимитов, ни дисконт LQDT не гарантируют неприкосновенность основного портфеля; право брокера на закрытие/реализацию обеспечения определяется договором и риск-правилами, а не описанием поля. Любое несогласованное использование брокером основного портфеля — инцидент по правилам проекта (раздел 15).

## 4. Авторизация, токены, сессии, отзыв, хранение секретов

**Схема.** OAuth 2.0 поверх Keycloak. Refresh-токен выпускается вручную в кабинете на один счёт; показывается один раз; действует **90 суток**; одновременно действующих токенов на счёте может быть несколько (число по памятке не ограничено). Access-токен запрашивается программно: POST `https://be.broker.ru/trade-api-keycloak/realms/tradeapi/protocol/openid-connect/token` с `grant_type=refresh_token`, `refresh_token`, `client_id` = `trade-api-read` либо `trade-api-write`; в ответе `access_token`, `expires_in`, `refresh_expires_in`, `refresh_token`, `token_type`, `session_state`, `scope` [S01, S03]. Access-токен живёт **24 часа**, передаётся как `Authorization: Bearer …` в REST и при инициализации WS. WebSocket-документация требует этот заголовок при соединении.

**Права (scopes).** `trade-api-read` — «Только для чтения»: рыночные данные, справочники, портфель, лимиты, история; выставление/отмена/замена заявок блокируются сервером. `trade-api-write` — «Для торговли и чтения данных»: создание рыночных и лимитных заявок MOEX, отмена/изменение, балансовые сервисы [S01]. Данные отделены от права выставлять заявки: read-only токен подходит для исследовательского подключения.

**Отзыв (существенное противоречие источников).** Быстрый старт сначала обобщённо говорит об аннулировании access при удалении refresh, затем уточняет: read-only access продолжает работать до истечения срока, максимум 24 часа, а торговый access «удаляется мгновенно» [S01]. PDF говорит о снятии торгового access «в течение нескольких минут» [S19]. **Безопасно не считать отзыв мгновенным ни для одного режима**; точные гарантии распространения отзыва по HTTP и уже открытым WebSocket запросить у поддержки. Отзыв токена **не равен** отмене принятых заявок или закрытию позиций — такой гарантии не найдено.

**Ротация и параллельные сессии.** Наличие нового `refresh_token` в ответе есть, но не описаны: одноразовость старого refresh, sliding expiration, параллельное обновление несколькими процессами, автоматическое продление на новые 90 суток. Ограничений на число одновременных HTTP/WS-сессий на токен в документации не найдено (неизвестность); неограниченное число токенов ≠ неограниченное число WS-соединений (лимиты — раздел 5). Правила одновременных сессий и блокировок требуют подтверждения.

**Минимальная политика секретов для будущего адаптера.** Отдельный read-only токен для наблюдения и торговый — только после допуска; секреты не попадают в отчёт, код, URL, Telegram и журналы; заголовки авторизации вычищаются из логов; хранение — изолированное защищённое хранилище/переменные окружения (требование отдельного от API); обновление токенов координируется одним компонентом; истечение refresh отслеживается заранее с календарным напоминанием; при неожиданной 401 — запрет новых входов, восстановление авторизации, затем сверка.

## 5. Лимиты запросов, подписок, пагинация, история, хранение

**HTTP** (по [S04]; лимиты заданы «для каждого счета клиента», не как независимая квота каждого токена):

| Сервис/категория | Лимит |
|---|---|
| Портфель, лимиты, справочник, заявки, сделки, статус заявки, дисконты, рыночные данные | 10 RPS по строкам таблицы |
| Неторговые операции | 3 RPS |
| Заявки | дополнительно 200 000 в сутки |

Как суммируются строки «Заявки» и «Получение статуса заявки», что входит в суточную квоту и как отсчитываются сутки — не установлено. Строки таблиц — по сервисам, не обещание общего/независимого бюджета или гарантированной пропускной способности. Не тратить всю квоту на сканирование рынка: нужен резерв на сверку и снижение риска.

| Сервис | Соединений | Сообщений клиента/с | Подписок |
|---|---:|---:|---|
| Портфель | 2 | 10 | — |
| Лимиты | 2 | 10 | — |

| Рыночные данные | 20 | 10 | 100 инструментов в одном соединении |

В таблице также указан объём «8кб» без исчерпывающей семантики — не считать подтверждённым ограничением суммарной скорости потока. Превышение лимитов → **HTTP 429 Too Many Requests**; документация рекомендует повтор с экспоненциальной задержкой, но это **не разрешает слепой повтор торговой команды** с неизвестным результатом. Нужны общий лимитер на счёт, backoff с джиттером, приоритет сверки/выхода. Полнота лимитов по тарифам/персональных лимитов счёта не подтверждена.

**Соединение.** Сервер шлёт `ping` каждые 30 секунд; точный срок ожидания `pong` не указан [S15]. Heartbeat доказывает активность соединения, не свежесть котировок и отсутствие пропусков. Все поля `dateTime` передаются в UTC [S16]; `tradeDate` для вечерней сессии FORTS может соответствовать дате следующей сессии [S12] — при сверках это учитывать.

**История и пагинация.**

- Свечи: интервалы `M1, M5, M15, M30, H1, H4, D, W, MN`; «Максимальное количество баров в одном запросе — 1440» [S06]; большие выборки делятся на окна (границы окон, дубли, пропуски, финальность текущего бара требуют проверки). Сторонняя обёртка заявляла «не больше 1000 баров» [S20] — противоречит текущей документации; возможна смена лимита со временем, константу в код не зашивать. M1 — минимальный перечисленный интервал, но **минимальный бесплатный практически оправданный таймфрейм ещё не установлен**: нужны права, стоимость, полнота и задержка данных по выбранным контрактам. Одно из исходных исследований (`gr`) без подтверждения называло «1–5 минут» практически оправданным бесплатным таймфреймом — это допущение, не доказанный факт.
- Свечи двух ног не воспроизводят одновременно достижимые цены исполнения: разность несинхронных OHLC-экстремумов нельзя выдавать за исполнимый спред.
- Обезличенные сделки: HTTP-история за текущую торговую сессию и отдельный WS-поток [S06] — не многолетняя тиковая история.
- Собственные заявки и сделки: поиск с пагинацией (`page` с 0, `size` по умолчанию 50, максимум 100), но «не более 1000 последних заявок»/«не более 1000 последних сделок» и «начиная с 26.01.2026» [S13]. Пагинация не превращает их в полный архив: нужен собственный журнал и отдельный проверяемый источник полной брокерской истории (отчёты/экспорт).
- История стаканов (архив L2) не доказана: текущий стакан и WS не подтверждают наличие архива; утверждения об «ограниченной/платной» глубокой истории стаканов — допущения отдельных отчётов, не документированный факт.
- Метод статуса заявки возвращает статус «только в рамках текущего дня» [S09]; для длительного анализа — списки сделок/заявок и собственный журнал.
- В справочнике завершение пагинации описано через длину ответа относительно `size`; часть схем неоднозначно помечает `page`/`size` как `in: path` без placeholders в URL — размещение параметров подтвердить до реализации, не исправлять по догадке [S05].

## 6. REST/WS возможности и охват фьючерсов MOEX

**Справочник и спецификации** [S05]. Поиск по типу, тикеру, ISIN; тип `FUTURES` входит в перечень («Список доступных биржевых инструментов: … фьючерсы» [S01]); для MOEX-фьючерсов используется `classCode=SPBFUT`. Поля: `boards`, `classCode`, `minimumStep` («Минимальный шаг цены»), `stepPrice` («Стоимость шага цены»), `currencyStepPrice`, `lotSize` («Размер лота»), `baseAsset`, `maturityDate`, а также флаги квалификации. Наличие полей не доказывает их заполненность и достаточность по всем контрактам: единицы количества, шаг и его стоимость, экспирация/роллирование сверяются с официальными спецификациями MOEX; класс и тикер конкретного фьючерса берутся из справочника, не выдумываются. Утверждения `gr` о полном наборе спецификаций (включая «начальное ГО») в information-service не подтверждены остальными отчётами — проверять фактическим чтением.

**Рыночные данные** [S06]. HTTP: текущие котировки (`POST /api/v1/quotes`), текущий стакан (`GET /api/v1/order-book`, `depth` 1–20, по умолчанию 20; `bidVolume`/`askVolume` считаются «не по всему стакану целиком», а по возвращённой глубине), обезличенные сделки текущей сессии (`POST /api/v1/last-trades`), исторические свечи (`GET /api/v1/candles-chart`). WS: котировки, стакан глубиной 1–20, обезличенные сделки, последняя свеча. Маркетинговое «без задержек» — не SLA по latency, полноте или синхронности ног. Данные отдельно от права выставлять заявки; торговое право API не доказывает бесплатную историю стакана или отсутствие задержки именно на счёте.

**Счёт, деньги, ГО, вариационная маржа** [S07, S08]. HTTP «Лимиты» (`GET /api/v1/limits`) и «Портфель» (`GET /api/v1/portfolio`) и соответствующие WS-потоки; отдельный WS маржинальных показателей. Существенные поля:

- `futureHolding`: `totalNet`, `averagePrice`, `varMargin`, `totalVarMargin`, `realVarMargin` («Начисленная в ходе клиринга вариационная маржа»);
- `futuresLimits`: `cbpLimit`, `cbplUsedForOrders` («Величина ГО, зарезервированного под клиентские заявки»), `cbplUsedForPositions` («…под открытые клиентские позиции»), `loadDate`, `varMargin`, `realVarMargin`; также `lockedForFutures` («Занято под ГО по фьючерсам»), `cbplPlanned`, блоки `moneyLimits`;
- маржинальные показатели: `collateralAvailable`, `varMargin`, `fortsStability` (`freeCash`, `fortsMarginCall`, `fortsForcedClosure` — «Уровень принудительного закрытия», `riskLevel`), `refillSum`, `futuresPortfolio[].futuresCollateral` («ГО по позиции»);
- дисконты по инструментам: `GET /api/v1/instruments-discounts`.

Это наблюдаемые показатели брокера по счёту, не предрасчёт ГО произвольного нового спреда и не обещание неизменности обеспечения: текущее занятое ГО не доказывает наличия broker-side pre-trade расчёта для пары и зачёта риска. Время данных (`loadDate`) контролировать: устаревшее ГО — повод запретить вход.

**Заявки и исполнения** — раздел 7. **Календарь и статусы** [S14]: GET `/api/v1/trading-schedule/daily-schedule`, `/api/v1/trading-schedule/status`; доступность API не означает непрерывные торги всеми инструментами; расписание, клиринг, техперерывы и экспирации сверяются с биржей. **Неторговые операции**: `POST /api/v1/operations/search` — ограниченно; утверждения о недоступности неторговых операций через API непоследовательны между отчётами, проверять методом.

## 7. Заявки: типы, TIF, идентификаторы, идемпотентность, гонки, совместная торговля

**Типы и TIF (по схеме создания [S09]; применимость к FORTS не подтверждена).** `orderType`: `1` рыночная, `2` лимитная, `3` алгоритмическая GTD, `4` айсберг, `5` условная. `timeInForce`: `1` Day (по умолчанию), `2` Fill Or Kill, `3` Good Till Date; для GTD `expiryDate` формата `YYYYMMDD`, не дальше 30 календарных дней. **IOC в исследованном enum отсутствует.** Другие отчёты по PDF/старым страницам перечисляли иные наборы (айсберг/стоп-лимит/тейк-профит/стоп-лосс/комбинации; либо только market/limit с анонсом стопов на июнь 2026) — см. раздел 13; для проектирования считать подтверждёнными рыночную и лимитную, остальные типы подтверждать на выбранных фьючерсах отдельно. Общая схема не доказывает все режимы для FORTS; совместимость айсберга/условных заявок с TIF уточнить. Наличие FOK для одной ноги **не создаёт FOK для пары**.

**Обязательные поля создания:** `clientOrderId`, `orderQuantity`, `orderType`, `side`, `ticker`, `classCode`. Цена положительная, до 8 знаков после запятой; допустимость цены конкретного инструмента дополнительно ограничена биржей. `orderQuantity` описано как «шт.»; для фьючерсов подтвердить соответствие контрактам/лотам, правила акций не переносить.

**Идентификаторы.** Клиентский UUID (`clientOrderId` — «Используется для отслеживания и предотвращения дублирующих заявок» [S09]); биржевой `orderId`, `orderNumber`; `executionId`; `originalClientOrderId` в цепочках замен (подписи в примерах неоднозначны — хранить связи явно). GET `/api/v1/orders` принимает `orderIdType=1` (клиентский UUID) или `2` (биржевой ID). В описании формата биржевого ID и примере есть различие в длине даты — хранить полученную строку без самостоятельной сборки. Хранить раздельно: внутренний ID идеи/пары (клиентская сущность, не поле API), `clientOrderId` каждой операции, исходный/новый UUID при замене, биржевой ID, `executionId`, тикер/класс/счёт/направление/количество/время. Утверждение одного из отчётов (`mm`) об отсутствии `clientOrderId` в API противоречит схемам [S09, S12] и отклонено.

**Идемпотентность (не установлена).** UUID описан как средство предотвращения дублей, но области уникальности/TTL, ответа на повтор того же UUID (с тем же/другим телом), после рестарта и через другой токен не документированы. Exactly-once обещать нельзя. Практические правила: durable UUID на намерение; новый UUID для модификации (замена = отмена + создание нового); после неизвестного результата **не** создавать новый UUID для того же намерения вслепую; dedupe по доступным ID исполнений, не по одному времени; журнал должен допускать исправления (в `executionType` есть «Исправлено»).

**Асинхронность и гонки.** Асинхронный метод «возвращает только подтверждение приёма запроса»; sync-метод «дожидается результата обработки заявки и возвращает её актуальное состояние» [S10], но при потере ответа неопределённость остаётся. HTTP `200` ≠ Filled. На запрос отмены риск активен до подтверждения и сверки: сделка может произойти одновременно с отменой. Pending Cancel (`6`) и Pending Replace (`9`) — не финал. «Отменена» может означать отмену неисполненного остатка после частичного исполнения — позиция остаётся. При замене учитывать цепочку исходная→новая и гонку исполнения. Не складывать повторно `lastQuantity`; использовать `executedQuantity`, `remainedQuantity`, `lastQuantity` и ID исполнений.

**Статусы.** Документированные `orderStatus` потока [S12]: `0` Новая, `1` Частично исполнена, `2` Полностью исполнена, `4` Отменена, `5` Заменена, `6` Отменяется, `8` Отклонена, `9` Заменяется, `10` Ожидает подтверждения новой заявки. В сообщении также `executionType`, `orderQuantity`, `executedQuantity`, `lastQuantity`, `remainedQuantity`, `averagePrice`, `transactionTime`, `tradeDate`, `executionId`. `executionType` и `orderStatus` — разные перечисления (код `9` означает разное) — не смешивать. `averagePrice` — «Для сделок РЕПО/спредов: цена первой части» [S12]: эта цитата описывает отчётность бэк-офиса и **не доказывает** доступность фьючерсного спредового ордера.

**Совместная ручная торговля.** Отмена и изменение заявок, поданных через Trade API и приложение «БКС Мир инвестиций», описаны явно [S11]; полнота охвата всех иных каналов (QUIK и пр.) не доказана. Ручные/чужие операции не отменять автоматом по сходству тикера; при обнаружении внешних изменений — сверка всех позиций и доступных заявок, явное принятие внешней операции в модель, пересчёт капитала; источник операции в общих полях структурно не гарантирован.

**Что сервер делает и чего не делает.** Сервер: проверяет права, ограничения, риск/статусы, исполняет и отслеживает заявки. Сервер **не документирован** на: атомарную пару, exactly-once, server replay/sequence, cancel-on-disconnect, mass cancel, kill switch, пользовательский stop-loss по относительному результату, изоляцию тестового капитала, предрасчёт ГО пары.

## 8. Спреды: атомарность, `spread`, биржевые календарные спреды MOEX

**Атомарной произвольной пары в API нет.** В схеме создания один `ticker` и один `classCode`; массива ног/операции «все ноги либо ни одной» не найдено [S09]. Поле `spread` — «Защитный спред. Используется для условных заявок» (защита условной заявки), не признак двухногой фьючерсной заявки. Упоминание «Для сделок РЕПО/спредов: цена первой части» относится к отчётности сделок, а не к способу подачи. Спредовая стратегия реализуется двумя (или более) независимыми одиночными заявками с координацией и риск-контролем на стороне клиента; атомарная спредовая заявка не равна быстрой отправке двух независимых.

**Биржевые календарные спреды MOEX — ключевой нерешённый вопрос.** По материалам отчёта `cg` (проверка 21.10.2026), на Московской бирже календарный спред — самостоятельный торговый инструмент (одновременная покупка/продажа фьючерсов с одним БА и разными экспирациями); биржа документирует синтетическое сопоставление заявок спреда с заявками из стаканов обоих фьючерсов и типы спредовых заявок `limit`, `market`, `FOK`. Точная ссылка на документ MOEX в исходном отчёте не сохранена (в выдаче фигурировал `moex.com`) — **прямой URL и формулировки нужно перепроверить первоисточником MOEX**. Существенно: если БКС предоставляет доступ к таким инструментам через обычный интерфейс заявок, часть задачи «две ноги» решается биржевым инструментом, а не эмуляцией. Однако публичная документация БКС **не подтверждает** ни доступности конкретных спредовых тикеров через BCS Trade API, ни их приёма торговым сервисом, ни единиц/режимов исполнения. Проверить справочник инструментов на спредовые коды и получить письменное подтверждение БКС — приоритетный вопрос поддержки (раздел 14, п. 5).

**Вывод для проектирования.** До подтверждения считать базовый сценарий синтетическим (пара одиночных заявок), а стратегии, требующие гарантированного одновременного входа, — исключёнными либо подлежащими изменению требований. Если атомарность/биржевой спред будут документально подтверждены — пересмотреть разделы 8–10.

## 10. Минимальная модель событий/состояний (с неизвестным)

Это **проектное предложение клиента, не дополнительная гарантия сервера**.

**Заявка (каждая нога):**

`Prepared → Sent → Accepted/PendingNew (10) → Working/New (0) → PartiallyFilled (1) → Filled (2)`

Ветви: `Rejected (8)`; `CancelPending (6) → Cancelled (4)`; `ReplacePending (9) → Replaced (5)` с привязкой к новой заявке. Из любого состояния отправленной операции при потере ответа/связи — флаг **UnknownOutcome / ReconciliationRequired**: неизвестность не равна отмене или отклонению. «Отменена» может означать отмену остатка после частичного исполнения — позиция остаётся.

**Пара (спред):** `Flat → EntryPending → Unhedged/PartiallyHedged → Hedged → ExitPending → Flat`, плюс `ReconciliationRequired`. «Обе заявки приняты» ≠ Hedged. Коэффициент хеджа и допустимый денежный дисбаланс задаются исследованием стратегии, не API. FOK одной ноги не даёт FOK пары; условная заявка (если доступна) не гарантирует цену выхода/ликвидность/исполнение второй ноги.

**Правила обработки (сводно):** (1) намерение и UUID фиксировать в устойчивом журнале до отправки; (2) HTTP `200` асинхронного метода не переводит заявку в Filled, sync тоже требует анализа; (3) до подтверждения отмены считать риск активным; (4) дедупликация по ID исполнений и сверка накопленного количества; (5) при восстановлении сначала сверять заявки → сделки → позиции, затем разрешать новые входы; одно событие или один snapshot не доказывают консистентность всех сервисов на общий момент; (6) журнал допускает исправления («Исправлено» в `executionType`).

**Неизвестное модели:** точный TTL дедупликации UUID; время видимости статуса между HTTP и WS; полнота охвата ручных/серверных поручений; порядок и ровно-однократная доставка; семантика `8кб` в WS-лимитах; поведение при брокерском закрытии.

## 11. Сценарии отказа

Приоритет всех реакций: **остановить новые входы → установить фактическое состояние → управлять уже существующим риском**. Это проектные требования, не выполненные испытания.

| Сценарий | Опасность | Предлагаемая реакция |
|---|---|---|
| Timeout после принятия | Дубль при повторе | `UnknownOutcome`; поиск по исходному UUID (GET `/api/v1/orders`, поиск заявок/сделок, позиция, WS); при неясности — остановка и эскалация, **не** новый POST. 404 сразу после timeout — не доказательство отсутствия заявки |
| Частично исполнена одна нога | Открытый направленный риск | Учесть фактически исполненное; прекратить остальные входы; по заранее утверждённому плану отменить остатки и/или снизить дисбаланс (согласованный безопасный хедж/закрытие). Не наращивать риск ради «красивой пары»; ГО и риск считать по фактическим исполнениям и стакану |
| Истёк access/refresh | Прекращение управления при живых заявках | Запрет входов; обновление access по refresh; при окончании refresh — новый выпуск в кабинете; затем полная сверка; резервный ручной канал (МИ/телефон). Истечение токена не закрывает позицию |
| Разрыв WS / пропуск событий | Локальное состояние отстаёт | Переподключение, повторная подписка, HTTP-сверка (заявки, сделки, позиции, лимиты/ГО), контроль границ истории; **replay не предполагать**; торговля запрещена до согласования состояния |
| Дубликат команды/события | Повторная позиция, двойной учёт | Устойчивые UUID, дедупликация событий, журнал, сверка накопленного исполнения; серверный TTL дедупликации уточнить; лишний объём трактовать как незапланированную позицию |
| HTTP 429 | Потеря возможности срочной отмены | Общий лимитер на счёт, резерв квоты, backoff чтения; торговые повторы только после анализа результата; приоритет сверки/выхода |
| Устаревшее ГО / сдвиг дисконта LQDT | Недостаток средств, затрагивание основного портфеля | Контроль `loadDate`/свежести и запаса; при неизвестности — запрет входа, запрос актуальных лимитов; неизвестный запас считать недостаточным; внебюджетное использование активов — инцидент |
| Ручная заявка/отмена через МИ | Расхождение с моделью | Сверка всех позиций и доступных заявок, принятие внешней операции; не реконструировать позиции только по собственным ID; не отменять чужие поручения автоматом |
| Принудительное закрытие брокером | Портфель меняется вне алгоритма | Инцидент: запрет входов, сверка сделок и остатков, уведомление; не восстанавливать позицию автоматически |
| Перезапуск/потеря журнала | Неизвестные действующие заявки | Старт в read-only/reconciliation; при невозможности полного восстановления — ручная эскалация |
| Клиринг/остановка торгов/экспирация | Отказ или задержка исполнения | Сверять расписание, статус и контракт; не обещать немедленный безопасный выход |

При типичной ручной реакции 3–90 минут (медиана ~5–15 минут) Telegram **не является** механизмом гарантированного аварийного выхода. Нужны заранее утверждённые пределы незащищённой позиции и действия без ожидания пользователя; возможность их выполнения ещё предстоит доказать.

## 12. Sandbox, риск-контроль, восстановление, изоляция секретов: что серверное, что клиентское

**Sandbox.** Подтверждённого официального sandbox/тестового счёта/симуляции исполнения для Trade API в исследованной документации нет (поиски по `trade-api.bcs.ru` безрезультатны; сторонний опыт — Habr [S25] — также указывает на отсутствие песочницы; демо-счёт БКС для веб-терминала не документирован как доступный через API). Отсутствие подтверждения ≠ окончательное доказательство отсутствия — вопрос поддержке. Проверки без сделок возможны только через read-only методы; **переход к «тестам» боевыми заявками не является автоматическим следствием отсутствия sandbox**.

**Риск-контроль.** Документированы наблюдаемые риск-показатели (`fortsStability`, `riskLevel`, `fortsForcedClosure`, `refillSum`, дисконты) и право брокера на принудительные действия. Не документированы: клиентский kill switch, «закрыть всё», mass cancel, отключение торговли с сохранением данных, серверный пользовательский stop-loss по относительному результату, гарантия изоляции тестового капитала, двухногий хедж. Аварийное сокращение реализуется клиентом: перечислить позиции → отменить свои заявки (списком+отменой) → выставить компенсирующие заявки с учётом RPS.

**Отключение сети/отзыв доступа** само по себе не отменяет заявки и не обнуляет позицию. Что обеспечено сервером: права, лимиты, статусы, риск-уровни. Что нужно реализовать клиенту: kill switch (блок новых входов + сверка/безопасное сокращение по отдельному разрешению), журнал intent→ID→fills→позиции, дедупликацию, reconcile REST/WS, обслуживание токенов, режим «никаких новых входов» при любом сбое.

**Календарь/часы.** Расписание и торговые статусы — серверные методы [S14]; интерпретация (вечерняя дата FORTS, UTC, клиринги) — на клиенте. Мониторинг 24/7 не означает торгов всеми инструментами 24/7.

**Изоляция секретов** — полностью клиентская обязанность (раздел 4). Восстановление после сбоев: сначала авторизация/подписки, затем сверка заявок, сделок, позиций, денег/ГО и ручных операций до возобновления; при неопределённости — человек, а не повтор POST.

## 15. План будущего подключения и предварительных проверок только на чтение

**Ни один пункт не выполнен.** До отдельного разрешения не выпускать токены и не входить в счёт. Никаких секретов, торговых POST, платных подписок, больших выгрузок и производственного доступа.

1. Ответы поддержки (раздел 14) о цене, персональном доступе и read-only правах; тариф не менять автоматически.
2. Пользователь самостоятельно проверяет наличие раздела API и, если согласовано, выпускает **отдельный read-only refresh** для одного выбранного счёта; секрет остаётся у пользователя, в отчёт не передаётся.
3. В разрешённой среде проверить авторизацию, сроки, scope, отзыв/ротацию. **Не** проверять запрет торговли отправкой настоящей заявки: при ошибке прав она может исполниться.
4. Небольшой набор справочных записей по заранее выбранным фьючерсам; сопоставление со спецификациями MOEX (шаг, стоимость шага, лот, экспирация). Тикеры выбирать до запроса.
5. Расписание и торговые статусы, UTC, вечернюю торговую дату, экспирации.
6. Snapshots портфеля/лимитов/маржинальных показателей: единицы, `loadDate`, null-поля. Персональные значения не публиковать.
7. Небольшая WS-подписка на выбранные инструменты: heartbeat, переподключение, повторная подписка, свежесть. Не добиваться 429 нагрузкой.
8. Ограниченное окно свечей (включая границы окна и текущий незавершённый бар) и стакан глубины до 20. Большой исторической выгрузки не делать.
9. Если на счёте уже есть собственные поручения/сделки и чтение разрешено — проверить их поиск и соответствие брокерскому отчёту. Сделки для наполнения истории не создавать.
10. Замеры отдельно от документации: дата, среда/сеть, тип токена без секрета, запрос без персональных значений, ответ/ошибка, задержка; свежесть/полнота/допустимость данных и фактическое свободное ГО/резерв/ВМ на **общем** счёте. Из малой выборки SLA не выводить.

Проверка соответствия бюджету ресурсов (VPS 1 vCPU, 1 ГБ RAM + 2 ГБ swap, общий бюджет фоновых задач 250–350 МБ, не измеренный) — отдельными замерами после разрешения; на текущем этапе к VPS не подключаться.

## 16. Неисполненный допуск реальной торговли

Реальная торговля **не допущена**. До запуска, независимо от результатов публичной части, должны быть выполнены: актуальные договор/тариф, разрешения БКС, признание статуса и доступ конкретных контрактов; подтверждённые типы поручений/TIF, единицы и семантика замены для выбранных инструментов; ответы по повторным UUID, timeout, видимости статуса, потоку и полноте истории; проверенные восстановление, журнал, обработка частичного хеджа, ручное вмешательство и аварийный канал; решение о sandbox либо отдельное решение о допустимом испытании (**не автоматический переход к тестам боевыми заявками**); независимо доказанная жизнеспособность стратегии и бюджета (комиссии, ликвидность, ГО, ВМ), а не только техническая доступность API; утверждённый риск общего счёта и обращение с LQDT (API не обособляет 30 000 ₽); реализованные правила действий при относительной просадке/отставании (предупреждение 5 тыс. ₽, действия при 10 тыс. ₽ от максимума или накопленном отставании 10 тыс. ₽, внешняя граница 15 тыс. ₽, пересмотр через 90 дней без обнуления — это **правила пользователя, не биржевые stops и не гарантированный предел убытка**); вход проходит без экстренных средств; совокупные положительные дополнительные выделения ≤15 тыс. ₽, все выделения вместе ≤45 тыс. ₽ (возвраты лимит не восстанавливают); при накопленном отставании 10 тыс. ₽ дополнительные средства — только для безопасного выхода в ноль; несогласованное вовлечение основного портфеля — инцидент с учётом выделений (выручка от продажи LQDT сама по себе не равна экономическому убытку; доход LQDT, остающегося в допустимом залоге, не вычитается второй раз при сравнении с контрфактическим сценарием); проверены ресурсы среды.

Вывод **не переносится автоматически на масштаб 10–20 млн ₽**: там заново проверяются ликвидность, исполнение, комиссии, обеспечение и операционные пределы.

## 17. Минимальные границы будущего адаптера (без кода и выбора стека)

1. **Авторизация:** scopes, сроки, координация обновления, отзыв, безопасное хранение секретов (изолированно; без логов/Telegram/отчётов).
2. **Справочник/календарь:** инструмент, режим торгов, единицы цены/количества, шаг и его стоимость, экспирация, актуальный статус.
3. **Рыночные данные:** чтение/подписки, timestamps, свежесть, переподключение; без права решать о входе.
4. **Состояние счёта:** позиции, деньги, ГО/ВМ, риск-показатели, время обновления; отдельный внутренний учёт тестового бюджета (брокерские `dailyPL`/`varMargin` ≠ относительный результат к LQDT).
5. **Жизненный цикл поручений:** журнал intent→UUID→ID→fills→позиции; раздельные Accepted/Executed/UnknownOutcome; корреляция замен; дедупликация с исправлениями.
6. **Сверка и аудит:** reconcile REST/WS, обнаружение ручных/брокерских вмешательств, независимый источник полной истории.
7. **Политика допуска:** read-only по умолчанию; запрет новых входов при сбое/лимите/неизвестном ГО; общий лимитер с резервом квоты; управление открытым риском по отдельному утверждённому плану (частичный хедж); kill switch.
8. **Оповещения:** Telegram как дополнительный канал, без секретов и лишних персональных данных; потеря уведомления не разрешает торговлю.

Адаптер не решает экономическую обоснованность пары, налоговый режим, перенос статуса КПУР и допустимость обеспечения. Модель риска стратегии считает пару как две независимые ноги с комиссией, проскальзыванием, изменениями ГО и ликвидностью и сравнивает результат с контрфактическим LQDT при одинаковых внешних денежных потоках.
