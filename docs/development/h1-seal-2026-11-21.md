## Contract and active storage

The exact source plan from C1 remains unchanged:
`e40d53108e972d6fa001e33342ec38da5c927f3624a5ca5a9cc83e29eb8acbda`.
It covers 120 intake H1 datasets / 448,565 bars, with zero screened H1 copies
on this workstation. Tests cover distinct copies in both namespaces.

`data-lake/h1-seal.json` contains the copied verified source records and the
screen-first selection map. `h1-seal.enabled.json` binds its canonical hash.
The reader validates table hashes against those records, not a later mutable
candidate manifest. It preserves original JSON source paths/hashes in provenance,
including when those JSON files are absent. File signature changes invalidate
cached verification. Invalid controls, corrupted/missing tables, new preferred
screened copies, changed retained JSON, unsealed input or symlinks fail closed.

**`data-lake/candidates/h1-0fb843b/` is now active production storage**, despite
its historical candidate directory name. Do not delete, compact or rewrite its
tables as disposable staging. Do not refresh sealed JSON in place: with originals
present, deactivate under supervision first, refresh/replan/reverify, then seal
the newly reviewed candidate. If JSON has subsequently been archived, restore
and verify it before using the guarded deactivation operation.

`ScreenerInputs` and calendar H1 selection use the same sealed source map. Screen
availability and audit checks no longer require an H1 JSON file when a verified
sealed source exists. Daily/funding source routing is unchanged. Actual adapter
read of `SiZ2_1h.json` returned backend `sealed_parquet`, 5,350 rows, and its
original source path. No process-local shadow override was used for C2 checks.

## Supervised activation and rollback rehearsal

The existing supervised screener was unloaded for the control-file changes.
The procedure, with service restoration in a `finally` block, was:

1. Record hashes of every pre-existing data/lake file.
2. Reverify the C1 plan/candidate and activate sealed reads for all 120 datasets.
3. Run the fixed production-input smoke script against the pre-archive baseline.
4. Deactivate through the guarded CLI logic. It required all original JSON and
   exact source selection to match, then retained the activation controls in a
   unique `data-lake/h1-seal-history/` directory.
5. Run the same smoke script on the restored previous reader contract.
6. Reactivate the same verified candidate, verify all 120 sealed records again,
   and restore the supervised service.

Result: **120 retained JSON**, **2,731 existing data files unchanged** and
**255 existing lake files unchanged**. Only seal controls and rollback history
were added. The final reader state is sealed/active. Original H1 JSON was never
renamed, removed or compressed. No additional disk reclamation is claimed.

This rehearses **reader routing rollback with retained originals**, not extraction
of an active-H1 archive. The latter remains a separate prerequisite to removal.

## C3 — remaining removal prerequisites

Do not delete H1 JSON merely because the sealed reader can operate without it.
Before an active-H1 archive/apply operation:

1. Make default lake verification/maintenance compatible with archived pilot
   JSON; its current legacy verifier still requires those original files.
2. Preserve fixed search/rank/score/plateau/rejection evidence and measure cold
   load/column projection; C2's bounded smoke does not replace these gates.
3. Create a dedicated active-H1 archive with exact hashes, verify every member,
   and rehearse full extraction/rollback without overwriting working files.
4. Measure net allocation including archive, live lake and seal/catalog overhead,
   and confirm the planned removal threshold before supervised apply.
5. Recheck the exact active source plan and all reader consumers immediately
   before removal; verify proof/screen/funding/calendar/UI again afterwards.

`source_deletion_allowed=false` remains explicit in controls and CLI results.
No active-H1 deletion CLI or scheduled deletion was added in this release.
