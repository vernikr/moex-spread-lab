# Agent performance 2: shorten time to a verified change

**Status:** Proposed, 2026-11-22. Repository inspected at `e12bb51`. This extends the [first performance plan](../agent-performance-plan.md); it does not authorize weaker test gates, unattended deployment, or changes to the research/accounting contracts. It optimizes task delivery, not only screener runtime.

## Findings from the three complete exports

| Export and task | Bash calls | Sum of reported call durations | Calls under 1 s | Largest measured recurring cost |
| --- | ---: | ---: | ---: | --- |
| `fb9e1ee.md`: P1, then browser/bridge/benchmark/rounding work | 397 | 7,820 s | 151 | 22 successful full pytest runs: 4,370 s of pytest-reported elapsed time alone (about 73 min; 140–338 s per run). |
| `b687ae2.md`: P7.1 strategy discovery and lazy registry | 127 | 349 s | 100 | Two full pytest runs: 84.09 s and 89.71 s, both reporting 581 tests and 232 subtests. Equal counts do not establish identical inputs. |
| `9dae286.md`: P7.2 proof decomposition | 161 | 1,821 s | 56 | 12 full-suite command blocks, 79–89 s each, totaling 988 s, or 54% of summed Bash time. Twelve separate `remote sync` blocks totaled about 55 s. |

**Method.** Count `##### Used Bash` records once, normalize `ms`/`s`, and sum the displayed (rounded) tool durations. A block can include edits, several checks, or a remote operation; its duration belongs to the block, not to each component. For the 22 runs in `fb9e1ee.md`, use the pytest completion lines instead; exclude the 13-test focused run near L22019. These are neither session wall times nor CPU times. Exports do not expose enough start/end timestamps, overlap, user idle time, or model/context latency to reconstruct a critical path. They represent three workloads on differing revisions and environments, not a before/after benchmark. Source line references below use the original uploaded Markdown, 1-based; raw logs are deliberately not tracked.

### What to change first

- **Reduce redundant verification, not verification coverage.** In P7.2 the recurring full-suite cost dwarfs `git push` and workstation sync. Much of the cost is the chosen publish cadence, not necessarily duplicate execution on the same tree. In P7.1 a full suite ran twice in one turn (`b687ae2.md` L9443, L10228); separate commands also reran health and parity. Before eliminating any run, determine whether the relevant inputs changed. A failed or unproven check is not reusable. Several P7.1 commands piped through `tail`/`grep` without explicit `pipefail` (L9414, L9443, L10228); short output must not hide exit status.
- **Treat the two-vCPU sandbox as a different workload.** `fb9e1ee.md` reports 177.91 s at L2688 and 337.70 s at L14840 for different revisions/runs. The later 153.80 s sequential run (L22088) motivates a worker-count A/B, not a conclusion that sequential is faster. Browser smokes already have an offline runner, yet 11 took 189.1 s; the four longest scenarios alone took 99.6 s (L1770–1781). Profile application work inside scenarios before assuming Chromium startup is the dominant cost.
- **Spend less context rediscovering work.** P7.2 had 11 user `продолжи` messages after the first extraction (L1825–10606), and repeated health-baseline recalculation/review (e.g. L3014, L3766, L11852). P7.1 had 100 sub-second Bash calls, yet individual output blocks exceeded 10,000 characters (L3484, L9836). These are signs of interactive/context overhead, not measurements of it. A bounded work packet, symbol-level reads and compact test output address this without changing application behavior.
- **Make handoff predictable, not privileged.** `remote sync` is already cheap when configured; P7.1 still ran status/sync/status and then a separate manual remote operation (L10577–10673). The `fb9e1ee.md` work expanded from P1 to several independently reviewable deliverables. Benchmark-only iteration, merge/publish, and workstation promotion should be independently timed and separately authorized. The supplied exports contain credentials: do not commit or quote them, do not reuse them for future work, and have the owner revoke/rotate the exposed credentials and check any remaining exported copies or artifacts.

## Delivery roadmap

| Order | Deliverable | Proposed acceptance target (not a measured result) |
| --- | --- | --- |
| A | Measure and standardize the verification loop | One bounded report per run, real exit status, queue time separate from execution, no needless rerun for an identical input and check. |
| B | Shadow a risk-based test selector, then change publish cadence by agreement | At least 30% less median task-to-verified-main time on matched low-risk tasks; no attributable missed regression in shadow runs. |
| C | Profile and split expensive fixtures/browser tests | At least 25% lower p90 full offline suite on a pinned 2-vCPU runner; all current browser scenarios in under 120 s on the same class of runner. |
| D | Prototype a warm verification/merge lane and workstation promotion | At least 25% lower p90 ready-to-verified-main time than the improved cold lane, without worse flakiness or unacceptable cost. |

### A. One check runner, usable evidence, and reusable task state

1. Build a single documented launcher for `quick`, `affected`, and `full` profiles, used locally and in CI. Start by wrapping existing commands, not replacing the [health ratchet](../code-health-plan.md). Pin environment once with `uv sync --frozen`, then use `uv run --no-sync`; enforce `MOEX_OFFLINE_ONLY=1` on synthetic paths. A documentation-only profile must include document links, whitespace and secret checks; any uncertain classification falls back to the existing code gate. Make stage exit codes authoritative, add timeouts and process-tree cleanup, and report `passed`, `failed`, `not run`, or `unavailable` explicitly. Keep full logs out of chat and emit a small summary plus a bounded failure tail.
2. Emit versioned, sanitized records: task class, phase, base SHA and candidate input fingerprint, selected checks and reasons, runner/CPU quota, cold/warm status, queue/setup/collection/setup-call-teardown durations as applicable, pass/fail/timeout, retries, and publication/promotion status. Record phase start/end so overlap is observable. Benchmark on fixed synthetic inputs; no env values, account data, absolute home paths or raw agent exports in telemetry. A result can be reused only for the same check and unchanged relevant inputs; initially key the whole tree including uncommitted fixtures, lockfile, toolchain, config and execution mode. Cache dependencies and compiled artifacts before attempting broader pass-result reuse; never cache failures as passes.
3. Put a compact task packet in the agreed tracking surface: goal and non-goals, ownership, affected symbols, acceptance commands, completed checkpoints and next step. Give agents targeted symbol lookup and per-file diff summaries (use [existing Repowise tooling](../ci.md#workstation-repowise-mcp-setup) where available). Use semantic/AST-aware codemods for repetitive import-only rewrites with idempotence and diff review. For ratchets, consider a read-only per-symbol preview and a tool that proposes deletions/decreases only; never auto-accept new violations or raise ceilings. Keep the global ratchet check authoritative.

### B. Fewer full suites on the delivery path, same confidence at promotion

- Infer an impact plan from changed paths, package DAG and reverse dependents. Include contracts, compatibility imports, plugin discovery, fixtures/config and changed tests. Start conservative: shared fixtures, dependency/runtime/CI config, unknown paths, dynamic discovery changes, cross-package contracts, or missing diff data require the full gate. Proof/accounting changes retain mandatory numerical equivalence and relevant replay tests; browser, macOS and C99 sanitizer gates remain mandatory when the corresponding contract is touched. Keep dependency selection transparent (emit why each test group was included); historical timing and test coverage can rank checks, not silently exclude them.
- **Shadow first:** execute the proposed selection alongside the unchanged full gate on the same candidate. Record missed failures and inject known previous regressions into disposable worktrees, including registry discovery, proof parity, fixture changes and a JS module break. Require at least 30 candidates spanning docs, leaf, cross-package and parity-sensitive changes, no missed regression, and a working fail-full switch before trusting selection for early feedback. A passing affected suite must never be reported as full verification.
- **Separate checkpoint from publication.** With explicit agreement, keep multiple coherent local commits for a bounded work package, each with focused checks, then perform the full applicable gate on the exact integrated tree before one main publication and one workstation sync. Keep small reversible commits and stop on contract changes; do not combine unrelated features to amortize testing. Until cadence is changed, honor per-delivery push/sync and reuse only checks on equivalent inputs. For an illustrative 12-slice P7.2 replay, four integrated deliveries instead of twelve remove eight full-suite invocations: roughly 11 min of gross command time at 82 s each, before added focused tests, coordination and CI queueing. This is a scenario, not a savings claim or authorization to skip gates.
- In CI, measure redundant work before rewriting the workflow: the architecture script runs standalone and inside Tier 1; `test_perf_equivalence.py` belongs to proof's test path and is also a dedicated job. Consider single ownership per gate **only** after confirming equivalent environment/flags, required-check compatibility, and aggregate test collection parity. Compare the current `needs: architecture-gate` dependency with parallel job launch: dropping a scheduling dependency can lower green-path latency but increase wasted runner minutes on failures. Never remove architecture or parity coverage.

### C. Make full verification cheaper at the source

- Run matched measurements on pinned commits, fixtures and Python/tool versions with cgroup-aware caps; compare sequential, `-n 2`, `-n 4` where budget allows, and end-to-end CI matrix time including queue/setup. Use per-test setup/call/teardown and worker timelines to find contention, imports/collection, and long-file tails under `loadfile`. Account for process pools inside tests before adding xdist workers. Split the measured longest test files at fixture-ownership boundaries if this reduces the tail, not by committing a global duration file.
- Audit similar integration fixtures for repeated data preparation and expensive proof search. Move pure invariants into small deterministic examples; share read-only prepared fixtures where useful, but isolate mutable datasets, caches, registries and process pools. Keep representative full-resolution cases for pair/calendar, daily/hourly, worker/fallback paths, deterministic hashes, and ledger reconciliation. Compare test IDs and prior regression coverage before replacing fixtures; compare canonical outputs and repeat in a clean process with network disabled. Do not trim trial counts or histories in a parity test just to meet a time budget.
- Add phase timers to the browser runner: app startup, browser launch, fixture hydration, API compute, UI assertions. Pilot one long-lived Chromium process with a new context per scenario and separate app lifetimes where required; benchmark it against the existing isolated-process runner. Move headless assertions without UI-specific behavior to HTTP/JS contract tests while keeping actual UI transitions, rendering and result parity covered. Keep the full runner as reference until the replacement passes clean and repeated runs without cache leakage or increased flakes.

### D. Larger option: a warm, isolated verification and promotion lane

- If setup/queue and repeated runs remain material after A–C, compare a prebuilt versioned runner image with ephemeral per-job worktrees against a managed warm worker pool. Key environment/compiled caches on lockfile, OS/arch, Python, flags, compiler and source as applicable. Never reuse mutable application interpreter state or share writable caches across trust boundaries. Use resource-aware scheduling, bounded concurrency, job cancellation and cleanup. Compare using the exact same integrated tree; publish only the checked tree, and invalidate or rerun when `main` advances. If branch rules and the owner allow it, a merge queue can validate a small batch on the prospective merge tree, with failure bisection; do not replace the existing direct-main workflow without approval.
- Build workstation promotion on [the existing `remote` CLI](../remote-agent-testing.md#implemented-statussync-commands), not shell replay. One opted-in handoff should take an expected SHA, fast-forward without overwriting local work, sync dependencies only when needed, restart if required, and return verified running revision/health or a concrete reason it could not. Use explicit outcomes (`published`, `synced`, `health-confirmed`), bounded readiness retries rather than fixed sleeps, and idempotence for a repeated SHA. Provision short-lived scoped credentials via the runtime, not prompts or Actions artifacts. Leave market caches on the workstation, use isolated remote probes for comparison, and keep the current manual route if credentials or capabilities are absent. A future automatic restart on verified `main` is an owner opt-in, not part of this plan's rollout.

## How to decide whether it worked

Use three replay workloads: a frontend/static fix (P1), a cross-package plugin contract change (P7.1), and a multi-slice proof refactor (P7.2). Run A/B on matched revisions/patches and pinned runners; keep cold and warm samples separate. Start with at least five paired runs per workload for diagnosis; collect at least 20 comparable observations per reported cohort before treating p90 as actionable, and publish sample counts and ranges. Track task accepted → first actionable check → verified exact `main` SHA → workstation health (when requested); report user wait, CI queue, agent/tool wall time, runner minutes, retries and evidence volume separately. Track full-suite runs, user continuations, false skips and flakes as guardrails. Compare the end-to-end metric, not just a faster command. Stop rollout on a missed required check, numerical/hash drift, state leakage, or a falsely green handoff; fall back to the existing full/isolated workflow and investigate.

**Next implementation slice:** A only. Instrument existing checks, run the three replays and publish a sanitized baseline. Use it to choose between B and C first; defer D until the remaining bottleneck and runner economics justify it.
