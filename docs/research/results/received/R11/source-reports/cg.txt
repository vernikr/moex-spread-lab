Do not select a production stack yet. ## Hard no-go conditions

- Any need to change ports 22/443/20724, the x-ui service/data, firewall, routing, DNS, sysctl/network tuning, system packages or VPN configuration merely to make the project work.

- Unmeasured or inadequate host headroom, recurring swap-in/out under load, CPU contention that delays monitoring, disk-free reserve below the agreed floor, or resource interference with the existing scheduled workload.

- Unknown/stale data being displayed as current; alert failure leaving an apparently healthy state; replay causing duplicate signal or future duplicate order; or a restore not proven on a separate copy.

- Any need to publish a dashboard publicly, put secrets into a notebook/prompt/repository/log, or depend on a free/ephemeral hosted runtime for always-on monitoring.

- Any requirement for the system to automate orders or use core-account collateral before the separate authorization, account, risk and reconciliation gates are passed.

# 3. Workload dimensioning from the embedded assumptions

The numerical estimates below are derived from the prompt’s scenario ranges, not production telemetry. Daily-market history volume is inherently small if retained only as one bar per contract per trading day. Raw response snapshots at intraday cadence can be much larger, especially if the provider response contains verbose JSON and full metadata.

## 3.1 Daily OHLCV and open-interest baseline

Model: daily bars = number of contracts × 252 assumed trading days/year × years. For disk sizing only, use an explicit planning range of 100-200 bytes per normalized CSV row; this excludes provider response overhead, database indexes, versioned raw payloads and backups. Apply a 2-5× envelope to include normalization/index/provenance overhead and one copy of raw content; validate actual compressed and uncompressed sizes later.

| **Scenario** | **Calculation**               | **Daily rows over history** | **Normalized row payload** | **Planning envelope at 2-5×** |
|--------------|-------------------------------|-----------------------------|----------------------------|-------------------------------|
| Low          | 50 contracts × 3 years × 252  | 37,800                      | 3.8 MB at 100 B/row        | 8-19 MB                       |
| Middle       | 100 contracts × 3 years × 252 | 75,600                      | 11.3 MB at 150 B/row       | 23-57 MB                      |
| High         | 300 contracts × 5 years × 252 | 378,000                     | 75.6 MB at 200 B/row       | 151-378 MB                    |

These figures do not prove MOEX or a broker exposes five years of daily history, open interest for every contract, or a consistent back-adjusted/roll series. They show only that a daily-bar-only collection is unlikely to be the storage driver. History coverage, expired-contract accessibility, board mapping, corrections/revisions, OI field semantics and permissible use remain data acceptance tests [S1-S2].

## 3.2 Optional hourly / 15-minute watchlist snapshots

For a transparent range, convert 5-30 pairs into 10-60 watched contract legs. Assume 252 active days/year and an illustrative 12 effective observation hours per active day: 12 snapshots/day at hourly cadence, or 48 snapshots/day at 15-minute cadence. Real MOEX session calendars differ by market/instrument and must replace this illustrative 12-hour parameter.

| **Scenario**  | **Formula**        | **Normalized observations/year** | **Payload at 100-300 B/row** | **3-year raw+index range (2-5×)** |
|---------------|--------------------|----------------------------------|------------------------------|-----------------------------------|
| Low / hourly  | 10 legs × 12 × 252 | 30,240                           | 3-9 MB/year                  | 18-136 MB                         |
| High / 15 min | 60 legs × 48 × 252 | 725,760                          | 73-218 MB/year               | 0.44-3.27 GB                      |

A second, intentionally broad network sensitivity uses an assumed 0.5-5 KiB response per contract snapshot (not a MOEX/BCS measured payload). That yields approximately 15 MB-3.6 GB/year across the extremes above before protocol overhead; multiply by the retained years. Actual payload size, compression, batching and whether the source is polling or a stream determine the result. Measure it; do not size on the low end alone.

## 4.3 UI and access shape

“Dark-only” is a visual preference, not an architectural driver. Prefer a read-only local view or a small local HTTP UI only if it earns its memory cost. The default future access pattern should be a loopback-bound listener or an explicitly approved SSH tunnel, with authentication and no public dashboard ingress. Do not add a public reverse proxy, new firewall rules, or a listener bound to all interfaces simply to make the UI convenient. If the UI cannot fit the headroom envelope, view static/exported results locally on the Mac instead.

## 4.4 Reproducibility and stable seams

- Record both event time (exchange timestamp/session date) and knowledge time (when the system fetched/first knew the row). Preserve raw revisions/corrections and never silently replace data used by a previous run.

- Every row/snapshot needs provider, market/board, instrument identifier, contract expiry/roll mapping, timeframe, source timestamp, fetch timestamp UTC, request parameters, parser version, schema version, and raw-content hash. Preserve calendars/specifications with effective-from/effective-to time and source URL/version.

- Every research run needs immutable dataset release ID, code commit/archive hash, config/strategy version, timezone/calendar version, parameter set, seed (if any), run start/end and output checksum. Export compact CSV/Parquet plus JSON/README manifest so results can move between Mac, VPS and future provider.

- Bound batch size and memory: small instrument set × time window; persist the last complete page/date/instrument after validating row count/checksum; retry transient failures with capped exponential backoff and jitter. Make completed chunks idempotent.

- For broker/data-source changes, maintain a small adapter seam: instrument specification lookup, session calendar, candles/quotes/stream, data-quality timestamp, and rate-limit/error behavior. Keep signal logic and ledger schema independent from vendor payload shape.

# 5. Telegram: free delivery, limits and user-side reliability

Telegram states that the Bot Platform is free for users and developers. Its ordinary broadcast limits are not a meaningful bottleneck for a low-volume personal alert system, but delivery is rate-limited and access path reliability remains a separate concern [S3-S4].

| **Constraint**               | **Documented condition / operational interpretation**                                                                                                                                                                                                                                              | **Later requirement**                                                                                                                                                                                                                                                                      |
|------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Permission to contact        | Bots cannot start a private conversation; the user must message the bot first or add it to a group [S4].                                                                                                                                                                                         | Onboarding must be explicitly completed by the intended recipient; store only the authorized chat identifier, not arbitrary recipient discovery.                                                                                                                                           |
| Message limits               | Telegram FAQ: avoid more than 1 message/second in one chat; groups \<=20 messages/minute; broadcasts about 30 messages/second free. Paid broadcasts are irrelevant to a single-recipient screener [S3].                                                                                          | Per-chat queue plus event aggregation. Never burst a threshold-crossing cascade into dozens of duplicate messages.                                                                                                                                                                         |
| Rate/error handling          | FAQ says excess rates eventually return HTTP 429. BCS API separately explicitly recommends handling 429 with exponential backoff [S5]. Telegram API also exposes API-level response/error information [S3].                                                                                    | Retry only retryable errors; honor retry-after when supplied; capped exponential backoff + jitter; record attempt count, response code, returned message id and last error.                                                                                                                |
| Deduplication                | A send can succeed while the client times out before it sees the response; naïve retries can duplicate alerts. Telegram does not serve as the private project ledger.                                                                                                                              | Use a durable outbox with deterministic dedupe key (strategy/version + pair + event/bar timestamp + event type). Record “send outcome uncertain” separately and reconcile or mark it rather than blindly resending.                                                                        |
| Delivery versus action       | API success means message accepted by Telegram, not that the person noticed it or acted. Read/seen/user-action confirmation is not established by the send result.                                                                                                                                 | Track \`queued\`, \`sent\`, \`send_uncertain\`, \`delivery_failed\`, \`expired/stale\`, and separately recorded human acknowledgement/intervention. Do not mark a position filled from a Telegram response.                                                                                |
| Outage and stale alerts      | An alert channel can fail precisely when data, network or the process fails. Same-host “send a Telegram alert that Telegram is down” is logically impossible.                                                                                                                                      | Expose last-success timestamps and a health heartbeat; use an independent watchdog/secondary channel only if later justified. When delivery, clock or feed health is unknown, display impaired status and suppress new-entry eligibility.                                                  |
| Privacy and secret handling  | Bot tokens are bearer-like credentials embedded in Bot API request URLs; storing full request URLs in logs can leak them. Telegram messages can contain private trading information.                                                                                                               | No tokens in prompts, public Spaces, source control, URLs/logs, screenshots or chat transcript. Redact URL paths and exception objects. Send minimal details (event id, pair, status, timestamp, dashboard access path) rather than account or credential data.                            |
| Regional/user network access | A third-party live monitor reported Telegram domain blocking on Russian broadband networks on 21 Oct 2026; OONI published measurement evidence of Russian ISP blocking beginning 20 Mar 2026 [S18-S19]. These observations are location/provider-specific, not proof of this user’s access path. | Before relying on Telegram, test from the actual later deployment egress and recipient network with a user-approved benign test. Do not change the production VPN to make the test pass. If user-side access remains uncertain, Telegram cannot be the sole critical notification channel. |

Data-minimization rule: notifications should not carry broker tokens, balances, tax status or detailed account identifiers. A future bot should be outbound-only for notifications unless a separately specified command surface is needed. Any inbound commands require recipient allowlisting, authorization per command, replay protection, and no order/funding command in the initial branches.

# 6. Operational failure budget and fail-safe behaviour

The failure budget must be expressed as limits and explicit state transitions, not a vague uptime target. The thresholds below are proposals for test acceptance, not measured reliability promises and not guarantees on manual response time or trading outcomes.

| **Failure mode**                         | **Detection / proposed signal**                                                                                                                     | **Safe response**                                                                                                                                                                                                              | **Recovery / evidence to keep**                                                                                                                                     |
|------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Process crash / repeated restarts        | systemd unit state, restart count, last successful heartbeat, exit code, alert outbox age.                                                          | Restart only within a capped policy; after repeated failures enter degraded mode and suppress new entries. Do not repeatedly restart a crash-loop without limit.                                                               | Restart count, logs with secrets removed, checkpoint/event cursor; exercise forced termination at multiple commit boundaries.                                       |
| Stale / partial / revised market data    | Per-source/per-instrument last successful timestamp, expected next update by session calendar, gap count, timestamp age and cross-field validation. | Mark data stale/unknown; no new-entry eligibility; do not substitute old values as current or infer zero OI. Existing-position operational decisions remain manual per policy.                                                 | Preserve bad/late payload and quality flags; identify recovery gap; backfill in a bounded job, then reconcile event stream before re-enabling.                      |
| Disk full / inode full                   | df free bytes/inodes, file-growth slope, SQLite \`SQLITE_FULL\`, WAL/log growth.                                                                    | Stop data ingestion before storage exhaustion; preserve ledger and health reporting; no deletion of raw artifacts silently.                                                                                                    | Rotate only declared logs; archive after checksum/manifest; test write-failure handling; restore space before restart.                                              |
| Swap pressure / OOM / CPU starvation     | vmstat swap-in/out, \`/proc/pressure/\*\` if present, kernel/oom evidence if safely collected, process RSS/CPU.                                     | Pause bulk work or disable it by scheduler; collector must not monopolize the one vCPU; no automatic scaling or sysctl tuning.                                                                                                 | If project is material cause or host reserve cannot be restored, roll back project process only using approved commands; verify VPN/other workload health.          |
| External source/API outage or throttling | Timeout/5xx/429 counters, retry-after, latency p95, stream disconnect, no-data heartbeat.                                                           | Capped backoff, randomized staggering; open a circuit after repeated failures; tag data source degraded; do not switch to an unapproved provider or undocumented endpoint.                                                     | Resume with rate-limited catch-up, bounded date windows, idempotent checkpoints and reconciliation; preserve error types/response metadata.                         |
| Telegram outage / undelivered alert      | Last successful send, pending queue age, error/429 state, separate health state.                                                                    | Prioritize risk and outage notifications; aggregate noncritical alerts. | Session/holiday/clock boundary           | Host clock sync; source timestamp versus UTC receive time; calendar version and expected trading sessions.                                          | Do not infer market closed/open from a daily wall-clock schedule alone. ## Recovery objectives to test, not promise

| **Measure**             | **Proposed test target**                                                                                                                                      | **Important qualification**                                                                                          |
|-------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------|

# 12. Falsification criteria and project changes

The present thin-VPS hypothesis is falsified if any of the following is found during later authorized preflight or benchmark work:

- The real available background headroom is below the minimum safe envelope once VPN + the scheduled workload are included; or the project cannot meet its limit without reducing monitoring coverage.

- Even daily-only data collection causes recurring timeouts, rate-limit storms, CPU or memory pressure, disk-growth violations, or missed health/alert work.

- Free accessible feeds lack required expired-contract history, open interest, contract metadata, timestamps or usable freshness for the intended signal horizon.

- User-side Telegram access is too unreliable and no independently functioning, acceptable alternate alert route is available; critical alerts then cannot be considered dependable.

- State recovery/replay can lose committed events, generate duplicate side effects, hide a data gap or present a stale quote as live; the prototype must remain research-only until corrected.

- The only way to make the stack fit would be to touch protected VPN/network components or consume core-account collateral/permissions beyond explicit approval.

- The only candidate free/paid service requires a prohibited payment method/phone, unsupported region, terms acceptance incompatible with confidential data, or an always-on guarantee it does not make.

## Possible changes if a gate fails

- Move broad history and research to the Mac; reduce VPS to health/outbox only or remove it from the live loop entirely.

- Start with daily end-of-day signals and an explicitly bounded watchlist; do not force 15-minute polling if the provider limits/freshness or resource budget fails.

- Use a separate, justified low-cost host for always-on monitoring rather than reconfiguring the VPN host; require cost, region, backup and exit plan review.

- Replace “always-on Telegram alert” with an explicit degraded/no-entry operating state until client path or an alternate channel is verified.

- Keep the broker branch read-only/manual longer. If order idempotency, state reconciliation or safe cancel/flatten semantics cannot be proven from current broker docs and controlled later tests, do not automate order submission.

# 14. Conclusions

The rational starting point is a local-first research workflow with a strictly bounded, optional VPS monitoring component. The first deployment can remain a single small process or a minimal pair of processes only if the measured total RSS and CPU fit a negotiated budget without affecting the VPN or existing workload. Large research should be scheduled offline. Portable raw snapshots, versioned data releases and a replayable ledger matter more to evidence quality than containerizing or selecting a server database now.

Treat MOEX delayed/free data, BCS API access, Telegram reachability and Gemini/Hugging Face/Colab availability as separate external contracts that can change. The system must have explicit “data stale,” “alerts impaired,” “state uncertain,” “resource budget exceeded” and “recovery pending” states. No new-entry eligibility should survive an unresolved critical condition. Manual operations, capital limits, emergency funding and broker execution remain outside this stage and cannot be inferred from a working stack.

No feasibility measurements were made. The next defensible claim after this report is not “it fits,” but “the specific measured workload passed the stated gates on the observed host, at the recorded times, under an explicit rollback and recovery plan.”

# Appendix A. Calculation notes

| **Quantity**                 | **Calculation / range**                                                                                                                    | **Interpretation**                                                                                                                                             |
|------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Daily bars                   | N contracts × 252 days/year × years                                                                                                        | 252 is a planning convention, not the actual calendar/session count for all futures.                                                                           |
| Normalized bar bytes         | 100-200 bytes/row assumed                                                                                                                  | Used for simple planning only; includes identifying fields and common OHLCV/OI scalars but not all database indexes or raw JSON.                               |
| Daily storage envelope       | Normalized bytes × 2-5                                                                                                                     | Represents raw+normalized/index/provenance sizing sensitivity, not a measured compression ratio.                                                               |
| Intraday observations/year   | 2 × pair count × (12 hourly or 48 quarter-hourly samples/day) × 252                                                                        | Assumes 12 effective observation hours/session/day and one observation per contract leg, even though actual contracts have different sessions.                 |
| Intraday network             | Observations × 0.5-5 KiB/response assumed                                                                                                  | An explicitly assumed payload range, not an observed API payload. Streaming, batching and transport compression can materially change it.                      |
| Proposed resource thresholds | \<=120 MB steady RSS; \<=150 MB peak; \<=1 GB project disk; \>=2 GB and \>=15% free disk; \<=5% average CPU in proposed background window. | Conservative initial gates to be reconciled against real host baseline and service overhead; revise downward or move off-host if measured headroom demands it. |
