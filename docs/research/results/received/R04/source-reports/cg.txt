# R04 — бесплатные рыночные данные и историческая полнота

**Дата исследования: 7 октября 2026 г.**
Исследуемый вопрос: какие самые мелкие практически полезные бесплатные данные доступны по фьючерсам Московской биржи для истории и мониторинга, и какие выводы нельзя делать без платных либо самостоятельно собираемых котировок. 

## Итог

Для этого проекта я бы разделил понятия **«технически доступно бесплатно»** и **«можно законно и воспроизводимо использовать как историческую исследовательскую базу»**.

Главный результат:

> **Самый мелкий практически полезный бесплатный слой для будущего сбора — 1 минута, но его надёжная история должна собираться самостоятельно из разрешённого брокерского потока.**
> **Самый мелкий исторический слой, который можно уверенно считать общедоступным без покупки исторического MOEX-фида, — дневные данные; для календарных спредов на сайте MOEX публично видны дневные Last/Bid/Ask/High/Low/Volume/Trades.**

MOEX ISS технически предоставляет текущие рыночные данные бесплатно с задержкой, а платный режим добавляет realtime; в старом, но официальном ISS Developer Manual прямо сказано: **“It is possible to get delayed market data for free or subscribe for real-time.”** При этом тот же документ указывает, что **historical data и orderbooks доступны подписчикам**. 

Для текущих фьючерсов современная документация MOEX/ALGOPACK описывает **M1 candles**, current `BID`/`OFFER`/`LAST`, `NUMTRADES`, `VALTODAY`, `VOLTODAY`; но это не означает бесплатную многолетнюю историческую выдачу этих полей. ([moexalgo.github.io][1])

### Практически для проекта

| Задача                                        | Наиболее мелкий полезный бесплатный слой    | Ограничение                                                                     |
| --------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------- |
| Скрининг пар за годы                          | **1 день**                                  | Не позволяет восстановить исполнение                                            |
| Исторический carry/relative value             | **1 день + settlement + OI**                | Недостаточно для intraday timing                                                |
| История календарных спредов                   | **1 день, включая Bid/Ask**                 | Спред уже агрегирован за день                                                   |
| Будущий мониторинг вручную                    | **1 минута**                                | Нужен разрешённый realtime/near-real-time брокерский поток или собственный сбор |
| История для исследования после начала проекта | **1 минута, собирать самому**               | Backfill до даты начала не решается                                             |
| Проверка фактического исполнения              | **тики/сделки + Bid/Ask**, лучше ещё стакан | Исторический слой обычно платный или self-collected                             |
| Очередь/проскальзывание/вероятность fill      | **L2/L3, snapshots/events**                 | Обычный OHLCV этого не содержит                                                 |

# 1. Что реально даёт MOEX бесплатно

## 1.1. ISS: бесплатный текущий слой, но не бесплатная историческая база

Официальный **MOEX ISS Developer manual, Version 1.4** описывает два разных пространства:

* `/iss` — текущие market data;
* `/iss/history` — historical data/trading results.

В нём перечислены `trades`, `orderbook`, `candles`, `candleborders`, `dates`, `turnovers`, `listing` и другие объекты. Ключевое ограничение указано непосредственно в документе: **“Orderbooks and historical data are only available to the paid subscribers.”** Для неавторизованного пользователя текущие данные идут с **15-minute delay**. 

При этом MOEX продолжает прямо описывать ISS как источник:

> “static market data … trades, best quotes, general market data, historical trade results and chart data.”

и указывает бесплатный delayed-доступ и платный realtime. ([Moscow Exchange][2])

**Вывод:** публичный endpoint ISS — не доказательство наличия бесплатной многолетней истории. Технический API и право/тариф доступа надо рассматривать отдельно.

---

## 1.2. Что бесплатно видно по фьючерсам прямо сейчас

Текущая документация MOEX для FORTS описывает свечи:

* `OPEN`
* `HIGH`
* `LOW`
* `CLOSE`
* `VALUE`
* `VOLUME`
* `FROM`
* `TILL`

с интервалом **M1** как доступным форматом в realtime WebSocket-документации. Для текущей статистики фьючерсов также документированы `BID`, `OFFER`, `LAST`, `NUMTRADES`, `VALTODAY`, `VOLTODAY`. ([moexalgo.github.io][1])

Но эта документация относится к современному **MOEX ISS+/ALGOPACK** интерфейсу и сама по себе **не даёт оснований считать исторические M1 бесплатно доступными без подписки**. На странице ALGOPACK для real-time market data отдельно указывается, что авторизованному пользователю отдаётся realtime, а неавторизованному ISS — 15-минутно задержанные данные и ограниченный набор полей. ([moexalgo.github.io][3])

# 2. Самая полезная бесплатная история

## 2.1. Официальные дневные итоги по фьючерсам

Открытый архив MOEX по Срочному рынку содержит для фьючерсов, среди прочего:

* код контракта;
* дату экспирации;
* средневзвешенную цену;
* расчётную цену;
* первую сделку;
* максимум/минимум;
* последнюю цену;
* изменение;
* объём последней сделки;
* число сделок;
* объём торгов;
* open interest.

Такие страницы доступны по отдельным торговым дням и показывают как действующие, так и истёкшие контракты, когда они присутствуют в соответствующем дневном архиве. ([Moscow Exchange][4])

MOEX также предоставляет отчёты по фьючерсам за неделю/месяц/квартал и страницы итогов по конкретной дате. ([Moscow Exchange][5])

### Что это позволяет делать

На дневных данных уже можно исследовать:

* существование и ликвидность пары;
* динамику basis/calendar spread;
* изменение OI;
* дневные доходности;
* волатильность;
* грубое ранжирование широкого набора пар;
* rollover/expiry-структуру;
* проверки гипотез, не зависящих от внутридневного исполнения.

### Чего нельзя

Нельзя восстановить из этого:

* реальный момент входа;
* реальный Bid/Ask в момент сигнала;
* проскальзывание;
* последовательность движения двух ног;
* вероятность исполнения;
* реакцию на кратковременный разрыв ликвидности.

# 3. Особенно интересный бесплатный источник: сами календарные спреды MOEX

Для этого проекта это существенная находка.

MOEX публикует отдельные страницы **Historical data of calendar spreads**. В них по каждому дню есть:

`Last | Bid | Ask | Daily high | Daily low | Amount | Volume | Trades`

и присутствуют варианты скачивания CSV. ([Moscow Exchange][6])

Это лучше обычного дневного OHLCV по ногам для **первичного screening**, потому что биржа уже публикует фактическую дневную статистику самого spread-инструмента.

Но есть два серьёзных ограничения:

1. это **дневная агрегация**, а не временной ряд bid/ask внутри дня;
2. эти Bid/Ask не дают истории того, **какие цены можно было одновременно исполнять по обеим ногам**.

Поэтому из этих страниц можно получить доказательство «у спреда была такая дневная котировка/торговая активность», но нельзя получить честный intraday executable backtest.

# 4. Settlement price, OI и риск-параметры

## 4.1. Расчётные цены

В марте 2026 MOEX отдельно сообщила, что settlement prices публикуются в ISS в поле:

`SETTLEPRICE_CLR`

для фьючерсов и календарных спредов, причем текущие значения можно получать бесплатно с задержкой 15 минут. Архив доступен через ISS, итоги торгов и файловые архивы. ([Moscow Exchange][7])

Это очень полезный бесплатный компонент, потому что settlement price напрямую связан с вариационной маржой и не является просто `Close`.

**Для проекта settlement нужно хранить отдельно от last-trade close.**

---

## 4.2. ГО/ставки риска

Здесь бесплатная картина значительно хуже.

MOEX публично публикует изменения риск-параметров. Например, 2 марта 2026 года были опубликованы изменения `MR1/MR2/MR3` и `MRcurr1/MRcurr2/MRcurr3` для отдельных фьючерсов. ([Moscow Exchange][8])

Документы MOEX/NCC также описывают ситуации, когда из-за изменения/расширения параметров риска пересчитываются ценовые лимиты и диапазоны риска, причём отдельные уровни могут меняться при определённых событиях рынка. ([MOEX][9])

Отсюда важный вывод:

> **Исторического “одного числа ГО” для бэктеста недостаточно.**

Нужно знать как минимум:

`instrument × date/time × risk regime × applicable parameter`

и отдельно отличать:

* риск-параметр;
* price limits;
* concentration limits;
* непосредственно требуемое брокером ГО.

Полную point-in-time историю этих величин из публичного бесплатного набора я **не подтвердил**.

---

# 5. Спецификации и исторический survivorship

Это одна из самых важных частей для проекта.

В сентябре 2025 MOEX прекратила публикацию старого `FORTS_LIST.TXT` и указала, что справочники и описания инструментов Срочного рынка теперь нужно получать через ISS, а ежедневные справочные данные предоставляются отдельным Reference Data product. ([Moscow Exchange][10])

То есть для point-in-time истории нельзя просто сегодня взять список фьючерсов и применить его назад.

Нужно сохранить:

* `SECID`;
* тикер/код;
* базовый актив;
* срок исполнения;
* lot/multiplier;
* `MINSTEP`;
* валюту;
* торговые режимы;
* даты допуска/экспирации;
* price limits;
* relevant risk parameters.

**Текущий справочник ≠ исторический point-in-time universe.**

# 6. Expired contracts

Здесь ситуация неоднородная.

Официальный архив MOEX по результатам торгов действительно позволяет обращаться к данным **по конкретной дате** и тем самым видеть старые контракты, а отдельный раздел MOEX содержит архив/списки срочных контрактов. ([Moscow Exchange][5])

У Finam также существует **«Архив фьючерсов Московской биржи»**, в котором видны старые коды контрактов, включая контракты прошлых лет; страница прямо помечена как источник исторических данных по MOEX futures. ([finam.ru][11])

Но ни один из этих результатов не позволяет заявить:

> «полная M1/tick история всех expired contracts за весь период существует бесплатно».

Такого доказательства найдено не было.

# 7. Finam и прочие бесплатные альтернативы

## Finam

На странице котировок фьючерсов Finam показывает:

> “Задержка — 15 минут.”

Есть раздел экспорта и исторический архив. ([finam.ru][12])

Для экспортного сервиса Finam публикует ограничения:

* сделки — максимум 1 день за запрос;
* intraday candles — до 4 месяцев;
* daily candles и выше — до 5 лет. ([finam.ru][13])

Это делает Finam полезным как **вспомогательный бесплатный источник для проверки**, но не как автоматически доказанную замену историческому MOEX-фиду:

* не подтверждена полнота MOEX futures minute history за весь нужный период;
* есть собственные ограничения;
* есть зависимость от конкретного интерфейса/регистрации;
* данные поступают от MOEX и имеют собственные условия перераспространения.

На отдельных страницах Finam прямо указано: **“Перераспространение информации только с разрешения Московской Биржи.”** ([finam.ru][14])

# 8. Брокерские потоки: наиболее практичный бесплатный путь для будущего

Здесь появляется принципиально другая модель: не «скачать старую историю», а **собирать свою историю начиная с сегодняшнего дня**.

## ВТБ / QUIK

ВТБ сейчас прямо пишет, что QUIK даёт доступ к фондовому, срочному и валютному рынкам, котировки обновляются в реальном времени; для клиентов ВТБ:

* **«Бесплатное подключение»**
* **«Нет абонентской платы»**.

Также заявлены интеграции с архивами, базами данных, экспертными системами и т.д. ([VTB Bank][15])

Это делает QUIK наиболее естественным кандидатом для **собственного накопления realtime-истории**, если конкретные условия предоставления данных по вашему договору не ограничивают нужный способ использования.

Но из этого нельзя сделать вывод, что ВТБ предоставляет бесплатно многолетний исторический tick archive.

---

## БКС Trade API

Для будущей автоматизации найден существенно более явный интерфейс.

БКС документирует:

* исторические свечи;
* текущие котировки;
* текущий стакан;
* обезличенные сделки;
* WebSocket realtime candles;
* WebSocket realtime order book;
* WebSocket realtime trades. ([BCS Trading API][16])

В частности, WebSocket для последней свечи поддерживает:

`M1, M5, M15, M30, H1, H4, D, W, MN`.

Для стакана документирована глубина до **20 уровней**, а realtime trades содержат `side`, `volume`, `price`, `quantity`, `dateTime`. ([BCS Trading API][17])

Исторические свечи имеют лимит **1440 баров на запрос**; для M1 это максимум одни сутки за запрос. ([BCS Trading API][18])

Авторизация требует получить refresh-token в веб-версии БКС «Мир инвестиций». ([BCS Trading API][19])

**Стоимость непосредственно рыночного потока для клиента из этих страниц не установлена**, поэтому я не называю BCS API «бесплатным источником» безусловно. Это надо проверить по тарифу/договору именно клиентского счёта.

# 9. Самая маленькая технически возможная гранулярность

Документация терминала MOEX Spectra показывает ещё один важный факт: технический анализ строится из сделок, агрегированных в **1 second и 60 seconds** интервалы. При этом исторические данные для expired instruments терминал не загружает, а архивные данные агрегируются примерно в минутный timeframe. ([Moscow Exchange FTP][20])

Поэтому нужно различать:

**1 секунда** — технически возможна как локально агрегируемый слой,
**1 минута** — практически полезный минимальный слой для данного проекта,
но **ни один из этих фактов не доказывает наличие бесплатной полноценной многолетней истории**.

Для среднесрочных ручных spread-стратегий с реакцией порядка нескольких минут я бы рассматривал:

> **raw capture → 1-minute canonical bars → 5-minute research bars**

как рабочий кандидат, но не как окончательно утверждённый стек.

# 10. Исполнимость: где OHLCV перестаёт быть достаточным

Это главный предел бесплатной истории.

Из свечи:

`O/H/L/C/V`

нельзя честно вывести:

* была ли котировка в Bid/Ask;
* какое значение было одновременно на второй ноге;
* сколько времени котировка стояла;
* был ли объём реально доступен;
* сколько лотов было перед вами;
* сколько изменилось до исполнения;
* была ли возможность исполнить две ноги без legging;
* какое проскальзывание возникло бы при ручной реакции.

Особенно опасна идея:

> «внутри свечи был нужный High/Low, значит такой вход можно считать исполненным».

Это неверно для backtest исполнения.

`HIGH` и `LOW` являются экстремумами сделок, а не доказательством одновременной исполнимой комбинации Bid/Ask на двух ногах.

# 11. Что именно невозможно доказать только OHLCV

| Утверждение                                        |                OHLCV | Что нужно                    |
| -------------------------------------------------- | -------------------: | ---------------------------- |
| Пара исторически существовала                      |                   Да | Contract master              |
| Дневной/5m price relationship                      |                   Да | OHLCV                        |
| Дневной momentum/mean reversion                    |                   Да | OHLCV                        |
| OI dynamics                                        | Да, если OI хранится | OI                           |
| Settlement-relative spread                         |                   Да | Settlement                   |
| Был ли конкретный вход исполним                    |              **Нет** | Bid/Ask                      |
| Был ли spread одновременно доступен на обеих ногах |              **Нет** | синхронные quotes обеих ног  |
| Сколько стоял quote                                |              **Нет** | event/snapshot feed          |
| Slippage                                           |              **Нет** | сделки + quotes/order book   |
| Fill probability                                   |              **Нет** | order book/queue information |
| Реальный ручной execution test                     |              **Нет** | свои наблюдения/ордера       |
| Реальное intraday ГО в момент сигнала              |           Обычно нет | point-in-time risk data      |
| Полный survivorship-correct universe               |      Не только OHLCV | historical instrument master |

# 12. Point-in-time слой, который имеет смысл собирать

Минимальная структура для будущего исследования:

### `instrument_master_pti`

`SECID, contract_code, base_asset, expiry, minstep, multiplier/lotsize, currency, valid_from, valid_to, trading_session`

и отдельно:

`price_limit_up/down, risk_regime, MR1/MR2/MR3, relevant margin fields`

### `trades`

Минимум:

`TRADENO, TRADETIME, SYSTIME, PRICE, QUANTITY`

У MOEX/ALGOPACK для trade stream действительно документированы и `TRADETIME`, и `SYSTIME`; это важно для разделения **времени события** и **времени записи/приёма в системе**. ([moexalgo.github.io][1])

### `quotes`

Минимум:

`event_time, receive_time, bid, ask`

Для более качественного исполнения:

`bid_qty, ask_qty, depth levels`.

### `bars_1m`

`begin, end, open, high, low, close, value, volume, trade_count`

плюс желательно `source_last_event_time` и признак completeness.

### `settlement`

`trade_date, published_time, settle_price, source_version`

### `risk`

`valid_from, valid_to, MR1, MR2, MR3, price limits, concentration regime`

Это и будет нормальная **point-in-time база**, вместо попытки реконструировать прошлое из сегодняшних справочников.

# 13. Важный юридический предел бесплатного ISS

Здесь есть противоречие, которое нельзя замазывать.

Технический ISS Manual говорит о бесплатном delayed market data. 

Но действующее пользовательское соглашение сайта MOEX говорит, что пользователи получают бесплатные и платные информационные сервисы, а условия использования устанавливает Биржа. Пользователям запрещено распространять биржевую информацию и производные данные; отдельные договоры могут давать иные права. ([Moscow Exchange][21])

Отдельно в действующей публичной оферте на информационные услуги MOEX **Non-display** прямо определено как, среди прочего:

> «запись, копирование, систематизацию, преобразование…»

а для соответствующих информационных продуктов разрешено **«Накапливать, хранить и использовать … для собственного внутреннего использования»**. ([Moscow Exchange][22])

Но это положение относится к **платным информационным продуктам по соответствующей оферте**, а не автоматически ко всякому публичному delayed endpoint.

Поэтому безопасный вывод:

> **Публичная техническая доступность delayed ISS не является доказательством права бесконечно автоматически собирать, хранить и использовать эту историю как non-display dataset.**

Для проекта это означает: **не строить нормативное обоснование на факте, что endpoint отвечает без авторизации**.

---

# 14. Фактические ограничения по полноте

Исследование подтвердило наличие публичных данных в нескольких временных точках: официальные архивы доступны как минимум для отдельных дат июня, августа, сентября и октября 2026 года; текущие страницы также показывают expired/текущие контракты. ([Moscow Exchange][23])

Но **полный earliest timestamp бесплатной M1-истории по каждому SECID не установлен**.

Причины:

1. historical namespace ISS документирован как subscription-only;
2. прямой запрос к ISS API в этом сеансе браузинга не отработал, поэтому я не буду выдавать его фактический ответ за выполненный аудит;
3. наличие архивной web-страницы не доказывает полноту minute/tick history;
4. текущий instrument master не гарантирует historical survivorship.

### Поэтому формулировка результата

**Не подтверждено:**

> «Бесплатно можно получить полную M1 историю всех фьючерсов MOEX за N лет».

**Подтверждено:**

> бесплатно доступны текущие delayed market data; официальные дневные результаты и settlement; публичная дневная история календарных спредов; текущие спецификации; отдельные публичные риск-публикации. ([Moscow Exchange][7])

# 15. Объём данных: оценка, а не измерение

Торговый календарь MOEX на 2026 год показывает режим торговли Срочного рынка **06:50–23:50**, 337 торговых дней, включая дополнительные выходные/праздничные сессии. 

Это примерно:

`17 часов × 60 = 1 020 минут/день`.

Тогда:

### 50 контрактов, M1

`50 × 1 020 × 337 ≈ 17,2 млн строк/год`

### 100 контрактов, M1

`≈ 34,4 млн строк/год`

При условных 120–200 байт на одну сырую строку:

* 50 контрактов: примерно **2,1–3,4 ГБ/год**;
* 100 контрактов: примерно **4,1–6,9 ГБ/год**.

Это только оценка, без индексов, резервных копий и дополнительной metadata.

### Tick-уровень

В одном торговом дне MOEX может показывать порядка **2–3 млн сделок по всему Срочному рынку**; например, 5 октября 2026 года архив показывает около 2,36 млн сделок. ([Moscow Exchange][24])

Даже при нереалистично малых 40 байт/сделку:

`2,36 млн × 337 × 40 ≈ 31,8 ГБ/год`

до индексов и прочих полей.

Поэтому **полный raw-trade архив всего FORTS для VPS на 20 ГБ — практически не тот режим хранения, на который стоит рассчитывать**.

Для выбранной небольшой universe ситуация намного лучше.

---

# 16. Что это означает для ноутбука и VPS

### Ноутбук, 16 ГБ RAM

Нормально подходит для:

* нескольких десятков/сотни инструментов;
* 1m bars;
* point-in-time metadata;
* исследования по чанкам;
* хранения нескольких лет агрегированных данных.

### VPS, 1 ГБ RAM + 20 ГБ disk

Разумно использовать для:

* приёма маленькой текущей universe;
* хранения компактных M1/M5;
* Telegram-мониторинга;
* коротких rolling buffers.

Неразумно закладываться на:

* полный FORTS tick archive;
* большой raw order book archive;
* несколько лет сырых ticks;
* многочисленные параллельные исторические выгрузки.

При заданном пользовательском бюджете фоновых процессов **250–350 МБ**, даже компактный M1 collector потенциально реалистичен, но это пока **оценка**, а не измерение фактического потребления.

---

# 17. Рекомендованный кандидат по таймфрейму

Не окончательный выбор стека, а рабочий исследовательский кандидат:

### Основной: **5 минут**

Почему:

* в проекте реакция ручной торговли — минуты, а не секунды;
* 1m сохраняется как более мелкий слой;
* 5m значительно уменьшает объём и количество ложных микроизменений;
* среднесрочные spread-сигналы обычно не требуют микросекундной реконструкции.

### Альтернатива: **1 минута**

Нужна для:

* оценки чувствительности входа к latency;
* несинхронных движений ног;
* коротких sharp dislocations;
* формирования более реалистичных trigger windows.

### Контрольная агрегация: **15 минут**

Полезна для sanity check и более грубых среднесрочных моделей.

**1 секунда** я бы не делал исследовательским основным слоем: это уже дорого по истории и плохо согласуется с ручным режимом; кроме того, бесплатной полной истории такого уровня я не подтвердил. ([Moscow Exchange FTP][20])

---

# 18. Что можно исследовать уже сейчас бесплатно

Без покупки исторического фида уже можно сделать достаточно большую независимую часть проекта:

**Да:**

* сформировать universe контрактов;
* проверить сроки экспирации;
* собрать дневные цены;
* собрать settlement;
* собрать дневные Volume/OI;
* получить исторические дневные calendar-spread statistics;
* оценить длительность жизни контрактов;
* выявить пары с достаточной торговой активностью;
* провести screening по среднесрочным price relationships;
* подготовить точную спецификацию того, какие данные нужно собирать дальше.

**Нет:**

* честно доказать исторический executable edge;
* восстановить historical Bid/Ask на нужной минуте;
* подтвердить realistic slippage;
* доказать fill probability;
* восстановить point-in-time ГО без отдельной временной истории risk parameters;
* считать OHLC-extrema фактом исполнимой сделки.

---

# 19. Что становится платным или требует собственного сбора

Наиболее важная граница:

### Можно получить бесплатно

`daily OHLC + volume + OI + settlement + specifications`

и в некоторых случаях:

`daily calendar-spread Bid/Ask`.

### Понадобится платный/специальный источник или собственный сбор

`historical intraday Bid/Ask`
`historical order book`
`historical tick/trade tape за длинный период`
`point-in-time risk/margin snapshots`
`execution-quality data`
`queue/depth history`.

Для проекта **self-collected history** с даты запуска поэтому не является запасным вариантом — это фактически наиболее логичный способ постепенно закрыть исторический дефицит без покупки большого архива.

# 20. Воспроизводимый аудит публичных данных

**Фактически выполнено:** чтение и сопоставление публичных страниц MOEX, документации ISS, публичного архива FORTS, страниц calendar spreads, текущей документации MOEXAlgo, BCS API, ВТБ/QUIK и Finam.

В текущем браузинговом окружении прямой ISS endpoint вернул ошибку доступности. Поэтому я не приписываю ему измеренные timestamps, row counts или глубину, которых лично не получил.

# 21. Условия, при которых вывод придётся пересмотреть

Решение изменится, если проверка покажет хотя бы одно из следующего:

1. MOEX даёт законно использовать бесплатный delayed ISS в качестве постоянного non-display historical store для собственного исследования;
2. конкретный брокерский счёт включает без отдельной платы достаточный historical/intraday market-data service;
3. выяснится, что у требуемой universe есть полная бесплатная M1 история по expired contracts;
4. point-in-time risk parameters имеют публичный архив, полный для нужного периода;
5. целевой горизонт окажется настолько быстрым, что 1m станет недостаточным.

# Вывод для проекта

**Самый маленький практически полезный бесплатный набор сейчас:**

**История:**
`1D OHLC + Volume + OI + Settlement + contract master`
и, где доступно, `1D calendar-spread Last/Bid/Ask/High/Low/Volume/Trades`.

**С момента запуска собственного сбора:**
`1m bars` по обеим ногам + желательно `trade/quote timestamps`.

**Для реального исполнения:**
нужны `Bid/Ask` как минимум, а для серьёзной проверки fill/slippage — ещё и исторический стакан или собственные записи стакана.

Главное ограничение не в том, что «бесплатных котировок вообще нет». Оно в том, что **бесплатный публичный слой не даёт надёжно доказанной многолетней истории исполнимых цен**. Для среднесрочных спредов это принципиальная разница: дневный OHLCV годится для исследования экономической идеи, но не доказывает, что стратегия могла реально исполняться с заданным лимитом отставания от LQDT.
